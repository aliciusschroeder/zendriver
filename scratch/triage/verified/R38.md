## Lens: reproduce (verdict confirmed, realism medium, severity wrong-result)

### Summary
All four keys.py defects reproduce in real headless Chromium 141 (Python 3.13). (1) Grapheme clusters of 4 or more UTF-16 units are sent as a single char event, Chrome rejects them, and typing stops partway through. (2) Modifiers are released before the main key and in press order, so the main keyup carries no modifiers. (3) to_cdp_events mutates self.key, so a reused KeyEvents types a different character the second time. (4) SpecialKeys.SPACE sends code ' ', so the page sees e.code === ''.

### Refinements
A10.5: the call stops at the first long grapheme, so earlier characters are typed and later ones are lost; the field is left partly filled. Emoji of 2 units or fewer work. A10.9: besides the missing modifiers on the main keyup, each modifier keyup reports modifier state with its own flag cleared (Shift up reports shift=false) while the others are still set. A10.10: the CHAR-path mutation also turns a SpecialKeys member into a str, which changes later DOWN_AND_UP events (ENTER mutated to '\n' still maps back to Enter).

### Member verdicts
- A10.5: confirmed — Real Chromium, textarea.send_keys('x'+s+'y'). '👍' (2 units) works and the value becomes 'x👍y'. '👍🏽' (4 units), '🇩🇪' (4) and the family ZWJ emoji (11) each raise ProtocolException "Invalid 'text' parameter [code: -32602]" on Input.dispatchKeyEvent{type:'char', text:<whole grapheme>}, and the value is left as 'x'. from_mixed_input(['Hi 👍🏽!']) fails the same way and leaves 'Hi '. The cause is in KeyEvents.from_text / to_cdp_events (the CHAR branch for emoji): the grapheme library returns the whole cluster as one grapheme, and that cluster goes out as one char event.
- A10.9: confirmed — Document keydown/keypress/keyup logger. from_mixed_input(['A']) logs keydown Shift, keydown 'A' shift=true, keypress 'A', keyup Shift, keyup 'a' shift=false. Ctrl+Shift+a releases Control before Shift (press order, not reverse), and the final keyup 'a' has shift=false, ctrl=false. In KeyEvents.to_down_up_sequence, step 3 clears all modifiers before step 4 sends the main keyup.

Mutation sites: to_cdp_events (`self.key, override_modifiers = self._normalise_key(...)`) and _get_key_and_text (`self.key = self.conv_to_str(...)`).
- A10.11: confirmed — Real Chromium logger. send_keys(SpecialKeys.SPACE) and from_mixed_input([' ']) both log keydown " " with an empty code and keyCode 32. The control send_keys(SpecialKeys.TAB) logs code 'Tab'. ## Lens: refute (verdict confirmed, realism high, severity crash)

### Summary
I tried to refute all four keys.py members and could not. Each one reproduces in real headless Chromium 141 on Python 3.13. The most serious is A10.5: send_keys(str) sends each emoji grapheme as one 'char' event, and Chrome rejects any text of 4 or more UTF-16 units. So skin-toned emoji, flags and ZWJ sequences raise ProtocolException partway through typing. The other three are wrong-result bugs with lower realism. They only appear on the DOWN_AND_UP path (from_mixed_input, SpecialKeys, or a KeyEvents object the user builds and reuses).

### Refinements
A10.5: this is a Chrome limit (text must be under 4 UTF-16 units). Single-codepoint emoji and short combining sequences work; it fails on skin-tone modifiers, flags, keycaps, ZWJ families and long combining clusters. Earlier graphemes have already been typed when it raises. A10.9/A10.11: only the DOWN_AND_UP path is affected (from_mixed_input, SpecialKeys, explicit KeyEvents). Plain send_keys(str) uses CHAR, sends no keydown/keyup, and so cannot show these two bugs. A10.9 matters only to keyup handlers that read modifiers or e.key. Real keyboards also produce Shift-up before A-up during rollover, so robust pages already cope. A10.10 needs explicit reuse of a KeyEvents object.

### Member verdicts
- A10.5: confirmed — In real Chromium I called send_keys('x'+s+'y') for each case. Thumbs-up (2 UTF-16 units) and e+combining acute (2 units) both work. Thumbs-up with a skin tone (4), the DE flag (4), the family ZWJ emoji (11) and a+3 combining marks (4) each raise ProtocolException "Invalid 'text' parameter", and the field is left holding 'x'. Nothing upstream splits graphemes: KeyEvents.from_text passes the whole grapheme to to_cdp_events(CHAR). The repo test test_visible_events types a thumbs-up emoji, so emoji support is intended.
- A10.9: confirmed — In KeyEvents.to_down_up_sequence, step 3 releases the modifiers in press order, although its comment says reverse order. It does this before step 4 (main keyup), which then carries modifiers=0. Chrome log for Ctrl+Enter: keyup Control (ctrl=false), then keyup Enter (ctrl=false). For 'A': keyup Shift, then keyup 'a' (shift=false). For Ctrl+Shift+a, Control is released before Shift. Keydown carries the correct modifiers, so shortcuts handled on keydown still work (Ctrl+A/C/V in the repo test).
- A10.10: confirmed — Offline, KeyEvents('A').to_cdp_events(DOWN_AND_UP) gives Shift plus text 'A' the first time and plain 'a' with no Shift the second time. For '!' the second call gives '1'. In real Chromium, sending the same KeyEvents('A') object twice types 'Aa'. Cause: to_cdp_events assigns self.key = _normalise_key(...). zendriver itself never reuses an instance (from_text and send_keys build new ones), so only user code that reuses the public class is affected.
- A10.11: confirmed — In real Chromium, send_keys(SpecialKeys.SPACE) and from_mixed_input([' ']) produce keydown key=' ' with code '' (empty) and keyCode 32. TAB gives code 'Tab'. A space is still inserted, and e.key and e.keyCode are correct, so only handlers that check e.code === 'Space' miss it. send_keys(' ') with a str goes through CHAR and sends no keydown at all.

## Lens: fixsafety (verdict confirmed, realism high, severity crash)

### Summary
Confirmed all 4 keys.py claims against real headless Chromium 141 on Python 3.13. (1) Any grapheme of 4 or more UTF-16 units is sent as a single char event, and Chrome rejects it with ProtocolException "Invalid 'text' parameter" after the earlier characters are typed. 3 units are accepted. (2) to_down_up_sequence releases the modifiers first, in press order, and then sends the main keyup with modifiers=0. (3) The DOWN_AND_UP path does `self.key, ... = self._normalise_key(...)`, which rewrites self.key, and the CHAR path turns a SpecialKeys key into a str. (4) SpecialKeys.SPACE is (' ', 32), so the page sees e.code ''.

### Refinements
A10.5 is wider than emoji: any grapheme of 4 or more UTF-16 units fails, combining-mark sequences included, because every grapheme without a keyCode is forced onto the CHAR path. The exact limit is text16.size() >= 4 (3 accepted, 4 rejected). A10.10: the CHAR-path mutation mostly changes only the key's type, since SpecialKeys becomes str, but it is still a mutation. Seen in passing and not part of this group: Ctrl+Shift+a reports keydown key 'a' with shiftKey=true, because _handle_printable_char only upper-cases when modifiers == Shift exactly.

### Member verdicts
- A10.5: confirmed — Real Chromium: send_keys('x'+s+'y') raises ProtocolException Invalid 'text' parameter and leaves the textarea holding 'x' for s = skin-toned thumbs up (4 units), the DE flag (4) and the family ZWJ emoji (11). It also fails for a non-emoji grapheme 'a'+U+0301+U+0302+U+0303 (4 units), because unknown graphemes take the same CHAR path. The plain thumbs up (2 units) works. Splitting the text into chunks of at most 3 units works in a textarea, an input and a contenteditable.
- A10.9: confirmed — Key log, from_mixed_input(['A']): keydown Shift, keydown 'A' shift=true, keyup Shift, keyup 'a' shift=false. Ctrl+Enter: keyup Control comes before keyup Enter, and the Enter keyup has ctrl=false. Ctrl+Shift+a releases Control before Shift.
- A10.10: confirmed — ev=KeyEvents('A'): the first to_cdp_events(DOWN_AND_UP) keyDown texts are [None,'A'], the second are ['a'], and ev.key is now 'a'. The same happens for '!', '_' and '\n'. The CHAR path also rewrites KeyEvents(SpecialKeys.ENTER).key into '\n'.
- A10.11: confirmed — Real Chromium: send_keys(SpecialKeys.SPACE) and from_mixed_input([' ']) log keydown " " with an empty e.code. TAB logs code Tab.

### Fix assessment
- kind: minimal-local
- prototype: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/BE-fixsafety/R38/pkg
- regression test: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/BE-fixsafety/R38/tests/test_r38_keys.py
- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: keys.py only. (a) SpecialKeys.SPACE = ('Space', 32). (b) _get_key_and_text CHAR path uses a local variable and no longer assigns self.key. (c) The to_cdp_events DOWN_AND_UP branch normalises into a new instance, type(self)(key, self.modifiers).to_down_up_sequence(mods), so self is never mutated. (d) The to_cdp_events CHAR branch splits the payload text with a new classmethod _split_text into chunks of at most MAX_TEXT_UTF16_UNITS=3 units, never splitting a surrogate pair, and returns one char payload per chunk. (e) to_down_up_sequence sends the main keyUp while the modifiers are still held, then the modifier keyUps in reversed() order.
- risks: No locks or async state are involved. Changes callers could notice: (1) SpecialKeys.SPACE.value changes from (' ',32) to ('Space',32) on a public enum; the alternative is to keep the value and special-case the code in _handle_special_key_lookup and _handle_string_key_lookup. (2) Modifier combos now use real-keyboard order, so page keyup handlers see the modifiers. (3) A long grapheme now produces several keypress/input events, and the intermediate input events hold a partial grapheme. Insert-as-one would need Input.insertText, which is an API change because the payload list only carries dispatchKeyEvent args. (4) type(self)(...) assumes a subclass keeps the (key, modifiers) constructor, which matches how from_text uses cls(...). mypy: 332 errors, the same as an untouched copy, none new. ruff format and ruff check are clean.
