## Lens: refute (verdict confirmed, realism medium, severity crash)

### Summary
I could not refute this. HTTPApi._request in zendriver/core/browser.py (the urlopen call at about line 1133) uses the global urllib opener, which proxies from the environment. With http_proxy or HTTP_PROXY set and no_proxy not listing the literal 127.0.0.1, GET http://127.0.0.1:<port>/json/version goes to the proxy. I reproduced this with real headless Chromium 141: zendriver.start() raised 'Failed to connect to browser ... running as root' after 1.4s. During those same attempts, a direct GET to Chrome's port returned 200 with webSocketDebuggerUrl. Nothing serialises or bypasses this upstream, no test or doc asserts the current behaviour, and git history (shallow, starting at 5c1a005) shows no sign that it is deliberate.

### Refinements
Exact trigger: an HTTP-scheme env proxy (http_proxy or HTTP_PROXY) is set. ALL_PROXY is ignored by urllib (assumed from source, not run). https_proxy alone does not trigger the HTTPApi part.

no_proxy has to be missing the literal '127.0.0.1' (or '*' or '.0.0.1'). The common 'no_proxy=localhost' does NOT protect, and neither do curl/Go-style CIDR entries such as '127.0.0.0/8'; Python ignores both (verified on 3.11 to 3.13). That widens the reach beyond 'no_proxy unset'.

It fails only when the proxy cannot serve the client's loopback, which covers a remote corporate proxy or one that denies loopback destinations (assumed). A same-host forwarding helper such as cntlm or px works for the HTTP leg (verified with a faithful fake forwarder). Even then, websockets>=15 fails on the CONNECT for the ws leg unless that helper allows CONNECT to arbitrary loopback ports.

The result is a fast failure (about 1.4s) with a misleading 'running as root / sandbox' message. A blackholing proxy instead stalls start() for about 10s per attempt, about 110s with defaults.

MacOS: urllib reads system proxy settings when no env vars are set. The default macOS bypass list ('*.local, 169.254/16') does not match 127.0.0.1 in _proxy_bypass_macosx_sysconf (logic verified on Linux; real macOS behaviour assumed). Windows registry proxies: assumed.

Fix scope: (a) bypass only loopback hosts (127.0.0.0/8, ::1, localhost) rather than dropping proxies for every host. connect_existing to a remote DevTools host might legitimately need the proxy. (b) Without a matching proxy=None for loopback in Connection.aopen's websockets.connect (connection.py about line 440), start() still fails for every user on websockets>=15, which is the default pip resolution because pyproject only pins >=14.0. On that path start() also leaks the Chrome process, which is a separate cleanup bug.

Workaround for users: add 127.0.0.1 to no_proxy.

## Lens: fixsafety (verdict confirmed, realism medium, severity crash)

### Summary
Confirmed. HTTPApi._request (zendriver/core/browser.py, class HTTPApi, about line 1133) calls urllib.request.urlopen. urlopen's default ProxyHandler sends GET http://127.0.0.1:<port>/json/version to the http_proxy/HTTP_PROXY from the environment. On Linux, urllib only bypasses the proxy when no_proxy matches, and it never exempts loopback on its own. Every Browser.test_connection attempt then fails, and start() stops Chrome and raises 'Failed to connect to browser ... running as root ... sandbox=False'. A minimal local fix works: give HTTPApi its own opener built with ProxyHandler({}). The fix is incomplete for websockets>=15, which pyproject allows (websockets>=14.0) and which a fresh pip install resolves to. There, websockets.connect in Connection.aopen also takes ws/socks/https/http proxies from the environment by default, so start() still fails even with the HTTPApi fix. Fully fixing it also needs proxy=None on that connect call, gated on the parameter existing, because websockets 14.1 raises TypeError on it.

### Refinements
1. The trigger is narrower than 'behind a proxy'. urllib uses only http_proxy/HTTP_PROXY for the http:// DevTools URL; https_proxy and all_proxy are ignored (urllib registers all_open but never calls it for http). HTTP_PROXY is also ignored when REQUEST_METHOD is set. So on websockets 14.x, an environment with only https_proxy is not affected.
2. On websockets>=15, the CDP websocket picks the first of ws, socks, https, http from the environment via websockets.uri.get_proxy. A very common setup with only https_proxy therefore breaks start() through Connection.aopen, even with the HTTPApi fix. websockets 15.0.1 is what a fresh `pip install zendriver` picks; uv.lock pins 14.1, so CI does not see it. A full fix also needs proxy=None there.
3. Test-isolation gotcha for whoever lands the test: urlopen builds its global opener once, on its first call in the process, and keeps the environment's proxies from that moment. A regression test in the real suite would silently pass on unfixed code if an earlier test had already called urlopen. My test sets monkeypatch.setattr(urllib.request, '_opener', None) to prevent that. The fix itself does not depend on this.
4. Separate bug, not R21: when start() fails at the websocket stage (seen with websockets 15 and a proxy), Browser.start raises without stopping the browser. The Chromium process tree and its /tmp/uc_* profile leak; I had to kill the process group I started. This probably belongs to whichever group owns start-failure cleanup.
5. Chromium also sends its own traffic (clients2.google.com time check) through the env proxy. That is the browser's own traffic and out of scope.
