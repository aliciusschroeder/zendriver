## Lens: refute (verdict confirmed, realism low, severity crash)

### Summary
All four generator issues reproduce. A13.2: a scratch copy of the generator run from its scripts/ directory downloaded both spec JSON files there, deleted zendriver/cdp (left empty), and died with FileNotFoundError from the finally-block unlink. ### Refinements

A13.3 matters only to user code that stringifies ids or timestamps and parses them back or embeds them in JS. A13.4 matters only when passing a bare JS null as a call argument, and workarounds exist. A13.1, A13.3 and A13.4 need regenerating the out-of-scope zendriver/cdp.

## Lens: fixsafety (verdict confirmed, realism medium, severity crash)

### Summary
All four generator members reproduce. A13.2: main() downloads the spec with a relative filename (dl_file(p.name)), so it lands in the cwd. It then rmtree's REPO_ROOT/zendriver/cdp, parse() fails with FileNotFoundError, and the finally block's unlink() raises a second FileNotFoundError. The result: an empty cdp dir and stray JSON files in the cwd. A13.1 (array aliases with $ref items not converted; typed TargetFilter fails json.dumps), A13.3 (the __repr__ override changes str() and f-strings of int/float aliases) and A13.4 (CallArgument(value=None) is sent as undefined) all reproduce against real Chromium. These three need zendriver/cdp regenerated, so they are report-only.

### Refinements
The minimal A13.2 fix is dl_file(p.name, p) plus unlink(missing_ok=True). Optionally, move the rmtree of zendriver/cdp after the parse loop (parse() does not use output_path), so a bad spec never wipes the package. A13.1's generator fix breaks the only spelling that works today: TargetFilter([{'type': 'page'}]).to_json() would raise AttributeError, because a dict has no to_json. A tolerant `i.to_json() if hasattr(i, 'to_json') else i` would avoid that.
