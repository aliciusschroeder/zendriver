## Lens: reproduce (verdict confirmed, realism high, severity wrong-result)

### Summary
Confirmed. Browser.__aexit__ (browser.py:837-841) and Connection.__aexit__ (connection.py:593-599, which Tab inherits) both do `if exc_type and exc_val: raise exc_type(exc_val)` instead of returning None. I reproduced it three ways: against a fake CDP peer, against an unstarted Browser instance, and against real headless Chromium (Python 3.13.16, websockets 14.1). Any exception whose constructor needs more than one argument turns into TypeError: JSONDecodeError, UnicodeDecodeError, websockets ConnectionClosedError, and ExceptionGroup from a failing TaskGroup, so `except*` no longer matches. ProtocolException comes back as a new object with code=None and '[code: -32000]' folded into its message. KeyError('k') becomes KeyError(KeyError('k')). sys.exit(3) inside the block makes the process exit with status 1 and print '3'. A control context manager whose __aexit__ returns None passes every original exception object through unchanged. Browser.__aexit__ also never stops the browser: browser.stopped stays False and the Chrome pid is still alive after the block.

### Refinements
Saying the traceback is 'lost' overstates it. Because the new exception is raised inside __aexit__, the original is kept as __context__, and default printing shows it under 'During handling of the above exception, another exception occurred'. What actually changes is the type and identity of the exception the caller catches, plus its attributes, and its __traceback__ now points at __aexit__. This is not specific to a Python version (ExceptionGroup/TaskGroup cases need 3.11+; the JSONDecodeError and ProtocolException cases hit on every supported version). Connection.__aexit__ does call aclose() before re-raising. Browser.__aexit__ never calls stop(), so a separate question is whether it should. The suggested fix (just return None and let Python re-raise the original) is confirmed by my control context manager, which passes every original exception object through unchanged.

## Lens: refute (verdict confirmed, realism medium, severity wrong-result)

### Summary
I tried to refute this and could not. Browser.__aexit__ (browser.py:837-841) and Connection.__aexit__ (connection.py:593-599, inherited by Tab) both run `raise exc_type(exc_val)` when the body raises. On Python 3.13 this turns JSONDecodeError, UnicodeDecodeError, websockets ConnectionClosedError and a TaskGroup ExceptionGroup into TypeError. Exceptions that keep their type come back as new objects with their attributes lost: ProtocolException.code, OSError.errno/filename, and KeyError args nest as (KeyError('k'),). sys.exit(3) exits with status 1. With real headless Chrome, killing the browser in the middle of a command inside `async with browser:` gives TypeError instead of ConnectionClosedError. One sub-claim is refuted: the original traceback is not lost. The new exception's __context__ is the original object, and the default traceback printer shows it under 'During handling of the above exception'. Exceptions that build from one argument and carry no extra state (ValueError, RuntimeError, TimeoutError, CancelledError) keep their type and message, and asyncio.timeout around the block still works. No test checks the current behaviour, and git history shows no intent: the line has been there since the root import 5c1a005, and dd9a4f82 only added type hints. The repo's own test wrapper, CreateBrowser.__aexit__, does the right thing (stop, then return None).

### Refinements
The impact is narrower than 'everything breaks'. (1) Exceptions that build from one argument and carry no extra state (ValueError, RuntimeError, TimeoutError, CancelledError, and most exceptions zendriver raises itself) keep their type and message; asyncio.timeout and cancellation still work through the block. (2) The original traceback is kept: it is chained via __context__ and printed. An uncaught error in a script therefore shows the real cause plus a confusing extra TypeError. The real harm is to callers who catch a specific type around the block, use except*, read attributes (ProtocolException.code, OSError.errno) or depend on the sys.exit status. (3) It is only reachable when the user writes `async with browser:` or `async with tab:`. The first appears in examples/wait_for_page.py and examples/expect_download.py. The second is marked ':meta private:' and not documented, and the test suite never uses Browser.__aexit__. (4) The 'browser never stopped' part of A3.8 is a different root cause (__aexit__ has no stop) and should be tracked with the atexit-cleanup finding. (5) The bug does not depend on the Python version (3.13 tested); ExceptionGroup and TaskGroup only exist on 3.11+.

## Lens: fixsafety (verdict confirmed, realism high, severity wrong-result)

### Summary
Both Browser.__aexit__ (zendriver/core/browser.py, Browser.__aexit__ ~l.837-841) and Connection.__aexit__ (zendriver/core/connection.py, Connection.__aexit__ ~l.593-599, which Tab inherits: zd.Tab.__aexit__ is Connection.__aexit__ is True) run `if exc_type and exc_val: raise exc_type(exc_val)`. That rebuilds whatever the block raised. Exceptions whose constructors need several arguments (JSONDecodeError, UnicodeDecodeError, websockets ConnectionClosedError, ExceptionGroup) come out as TypeError. ProtocolException comes back as a new instance with .code=None. KeyError('k') becomes KeyError(KeyError('k')). sys.exit(3) inside the block exits the process with status 1. The caught exception's traceback points into __aexit__, and the original survives only as __context__. The minimal fix is to stop rebuilding: return None and let Python re-raise the original. I prototyped it. My regression test fails 14 of 16 cases on the repo code and passes 16 of 16 on the prototype. mypy reports no new errors, and the repo's test_connection.py and test_browser.py pass on the prototype (19 passed).

### Refinements
1) The root cause is a single pattern in two methods: Browser.__aexit__ and Connection.__aexit__. Tab inherits Connection.__aexit__, so one fix covers `async with tab`. Exceptions whose type survives (KeyboardInterrupt, CancelledError, single-argument errors) still lose their attributes and traceback; with CancelledError, asyncio.timeout still works on both versions (control test passes). 2) A3.8's 'browser is never stopped' is a separate design/API issue (should `async with browser` call stop()?). It is not part of this root cause, and the minimal fix should not change it. 3) Side observation, not in this group: when writing the fake peer I found that a reply whose 'result' cannot be parsed (e.g. Target.getTargets answered with {}) leaves conn.send() hanging forever. Transaction.__call__ raises KeyError from the cdp parser instead of calling set_exception, so the future never completes. Worth checking whether another group already owns it. 4) Regression test portability: the ExceptionGroup/TaskGroup and asyncio.timeout cases need Python 3.11+. The project supports 3.10, so guard those cases with a version skip when upstreaming.
