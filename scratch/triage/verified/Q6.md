## Lens: reproduce (verdict confirmed, realism high, severity wrong-result)

### Summary
Confirmed on Python 3.12 and 3.13, not on 3.11. In BaseRequestExpectation._request_handler (zendriver/core/expect.py, around lines 37-45) the code runs `self._remove_request_handler(); self.request_id = event.request_id; self.request_future.set_result(event)` with no done() guard. On 3.12+, Listener.listener_loop (connection.py, around lines 922-1016) drains buffered messages without yielding: wait_for no longer creates a task, and both asyncio.Queue.get on the flat-session inbox and websockets 14.1 recv return at once. It calls asyncio.create_task(callback(ev)) for every matching RequestWillBeSent before the first task runs and removes the handler. The first task resolves request_future with R1. Each later task overwrites request_id with Rn, then raises InvalidStateError, which nobody retrieves. From then on _response_handler and _loading_finished_handler match Rn. Result: .request/.value (RequestExpectation) describe R1, while .response, ResponseExpectation.value, response_body and loading_finished describe Rn. BaseFetchInterception._response_handler and DownloadExpectation._handler hit the same lost InvalidStateError on a burst; they keep the first event, so their result is still right.

### Refinements
Python-version dependent: reproduces only on Python >= 3.12 (3.12.3 and 3.13.16 tested). On 3.11, wait_for wraps each receive in a new task, so the loop yields between messages and the first handler task runs and unregisters before the next event is dispatched (0/20 real-browser trials, 0 fake-peer mismatches). Both receive paths trigger it on 3.12+: the flat-session asyncio.Queue inbox (real Chromium tab) and the owned-websocket recv (fake peer Connection). The wrong request is the last matching request in the same buffered burst, not always the page's last request. Root cause in expect.py: _request_handler mutates request_id before set_result and never checks request_future.done(). The fix should check done() before any mutation; a set_result guard alone is not enough. For BaseFetchInterception._response_handler (intercept.py ~35-42) and DownloadExpectation._handler (expect.py ~206-208), the only wrong effect is the lost InvalidStateError task: the first event is still the one returned. Unrelated observation outside the group: when page JS never reads a fetch() body, Chromium sent no Network.loadingFinished for it within 10 s, so response_body (which has no timeout) blocks.

## Lens: refute (verdict confirmed, realism medium, severity wrong-result)

### Summary
I could not refute this. On Python 3.12 and 3.13, when several Network.requestWillBeSent events that match the pattern are waiting in the inbox at once, Listener.listener_loop dispatches them back-to-back without yielding. It calls asyncio.create_task(_request_handler(ev)) once per event before the first task runs and calls _remove_request_handler(). The first task resolves request_future with R1. Each later task then overwrites self.request_id (BaseRequestExpectation._request_handler, expect.py:44) and fails on set_result with InvalidStateError, which nobody retrieves. From then on _response_handler and _loading_finished_handler match the last request (Rn). So .request/.value describe R1 while .response, ResponseExpectation.value and .response_body describe Rn. Reproduced on real headless Chromium and on a fake peer, on 3.12 and 3.13. No mismatch on 3.11.

### Refinements
1. Only on Python >= 3.12. Verified: 3.11 never reproduced (real or fake peer). On 3.10 and 3.11, wait_for wraps the receive in a new task and yields once per message, so the first handler task runs and removes itself before the next event is dispatched.

2. It needs at least 2 pattern-matching RequestWillBeSent events that are queued in the session inbox at the same time (same read burst). Spacing the frames 20 ms apart removes it. Exact-URL patterns never trigger it. Broad regexes plus parallel subresources or fetches trigger it almost every time (7/8 to 100%).

3. ResponseExpectation.value alone still returns a genuine matching response, just not the first. The harm is visible when code pairs .request/.value with .response/.response_body, or relies on 'first match'.

4. Extra consequence: if the last match in the burst never gets a response (failed, cancelled or blocked), exp.response and response_body hang forever, although the first match completed. Verified with the fake peer.

5. Every burst also leaves 'Task exception was never retrieved' InvalidStateError log noise.

6. The side claims about BaseFetchInterception and DownloadExpectation InvalidStateError were not reproduced. My real-Chromium intercept probe on 8 images logged 0 lost errors, so Fetch.requestPaused events apparently do not arrive in the same burst there. A done() guard would still be harmless there.

7. Not this group, but noticed while testing: Chrome sent no Network.loadingFinished for a fetch whose body JS never read (within 2 s), so response_body waits forever for such fetches regardless of this race.

## Lens: fixsafety (verdict confirmed, realism high, severity wrong-result)

### Summary
Confirmed on Python 3.12 and later. When several Network.requestWillBeSent events match in one burst, `expect_request`/`expect_response` pair the first matching request with the last match's response, loadingFinished and body. Each extra handler task also ends in a lost InvalidStateError. Cause: on 3.12+, Listener.listener_loop (connection.py, the create_task call at ~line 1000) dispatches a handler task for every buffered event before any of them runs. The first task removes the handler, but the tasks already created still run, and BaseRequestExpectation._request_handler (expect.py ~line 44) overwrites self.request_id each time. On Python 3.11 the listener path does not reproduce, because wait_for wraps _receive_message in a task, so the loop yields after each message. The handlers are still unsafe when they are dispatched twice, on any version. A minimal local fix in expect.py is safe. Of the two guard forms, use `request_id is not None`; the triage's `request_future.done()` early return adds a hang.

### Refinements
1. Version scope: through Listener.listener_loop the bug only shows on Python >= 3.12. There, asyncio.wait_for no longer creates a task, and both websockets' recv() and the session asyncio.Queue.get() return buffered data without suspending. Severity is still wrong-result, and on 3.12+ it is easy to hit: any pattern that matches several resources of one page.
2. Fix-form refinement: do not use the triage's `if self.request_future.done(): return`. A timed-out `asyncio.wait_for(exp.value, t)` cancels request_future itself (verified on 3.11 and 3.13). After that, the triage guard means no later match ever sets request_id, so `exp.response` and `response_body` hang. The repo code still resolves them, though it logs an InvalidStateError. I built that variant at .../Q6-fixsafety/alt; it fails test_response_still_resolves_after_timed_out_wait_for_request with a timeout. Instead, guard on `self.request_id is not None` and make every set_result conditional on `not future.done()`.
3. Sibling: BaseFetchInterception._response_handler in intercept.py has the same unguarded set_result. Adding `if not self.response_future.done()` there is safe. Extra paused requests stay paused until teardown's fetch.disable either way, so that guard changes nothing users would see.
4. A dispatch-time check in Listener (skip callbacks that are no longer registered) would change semantics for all user handlers. It is not needed here.

### Fix assessment
- kind: minimal-local
- prototype: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/Q6-fixsafety/pkg
- regression test: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/Q6-fixsafety/test_expect_burst.py
- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: zendriver/core/expect.py only (full diff at .../Q6-fixsafety/prototype.diff).
- BaseRequestExpectation._request_handler: returns early when `self.request_id is not None` (comment: matching events dispatched before the handler removed itself must not replace the tracked request), and wraps set_result in `if not self.request_future.done()`.
- _response_handler and _loading_finished_handler: still remove themselves on a request_id match; only set_result is guarded by `if not <future>.done()`.
- DownloadExpectation._handler: removes itself, then `if not self.future.done(): self.future.set_result(event)`.
The change is ruff format/check clean.
- risks: - Locking and cancellation: no locks are involved and the handlers contain no awaits, so there are no re-entrancy, lock-ordering or cancellation-path concerns.
- Behaviour change: after the first match, later matching requests in the same burst are ignored (intended), and no InvalidStateError tasks are logged any more.
- Cancelled future: if request_future was cancelled by a timed-out wait on exp.value, the first later match still sets request_id, so exp.response and response_body keep working as before.
- Not fixed (pre-existing): handler tasks created before `reset()` that run after it can still match into the new futures. Fixing that needs a generation token.
- Coverage gaps: intercept.py's BaseFetchInterception._response_handler is unpatched; it needs the same one-line set_result guard. The end-to-end test only fails on Python >= 3.12 (it passes on 3.11 repo code). The two direct double-dispatch tests and the cancel-edge test fail on 3.11 repo code too, so the suite still catches regressions on every supported version.
