## Lens: fixsafety (verdict confirmed, realism medium, severity hang)

### Summary
Chrome applies the download behaviour to a whole browser context. Without browserContextId it uses the default context, even when the command is sent on a context tab's session, and a call without eventsEnabled turns off DownloadWillBegin for that session. zendriver sends every call without browser_context_id and keeps the state per Tab (Connection._download_behavior). Confirmed on real Chromium: (1) download_file inside expect_download turns the events off, so ex.value hangs, and the file is downloaded despite the deny. (2) set_download_path and expect_download do nothing for create_context tabs, and the expectation hangs. (3) One tab's download_file or expect_download exit overwrites the path another tab set. The right fix is a design change: per-context state, the context id sent for non-default contexts, events kept on, and a per-context count of active expectations.

### Refinements
Fix-safety finding: the obvious per-context fix is not safe on its own. Version 1 of the prototype captured the previous behaviour at __aenter__, marked the context 'deny' and restored the captured value at __aexit__. With two expectations that overlap without nesting (A enters, B enters, A exits, B exits), it left the context permanently denied: B restores 'deny', and later downloads vanish silently. The repo itself sends those to ~/Downloads. The added test test_overlapping_expectations_do_not_leave_downloads_denied caught it. The fix needs a per-context count of active expectations, restoring the current per-context state only when the last one exits. Chrome also rejects the default context's id, so browser_context_id may only be sent for ids listed by Target.getBrowserContexts.
