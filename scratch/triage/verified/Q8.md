## Lens: reproduce (verdict confirmed, realism medium, severity crash)

### Summary
I confirmed this with my own runs, on pure Python, an in-memory Element and real headless Chromium 141. ContraDict.__getattribute__ (zendriver/core/_contradict.py, line 53) runs `if attribute in self: return self[attribute]` before any method lookup. So a stored key named clear/items/get/keys/values/update/pop/copy hides the bound dict method, and calling it raises TypeError: 'str' object is not callable. The class docstring says the opposite. Element._attrs is a ContraDict filled from DOM attributes in _make_attrs. As a result, `<br clear=all>` breaks await elem, update, query_selector, save_to_dom and remove_from_dom; an `items=` attribute breaks repr/str of the element and of any ancestor, plus Tab.get_all_urls(); a `get=` attribute breaks elem.get(), elem[...] and elem.<attr>. get_js_attributes() on any <br> also returns a ContraDict whose .clear() raises.

### Refinements
- remove_from_dom also breaks before doing anything, because it calls update() first. The element stays in the DOM.
- repr(br) for <br clear=all> works, since only `items` breaks __repr__. Whether a given name breaks a given path depends on which dict method that path calls: clear -> update/await/query_selector*/save_to_dom/remove_from_dom; items -> __repr__/__str__ (for any ancestor too) and get_all_urls(absolute=True); get -> Element.get/__getitem__/__getattr__ and cloudflare's attrs.get. cloudflare.py was not exercised.
- get_js_attributes() on any HTMLBRElement always has a 'clear' key, because the `clear` IDL property is enumerated even when the attribute is absent. So .clear() on that ContraDict always fails for <br>, and .get() fails for any element whose JS properties include 'get'.
- The `_check_key` warning guard is never reached for stored keys, because the `in self` check comes first.
- The behaviour predates repo history: git log on _contradict.py shows only dd9a4f8 (mypy types) and 5c1a005.
- Fix direction is consistent with the triage hypothesis: resolve class attributes and methods (e.g. type(self) / dict methods) before falling back to keys, or read the dict directly inside Element (dict.items(self._attrs), dict.clear, dict.get).

## Lens: refute (verdict confirmed, realism low, severity crash)

### Summary
I could not refute this. ContraDict.__getattribute__ (zendriver/core/_contradict.py, lines 52-58) returns self[attribute] whenever the name is a stored key, and it does this before the _check_key guard that would hand the name to dict. So a key named clear, items, get, values, keys, update, pop, copy, setdefault or popitem replaces the bound dict method with the stored string. This is the opposite of what the class docstring promises ("won't overwrite the methods"). Element._attrs is a ContraDict filled from the DOM attributes Chrome reports. Zendriver's own calls to self.attrs.clear() (Element.update), self.attrs.items() (Element.__repr__, Tab.get_all_urls) and self.attrs.get() (Element.get, __getitem__, __getattr__) then raise TypeError: 'str' object is not callable. I reproduced every public path in real headless Chromium, including the Google homepage HTML as served to a Chrome user agent, which contains <br clear="all" id="lgpd">. The bug is real and reachable, but a normal user needs an uncommon combination to hit it.

### Refinements
Which key breaks what: 'clear' only breaks methods that call update() on THAT element: update(), await elem, Element.query_selector(_all), set_text, save_to_dom, remove_from_dom, and the stale-node retry in Tab.query_selector(_all)(sel, _node=elem). It does not break select/find/click/repr. In practice 'clear' appears almost only on <br>, and users rarely call these methods on a <br>; a generic loop over children or select_all('*') hits it. 'items' breaks repr/str of the element and of every ancestor (because __repr__ recurses into children), save_to_dom (str(self)), and get_all_urls(absolute=True) when the attribute is on an a/link/img/script/meta element. 'get' breaks Element.get, __getitem__ and the deprecated __getattr__ for any unknown attribute name. values/keys/update/pop/copy only break user code that calls those methods on elem.attrs; zendriver itself never calls them. 'values' is common on SVG feColorMatrix/animate (verified that Chrome reports it). Matching is by exact key, so hyphenated names like data-items or data-copy are not affected. get_js_attributes() of any <br> always has a 'clear' key (HTMLBRElement.clear property, verified), but only .clear() on the result breaks. Workarounds for users: attrs['name'] and dict.items(attrs). The failure is a raised TypeError, not a hang, and it is not Python-version dependent.

## Lens: fixsafety (verdict confirmed, realism high, severity crash)

### Summary
ContraDict.__getattribute__ (zendriver/core/_contradict.py, first line of the method, `if attribute in self: return self[attribute]`) returns the stored value before it looks at the class. So a key named clear/items/get/keys/values/update/pop/copy hides the dict method, which contradicts the class docstring and the class's own warning message. Element._attrs is a ContraDict filled from DOM attributes, and Element.get_js_attributes() also returns one. ### Refinements

The finder's pure-probe example `cd.copy().clear()` is not a valid repro: copy() returns a plain dict. Use cd.clear() on the ContraDict itself. ### Fix assessment
- kind: minimal-local

- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: zendriver/core/_contradict.py, ContraDict.__getattribute__: `if attribute in self:` becomes `if attribute in self and not hasattr(type(self), attribute):`, with a 2-line comment. Keys that collide with a real class attribute then fall through to the existing code: _check_key, then getattr(super(), attribute) for dict-method names, or object.__getattribute__ for data descriptors such as __class__. Keys that are not class attributes (id, class, data-id, Items, title) are still returned as attributes, so that behaviour is unchanged.
- risks: No locks or async code are involved, so there are no re-entrancy, lock-ordering or cancel-path concerns. hasattr(type(self), name) goes through type.__getattribute__ on the class, so it cannot recurse into the instance hook, and it runs only when the name is already a key. Behaviour change callers could notice: cd.items, elem.attrs.clear, get_js_attributes().clear and similar now return the dict method instead of the stored value. The docstring and the _warning_names_message both document that, so code relying on the old result was relying on the bug. The values stay reachable via cd['items'], elem.get('items'), elem['items'] and elem.items (through Element.__getattr__). Remaining unchanged edge: dunder keys that are non-data descriptors (e.g. '__len__', '__init__', '__doc__') still shadow through object.__getattribute__, because the instance __dict__ is the dict itself. This is unrealistic for HTML attributes and was already the behaviour. mypy: 332 errors on both the prototype and an untouched copy, the diff of the two logs is identical, all errors are in zendriver/cdp/, and there are none in _contradict.py or element.py. The repo's tab/browser/cloudflare/frames/keyinputs suites pass 69/69 on both copies with headless Chromium. That covers Browser.info (a ContraDict read via .webSocketDebuggerUrl), which every browser start uses. Avoid the naive reorder variant, because it regresses getattr access for 'class', hyphenated keys and case variants of the warning names.
