## Lens: reproduce (verdict confirmed, realism low, severity wrong-result)

### Summary
util.cdp_get_module(Domain.lower()) fails for 23 multi-word CDP domains (WebAuthn, FedCm, DOMStorage, IndexedDB, ServiceWorker, ...). Connection._update_manual_domain therefore swallows ModuleNotFoundError, so a manual X.enable(params) is not tracked. Once a handler for that domain exists, the next send re-sends X.enable() with {} params. Reproduced with a fake CDP peer and on real Chromium. Only WebAuthn (enableUI) and FedCm (disableRejectionDelay) have optional enable params that this can reset. That they actually get reset is inferred from the spec defaults and not observable headless.

### Refinements
The practical wrong-result is limited to WebAuthn.enable(enable_ui=...) and FedCm.enable(disable_rejection_delay=...). For the other unmapped domains, enable takes no params, so the re-send is only redundant. For PerformanceTimeline and BluetoothEmulation the auto-enable call raises TypeError on every send (debug-logged). The opposite also holds: an auto-enabled multi-word domain stays in enabled_domains after a manual X.disable, so it is not re-enabled. The collision risk of a bare import_module of a lowercased name with an unrelated top-level module was not observed for any real CDP domain.

## Lens: refute (verdict partially-confirmed, realism low, severity wrong-result)

### Summary
The mechanism is real. _update_manual_domain calls util.cdp_get_module(domain_name.lower()), which cannot resolve 15 multi-word domains. A manual WebAuthn.enable(enable_ui=True) / FedCm.enable(disable_rejection_delay=True) is therefore not tracked, and after a handler is added the next send carries a param-less WebAuthn.enable / FedCm.enable. The user-visible harm is narrow and not demonstrated. Only WebAuthn and FedCm have optional enable params. The re-send happens only when the manual enable comes BEFORE add_handler. That enableUI / disableRejectionDelay actually get reset is assumed from the CDP spec, not observed.

### Refinements
It triggers only for a multi-word domain whose enable takes optional params (WebAuthn or FedCm in practice), only with a non-default param value (enable_ui=True or disable_rejection_delay=True; automation normally uses the default enable_ui=False), and only when the manual enable comes before add_handler. In that case it happens once, on the first send after add_handler; afterwards the domain sits in enabled_domains. Headless Chrome shows no WebAuthn UI anyway.

Order 'add_handler, then manual enable': the auto WebAuthn.enable {} goes out first and the user's enable(enable_ui=True) after it, so the user's params win and later sends do not re-enable. Only WebAuthn (enable_ui) and FedCm (disable_rejection_delay) have optional params. Eleven others (DOMStorage, HeapProfiler, ServiceWorker, WebAudio, LayerTree, ...) have param-less enable, so the redundant enable is harmless. The 'unrelated top-level module' point (e.g. py_webauthn installs `webauthn`) was only reasoned about and is harmless: the junk module goes into manually_enabled_domains.

## Lens: fixsafety (verdict confirmed, realism low, severity wrong-result)

### Summary
_update_manual_domain calls util.cdp_get_module(domain_name.lower()). For any multi-word CDP domain, getattr(cdp, 'webauthn') fails and importlib.import_module('webauthn') raises ModuleNotFoundError, which is swallowed. So a manual X.enable(params) is never tracked, and once a handler is added the next send emits a param-less X.enable. 23 of the 56 CDP domains are affected, not only the 15 listed.

### Refinements
The affected list is larger than claimed (23 domains, including CacheStorage, DOMDebugger, EventBreakpoints, FileSystem, SystemInfo, BackgroundService, CrashReportContext and DeviceOrientation). The manual-disable bookkeeping has the mirror-image bug, found by code reading: a manual WebAuthn.disable of an auto-enabled domain is not removed from enabled_domains, so zendriver thinks the domain is on and never re-enables it. _register_handlers itself resolves these domains correctly, because it passes the full dotted module path, which works through import_module.

### Member verdicts

Fake peer: after web_authn.enable(enable_ui=True), manually_enabled_domains was [], and after add_handler(CredentialAdded) the next send emitted [('WebAuthn.enable', {}), ('Page.reload', {})]. FedCm behaved the same. Real Chromium also showed the extra '{"method": "WebAuthn.enable", "params": {}...' frame, but the virtual authenticator kept working (get_credentials OK). The claimed reset of enableUI/disableRejectionDelay is inferred, not observed. The bug only triggers when the manual enable comes before add_handler; with the handler first, the auto-enable goes out before the user's enable.
