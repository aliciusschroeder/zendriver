## Lens: reproduce (verdict confirmed, realism medium, severity crash)

### Summary
All five config-argument claims reproduce on Python 3.13.16 against the repo copy, with my own probes. The worst one is K5. Config.add_argument rejects any argument whose lowercased text contains headless, lang, data-dir, data_dir, no-sandbox or no_sandbox. Browser.start passes --load-extension through add_argument, so Browser.create raises ValueError, and the browser never starts, whenever an extension path contains one of those substrings (for example .../headless-scraper/ext or /opt/LanguageTool). K2: argv carries duplicate copies of flags that Config adds itself (confirmed in /proc/<pid>/cmdline of a real Chromium). When the values differ, Config's copy comes last and silently overrides the user's browser_args value, because Chrome uses the last value of a repeated switch. K4: Config stores the caller's non-empty list by reference, so add_argument mutates it and leaks into other Configs built from the same list. K1: the browser_args property returns sorted(defaults + user args). It does not merge --disable-features and does not dedupe, so it differs from Config(). K3: each start() appends another --load-extension to browser.config. On an ordinary restart the duplicates never reach a launched Chromium, because start() keeps the host/port it set and takes the connect_existing path; they reach the real argv only if host/port are cleared by hand.

### Refinements
K3: the duplicates never reach a launched Chromium on an ordinary restart. After stop(), start() reuses the host/port it assigned and takes the connect_existing path, which fails with ConnectionRefusedError (that is a separate restart issue). The start() branch for a process that has exited (create(config=self.config)) also keeps host/port, so it takes the same path. K2: identical duplicates are harmless because Chrome uses the last value. The defect worth fixing is precedence: Config-appended flags (user_agent, lang, the default disable_webrtc=True policy, headless) override conflicting values the user put in browser_args. Also, browser_args=['--headless=new'] with headless=False leaves config.headless False, so the headless UA patch in start() is skipped. K5 is the member with real user impact: Browser.start aborts with ValueError for any extension directory whose path contains a blocked substring, and the substring list also blocks unrelated flags such as --accept-lang and *Language* feature names. A fix should match flag names exactly (split on '=' and compare the switch name) and should not route the internal --load-extension through the user-facing validation. K1: the only internal consumer is __repr__. K4: aliasing only shows when Config is used directly, since Browser deepcopies.

## Lens: refute (verdict partially-confirmed, realism medium, severity wrong-result)

### Summary
Four of the five config-argument claims are real in the code, but under a refute/realism lens most of them are cosmetic. K5 is the one that matters. add_argument rejects any argument whose lowercased text contains 'lang', 'headless', 'data-dir', 'data_dir', 'no-sandbox' or 'no_sandbox'. Browser.start passes '--load-extension=<paths>' through add_argument, so an extension whose path contains one of those substrings makes Browser.create raise ValueError before Chrome is launched. Examples: a 'languagetool' folder, a 'headless-scraper' project, or a Windows user called Lang/Lange, whose %TEMP% also holds unpacked .crx files. K1 (the browser_args property differs from __call__) and K2 (user args that repeat Config-owned flags are not removed) are confirmed, but Chrome tolerates the duplicates (verified): identical boolean switches are harmless and for value switches the last one, Config's, wins. K4 (Config keeps a reference to the caller's list) is confirmed only when the caller uses Config directly and calls add_argument. Browser.__init__ deep-copies the config, so zendriver.start/Browser.create never mutate the caller's list. K3 is refuted: a duplicated --load-extension never reaches Chrome, and would be harmless if it did.

### Refinements
- K5 is the actionable member. The realistic trigger is not a user calling add_argument with odd flags but Browser.start's own --load-extension call. Case-insensitive matching means Windows profiles like C:\Users\Lang or Lange also block .crx extensions, which are unpacked under %TEMP%. A fix should match flag names exactly (e.g. the part before '='), not substrings, and should not route --load-extension through the user-facing validation.
- K1 and K2 are cosmetic: Chrome tolerates the duplicates and Config's value comes last and wins. Deduping is a cleanup, not a behaviour fix.
- K4 needs direct Config use, add_argument and a list reused across Configs or mutated later.
- K3 should be dropped as stated. The real defect it brushes against belongs to another group: a Browser cannot be restarted after stop() or after its process dies. config.host/port (and self.info) persist from the first run, so start() takes the connect_existing path and fails with ConnectionRefusedError or 'Failed to connect' instead of relaunching.
- Side observation, out of group: Browser.__init__ eagerly formats logger.debug('... %s' % vars(self)). That calls Config.__repr__, which reads the user_data_dir property and creates a temp profile dir. When start() then fails before launch (e.g. the K5 ValueError), the dir is never cleaned up: two empty /tmp/uc_* dirs leaked in my K5 run.

## Lens: fixsafety (verdict confirmed, realism medium, severity crash)

### Summary
All five seeded leads reproduce on the repo code. Config.__call__ (config.py) never removes duplicate args, apart from user args that repeat the defaults. Config.browser_args returns sorted(defaults + user args) with nothing merged or removed. Config.__init__ keeps the caller's list (self._browser_args = browser_args). Config.add_argument rejects any arg that contains a blocked substring anywhere. Browser.start (browser.py) builds --load-extension through config.add_argument on every start. K5 is worse than the seed says: because Browser.start sends the extension path through add_argument, any extension whose absolute path contains 'lang', 'headless', 'data-dir' or 'no-sandbox' (case-insensitive, for example /home/lange/..., C:\Users\Langley\..., or a folder named language-helper) makes zd.start() raise ValueError before Chrome is launched. I showed this with real headless Chromium. K1 to K4 are cosmetic or minor wrong-result issues: Chrome uses the last value of a repeated switch, so identical repeats change nothing at runtime.

### Refinements
K5 is the real defect: Browser.start passes the extension path through add_argument, so a 'lang' substring in a home dir or username (Lange, Langley, Slang...), or 'headless' in a folder name, breaks zd.start(). The cleanest fix for both K3 and the K5 start crash is to build --load-extension inside Config.__call__ from _extensions and stop mutating config in Browser.start. Remove duplicates keeping the LAST copy. Keeping the first copy would change results, because Chrome uses the last value of a switch: [--window-size=800, --window-size=1000, --window-size=800] would become 1000 instead of 800. Related issues outside this group's members: (a) --headless, --no-sandbox, --user-data-dir and --lang passed through browser_args at construction are never checked, so '--headless=new' with headless=False runs headless while config.headless stays False and Browser.start skips its headless-only setup; (b) the quickstart docs assign config.browser_args, which has no setter; (c) Config.__repr__ calls the user_data_dir getter and can create a temp profile dir.
