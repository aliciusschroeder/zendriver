## Lens: reproduce (verdict confirmed, realism medium, severity wrong-result)

### Summary
Confirmed. I reproduced it with my own probes on Python 3.13.16 and the real headless Chromium. Calling print(config), str(config), repr(config) or config(), or reading config.user_data_dir, on a template Config runs mkdtemp (Config.user_data_dir getter, config.py ~L140-151, called from Config.__repr__ ~L247 and Config.__call__ ~L200). The path is stored on the template and _custom_data_dir stays False, so every deepcopy made in Browser.__init__ (browser.py ~L259) carries the same 'temporary' profile. With a printed template or a called config(), b1 starts. b2's Chromium aborts with 'Failed to create .../SingletonLock: File exists' and zd.start raises 'Failed to connect to browser'. b2's failure path then removes b1's live profile: start -> stop -> _stop:919 -> _cleanup_temporary_profile:927 rmtree. b1 keeps running and its profile directory is gone. Without the repr (control run), the two browsers get distinct dirs and both start. Separately, Browser.__init__ formats logger.debug('Session object initialized: %s' % vars(self)) (~L274) eagerly, even at WARNING level, and that materializes the instance copy's temp dir. When start() then fails before spawning Chrome (bad executable), or the connect-existing path fails, the dir is never removed. _stop returns early at `if not self.connection and not self._process: return` (~L875), before _cleanup_temporary_profile, and create() never registers the atexit cleanup. Each failed attempt leaks one empty uc_* dir.

### Refinements
Two separate mechanisms are involved. (1) Template sharing: the user's own repr(), str() or config() call, or the user_data_dir getter, on the template materializes the lazy dir. Browser.__init__'s debug log does NOT touch the template, because it formats vars(self) after the deepcopy, so only user-side inspection triggers the sharing bug. (2) Leak: the eager '%' formatting in Browser.__init__ (~L274) materializes the per-instance copy's dir, and _stop's early return (~L875) skips _cleanup_temporary_profile when start() failed before a process or connection existed. On the connect-existing path, a temp profile is created even though it is never used. In my runs b2's Chromium aborted on SingletonLock 'File exists' and did not hand off to b1's process. The scratch TMPDIR is long, which may affect the singleton socket path. Either way b2 fails and its stop() deletes the shared dir. The leaked dirs are empty mkdtemp dirs, one per failed attempt.

## Lens: refute (verdict confirmed, realism medium, severity crash)

### Summary
I tried to refute this group and could not. Its central claim holds. Config.__repr__ (repr, str, print, f-strings, logging that actually emits), Config.__call__ and a read of the Config.user_data_dir property all run mkdtemp on the template Config and leave _custom_data_dir False. After that, every deepcopy in Browser.__init__ carries the same temp path. I verified the next steps with real headless Chromium 141. The second zd.start(config) fails after 2.5 s with 'Failed to connect to browser', and its stop() runs shutil.rmtree on the profile directory the first browser is still using. The failed-start leaks are also real. A bad browser_executable_path leaks one empty uc_* directory per attempt, and so does a connect-existing start with nothing listening. Two parts of the claim are wrong or overstated. First, Browser.__init__'s eager '%s' % vars(self) debug line materialises only the browser's own deepcopy, never the template, so it causes the leaks but not the shared profile. Second, Chrome does not hand the launch over to the first browser's process: it aborts. The deleted profile also has almost no visible effect on the first browser.

### Refinements
1) The Browser.__init__ debug line never touches the template. It formats vars(self) after the deepcopy, so it only feeds the failed-start leaks (A3.7/B16.6). The shared profile needs user code to touch the template: repr, str, print, an f-string, an eager '%' format, an emitted logging call, config() or reading .user_data_dir. A lazy logger.debug('%s', cfg) at a disabled level is safe. 2) Chrome does not forward the launch to the running process. Headless Chromium 141 aborts the second launch on the live SingletonLock (verified), so the visible symptom is always that the second zd.start raises after browser_connection_max_tries * timeout (2.5 s by default), with a misleading hint about root and sandbox. 3) Deleting b1's live profile is almost silent. Navigation, localStorage, cookies, new tabs and new contexts all kept working, and Chrome recreated the directory (verified). The real harm is that the second browser cannot start. 4) It only bites when two or more browsers from one template run at the same time. Sequential reuse (start, stop, start) works. 5) The leaks are empty directories, one per failed attempt. Path (a) needs an explicit nonexistent browser_executable_path. Path (b) needs host and port set with nothing listening. 6) Aside, out of scope: with a very long TMPDIR (the scratchpad path), Chromium failed to start at all in my control run. A short TMPDIR fixed it, which looks like the Unix-socket path limit for Chrome's singleton socket, not zendriver.

## Lens: fixsafety (verdict confirmed, realism medium, severity wrong-result)

### Summary
Confirmed on repo code (Python 3.13.16, real Chromium 141 plus browser-free tests). Config.__repr__ (config.py, Config.__repr__ ~l.254-255) calls getattr() on every property in the class dict. That includes user_data_dir, whose lazy getter (Config.user_data_dir ~l.140-151) runs mkdtemp, stores the path on the template and leaves _custom_data_dir False. Browser.__init__ (browser.py ~l.259) deep-copies the template, so every browser gets the same 'temporary' profile. With real Chromium the second zd.start(config) fails with 'Failed to connect to browser', and its stop() rmtree's the profile that b1 is still using. Browser.__init__'s eager `logger.debug('...%s' % vars(self))` (~l.274) runs repr on the browser's own copy, so a temp dir is created at construction even with debug logging off. start() raises FileNotFoundError at the executable check (~l.539) before anything cleans it up, so one uc_* leaks per failed call. For connect-existing, start() always calls self.config() (~l.565), which creates the dir. When the connection fails, stop() hits the early return in Browser._stop (~l.875, `if not self.connection and not self._process: return`) and skips _cleanup_temporary_profile, so that dir leaks too. The minimal local fix has two parts: (1) __repr__ reads self._user_data_dir for user_data_dir and no longer calls the getter; (2) the early-return path of _stop calls _cleanup_temporary_profile. Optionally, (3) the debug log in __init__ becomes lazy. This fixes the repr-driven sharing and both leaks. Calling config() or reading config.user_data_dir on a template still makes browsers share a profile; fixing that needs a design decision.

### Refinements
1) Which change fixes which member: the __repr__ change alone fixes A3.6/A9.3/B16.5 (print/repr/logging trigger), A3.7 and B16.6(a). The lazy debug log is then only belt-and-braces. B16.6(b) needs the _stop early-return cleanup.
2) Residual that the minimal fix does not cover: config() (which the docstring offers as a way to inspect the args) and reading config.user_data_dir on a template still materialise one shared, non-custom temp dir. On the prototype both give 'shared profile: True'. Smallest fix, prototyped in .../R14-fixsafety/pkg2: right after the deepcopy in Browser.__init__, add `if not self.config.uses_custom_data_dir: self.config._user_data_dir = None`. It passes 8/8 of my tests and the same 29 repo tests. It changes behaviour, though: a temp dir already created on the template is orphaned (an empty uc_ leak), and a user who pre-seeded the auto temp dir would silently get a fresh one. So it is a maintainer decision, not part of the minimal patch.
3) The browser.py line ~259 deepcopy in the group 'where' is only the propagation point. The root cause is the side-effecting getter being reached through __repr__.
4) Optional polish: _cleanup_temporary_profile reads the lazy getter, so on the new early-return path a never-started browser creates and then deletes a uc_ dir (net zero, verified). Guarding on self.config._user_data_dir would avoid that.

- diff summary: config.py Config.__repr__: `if k == "user_data_dir": v = self._user_data_dir` (with a short comment), then `elif isinstance(v, property): v = getattr(self, k)`, so repr never runs mkdtemp (an unset dir prints 'user_data_dir = None'). browser.py Browser.__init__: `logger.debug("Session object initialized: %s", vars(self))` (lazy; checked that it still renders the dict when DEBUG is on). browser.py Browser._stop: the early-return branch `if not self.connection and not self._process:` now runs `await self._cleanup_temporary_profile()` before `return`.

(b) stop() of a never-started or failed connect-existing browser now deletes its non-custom temp dir. That dir is normally its own; it is only someone else's in the residual config()/read-sharing case, where a never-started copy's stop() could now delete a live sibling's profile (contrived: Browser(config) + stop() without start()). The pkg2 variant removes that hazard.

Not fixed: config()/reading user_data_dir on a template still shares one profile, which needs the design-level reset in Browser.__init__ (see refinements).
