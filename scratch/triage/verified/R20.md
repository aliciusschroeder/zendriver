## Lens: reproduce (verdict confirmed, realism high, severity wrong-result)

### Summary
Confirmed in real headless Chromium 141 (Python 3.13). Element.send_keys(str) calls KeyEvents.from_text(text, KeyPressEvent.CHAR) (zendriver/core/element.py, Element.send_keys ~line 721). That maps both '\n' and '\r' to SpecialKeys.ENTER. KeyEvents._get_key_and_text (CHAR branch) then calls KeyEvents.conv_to_str (zendriver/core/keys.py ~line 167), which returns '\n'. So the payload is Input.dispatchKeyEvent(type='char', text='\n'). Chrome turns that into keypress charCode 10, which inserts nothing and does not submit the form. The result: line breaks are silently dropped from textarea and contenteditable input, and 'query\n' or 'query\r' never submits. A raw char '\r' (charCode 13) works correctly. The class's own SPECIAL_KEY_CHAR_MAP maps ENTER to '\r', and the DOWN_AND_UP path uses that map and works. CRLF works only by accident: grapheme treats '\r\n' as one grapheme, so it skips the ENTER mapping and goes out as raw text '\r\n'.

### Refinements
Two points the claim slightly understates. First, '\r' alone is also dropped: from_text sends '\r' through the same ENTER→conv_to_str path, which produces '\n'. Second, contenteditable elements also lose the line break ('a\nb' becomes 'ab'). The bug is confined to the CHAR path: send_keys(str), and from_text(..., KeyPressEvent.CHAR) when passed explicitly. send_keys(SpecialKeys.ENTER) and from_mixed_input / from_text with DOWN_AND_UP use SPECIAL_KEY_CHAR_MAP ('\r') and work. CRLF works by accident because grapheme groups '\r\n' into a single grapheme that goes out unmapped.

## Lens: refute (verdict confirmed, realism high, severity wrong-result)

### Summary
I could not refute this. Element.send_keys(str) builds its events with KeyEvents.from_text(text, KeyPressEvent.CHAR), which maps both '\n' and '\r' to SpecialKeys.ENTER. The CHAR branch of KeyEvents._get_key_and_text then calls KeyEvents.conv_to_str(ENTER), and conv_to_str returns '\n' (keys.py, around line 167). The class's own SPECIAL_KEY_CHAR_MAP and the DOWN_AND_UP path (_build_action_data) use '\r' for ENTER. Verified on real headless Chrome 141.0.7390.37: Input.dispatchKeyEvent(type='char', text='\n') fires only a keypress with charCode 10. It inserts nothing and does not submit the form, so send_keys('abc\n') and send_keys('abc\r') never submit, and a textarea or contenteditable loses every line break. '\r' alone is a regression: the old char-per-char send_keys path sends a raw '\r', which does submit (checked by emulating that path).

### Refinements
(a) A bare '\n' did not work before the KeyEvents rewrite either: the old char-per-char path also sent char '\n', as my emulation shows. So the '\n' part is long-standing; only '\r' is a new regression, and I checked that only by emulating the old path. (b) CRLF '\r\n' works by accident: it is one grapheme, so _handle_string_key_lookup misses it, and it goes out as raw char '\r\n', which Chrome treats as Enter (verified). (c) Only the str -> CHAR path is affected. send_keys(SpecialKeys.ENTER) and from_mixed_input(...) (DOWN_AND_UP) send keyDown with '\r' and work (verified). (d) Note for the fix: switching the CHAR path to char '\r' fixes implicit form submission and line breaks in textarea and contenteditable (verified with raw char '\r'). But a char event never fires keydown, and the keypress has an empty key. JS handlers listening for keydown with key==='Enter', common in SPA search boxes, would still not react. Sending Enter as a keyDown/keyUp pair even in CHAR mode would cover those handlers too: SpecialKeys.ENTER produced keydown 'Enter', keypress 13 and a submit (verified). (e) The logic is pure Python, so the Python version does not matter. Realism: 'query\n' to submit and multi-line textarea input are common automation idioms, and the docstring recommends \n. Workarounds exist (SpecialKeys.ENTER, '\r\n') but are not obvious.

## Lens: fixsafety (verdict confirmed, realism high, severity wrong-result)

### Summary
Confirmed on real headless Chromium 141. When `Element.send_keys` gets a str, it calls `KeyEvents.from_text(text, KeyPressEvent.CHAR)`. That maps a lone '\n' or '\r' grapheme to `SpecialKeys.ENTER`. `_get_key_and_text` (CHAR branch) then calls `conv_to_str(ENTER)` (zendriver/core/keys.py, `KeyEvents.conv_to_str`, around line 167), which returns '\n'. Chrome turns `Input.dispatchKeyEvent(type='char', text='\n')` into keypress charCode 10. That inserts nothing and does not trigger implicit form submission. Only '\r' (charCode 13) acts as Enter, which is the value the class's own `SPECIAL_KEY_CHAR_MAP` and the DOWN_AND_UP path already use. Changing that one line to `return "\r"` fixes it.

### Refinements
1. CRLF ('\r\n') is not affected: it is one grapheme and goes out as raw char text, so the bug only hits a lone '\n' or a lone '\r'.
2. The minimal fix covers native line insertion (textarea, contenteditable) and native implicit form submission. It does not cover JS handlers listening on keydown: CHAR mode fires only keypress. With the fix, send_keys('q\n') still logs only ["keypress:","keypress:"], with e.key == '' and no keydown/keyup. SPAs that handle Enter in onKeyDown still will not react. Fixing that is a design change, for example emitting DOWN_AND_UP for ENTER inside from_text even in CHAR mode. It is not needed for this group.
3. `KeyEvents(SpecialKeys.ENTER).to_cdp_events(KeyPressEvent.CHAR)` is public API. Its payload text changes from '\n' to '\r', which is an improvement.
