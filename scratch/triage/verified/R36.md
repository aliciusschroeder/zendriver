## Lens: refute (verdict confirmed, realism high, severity wrong-result)

### Summary
I could not refute the code defects. find_elements_by_text (tab.py:681) never deduplicates: performSearch returns both the element that matched by attribute value and its text node, and the text node is replaced by its parent, so the same element is returned twice. tag_hint is never read in the body. find_element_by_text (tab.py:776) never reads return_enclosing_element. The include_frames per-document query errors are print()ed (tab.py ~572), and the stale retry passes _node=doc, which skips content_doc collection. Realism varies a lot by member. Duplicates are high-realism: the repo's own tests/sample_data/groceries.html gives find_all('Apples') -> [SCRIPT, LI, LI]. tag_hint and return_enclosing_element are low-impact API inaccuracies. A5.6's partial results only reproduced under concurrent queries (the R37 root cause), not in sequential use or right after page load.

### Refinements
A6.4: any element whose attribute value (title, aria-label, alt, value, placeholder) contains the search text and that also has the text as content is returned twice. The same goes for an element with several matching text nodes. Main-document <input placeholder> searches also return the INPUT plus its user-agent shadow placeholder DIV, which is a related double hit. Only find_all/find_elements_by_text callers are affected; find() picks one. A5.6 is only reachable when several queries run concurrently on one tab, or in theory when an iframe document is replaced between getDocument and querySelectorAll; the select loop and browser.get's load wait hide this in sequential use. tag_hint and return_enclosing_element are low-realism doc/API mismatches (wrong-result bordering on cosmetic).

## Lens: fixsafety (verdict confirmed, realism high, severity wrong-result)

### Summary
All claims reproduce on Chromium. find_elements_by_text returns the same element several times (an attribute plus a text match, or several text nodes of one element). tag_hint is never read. return_enclosing_element is plumbed through find -> find_element_by_text but never used, and find_elements_by_text always replaces text nodes with their parent. query_selector_all(_include_frames=True) print()s and drops iframe-document errors, and its tab-level stale retry passes the fresh doc as _node, so iframe documents are never collected. select/select_all then return partial lists, even in a single sequential call right after page load (7 of 8 runs). A local fix covers all of it. It adds one optional kwarg to find_elements_by_text.

### Refinements
A5.6 overlaps R37: concurrency is the main source of the stale iframe ids. A single call right after load also hits them, apparently because the iframe document is swapped while it loads. The dedup is needed by R28 as well, to remove the main-loop/iframe-branch duplicate of A5.9. The return_enclosing_element fix needs a new optional kwarg on find_elements_by_text; this is backward compatible.
