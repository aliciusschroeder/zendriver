## Lens: reproduce (verdict confirmed, realism high, severity wrong-result)

### Summary
Tab.wait_for_ready_state (zendriver/core/tab.py, inner _poll, the `if ready_state == until:` line, ~1343) uses strict equality. document.readyState only moves forward (loading -> interactive -> complete), so once a page is 'complete', the default until='interactive' and until='loading' never match. The call polls every 0.1s until the timeout and then raises TimeoutError('time ran out while waiting for load page until interactive'). I reproduced this on real headless Chromium and with a browser-free instance patch. In the normal flow (browser.get(url, new_tab=True) and then wait_for_ready_state() with nothing in between), a small file:// page was already 'complete' on the first evaluate, so the default call failed every time.

### Refinements
The claim holds as written. One addition: the TimeoutError is not limited to pages that were already complete before the call. If a page goes loading -> complete between two 0.1s polls, the poll never sees 'interactive' and the call times out the same way. I only argued this from the code; my runs did not trigger it, since the page was already complete. until='loading' fails on any page past loading, so it is nearly unusable after Browser.get. The impact is the full timeout spent (10s by default) followed by a spurious TimeoutError, not a hang.

## Lens: refute (verdict confirmed, realism high, severity wrong-result)

### Summary
Tab.wait_for_ready_state (zendriver/core/tab.py, inner _poll, line ~1343) checks `ready_state == until`. A page that has already passed the target state never matches. The default until='interactive' (and until='loading') then polls for the whole timeout and raises TimeoutError, even though the page went past 'interactive' long before. I could not refute it. Nothing upstream reaches 'complete' later than the call: Tab.get waits for listener idle after Page.navigate, so a fast page is usually 'complete' by the time get() returns. No keepalive or close path ends the wait early. Git history and tests show no sign the equality is deliberate. I reproduced it deterministically against real headless Chromium.

### Refinements
- Only targets earlier than the page's current state are affected. until='complete' always works, and that is what every in-repo test, doc and example uses, which explains why the suite stays green.
- The default 'interactive' fails only if the page is already 'complete' at the first poll, or reaches 'complete' between 100ms polls. In practice that covers nearly any static or fast page after browser.get/tab.get, because Tab.get waits for listener idle (verified: readyState was already 'complete' when get() returned).
- The default succeeds on pages whose 'interactive' phase is still in progress when the call is made (verified with a slow subresource).
- until='loading' is almost useless today: it succeeds only if a poll lands while the new document is still loading.
- Edge case for the fix: document.open() moves readyState backwards, from 'complete' to 'loading' (verified in Chromium). A rank-based >= check would treat that document as not yet 'interactive' until it closes, which is arguably correct.
- Effect: the call raises TimeoutError after `timeout` (default 10s) instead of returning True at once. That is wrong-result (a spurious exception and wasted time), not a hang.

## Lens: fixsafety (verdict confirmed, realism high, severity wrong-result)

### Summary
Confirmed. In Tab.wait_for_ready_state (zendriver/core/tab.py, _poll at about line 1343) the check is `ready_state == until`. A document's readyState only moves forward, so a page that is already 'complete' never equals 'interactive' or 'loading'. The default call `await tab.wait_for_ready_state()` (until='interactive') on a page that has finished loading therefore polls until the timeout and then raises TimeoutError('time ran out while waiting for load page until interactive'). I reproduced this with real headless Chromium (Python 3.13.16) and with a browser-free regression test. The fix is a minimal local one: accept the requested state or any later state. The test fails on the repo code (5 failed, 5 passed) and passes on the prototype (10 passed). mypy shows no new errors.

### Refinements
- until='loading' is also broken: it times out on any page that is no longer loading. Under the fixed meaning ('this state or a later one') it is trivially true once a document exists.
- until='complete', the value every in-repo caller and test uses, is unaffected. That is why the existing test suite never caught this.
- The bug does not depend on the Python version.
- The docstring already says 'Waits for the page to reach a certain ready state' and documents `:raises asyncio.TimeoutError: If the timeout is reached before the ready state is reached`. A page that is 'complete' has reached 'interactive', so the current behaviour contradicts the documented contract. 'Reached' is also how Playwright's wait_for_load_state behaves: it resolves immediately if the state was already reached.

### Fix assessment
- kind: minimal-local
- prototype: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/Q11-fixsafety/pkg
- regression test: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/Q11-fixsafety/test_q11_ready_state.py
- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: zendriver/core/tab.py, Tab.wait_for_ready_state. Before `async def _poll()` add:
    # document.readyState only moves forward, so a later state also means
    # the requested one was reached
    states = ("loading", "interactive", "complete")
    reached = states[states.index(until) :]
and in _poll change `if ready_state == until:` to `if ready_state in reached:`.
The timeout, the error message and the evaluate-hang handling from #291 are unchanged. ruff format and ruff check are clean. Suggested CHANGELOG Unreleased/Fixed entry: '`Tab.wait_for_ready_state` no longer times out when the page is already past the requested state, such as the default `until="interactive"` on a page that has finished loading'. Optionally add to the docstring that it returns immediately if the page is already in that state or a later one.
- risks: - Locks and re-entrancy: no locks or shared state are touched, so there is no re-entrancy, deadlock or lock-ordering concern.
- Cancel and error paths: unchanged. The index is computed outside asyncio.wait_for, so the existing timeout still covers evaluate(). A ProtocolException from evaluate (for example a context destroyed during navigation) still propagates as before.
- Unexpected values: None, '' or any other unexpected readyState value is not in `reached`, so polling continues as today. The regression test covers this.
- Invalid `until` (behaviour change): a value outside the Literal, such as 'complet', now raises ValueError from tuple.index immediately instead of polling and then raising TimeoutError. mypy already rejects such values at the call site. If even that change is unwanted, use `reached = states[states.index(until):] if until in states else (until,)`.
- until='loading' (behaviour change): it now returns at once on any document. Code that relied on == to detect a new navigation entering 'loading' after an old 'complete' document would return early, but that was already racy because a 100ms poll can miss the loading phase.
- until='interactive' and other callers: 'interactive' can now be satisfied by a 'complete' document, which is the intended fix. Callers using 'complete' (all in-repo callers and tests) are unaffected; the repo tests that use it pass on the prototype.
- mypy: the prototype and an untouched copy each report 332 pre-existing errors, all path-related in cdp/ modules, with an empty diff. Neither reports any error in core/tab.py, and `uv run mypy` on the repo itself reports no issues.
