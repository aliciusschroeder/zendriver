## Lens: refute (verdict confirmed, realism medium, severity wrong-result)

### Summary
Confirmed on real headless Chromium 141. The headless UA override and the expert attachShadow patch are applied lazily, inside a Tab's first Connection.send. So the first document of a tab opened with Browser.get(new_tab=True), Browser.create_context(url), or window.open popups is requested with 'HeadlessChrome' in User-Agent, and page JS sees navigator.userAgent containing 'Headless'. The expert patch is also missing on that first document. The main tab is unaffected because Browser.get sends Page.navigate through the tab, which runs the preparation first. A reload of the new tab is clean.

### Refinements
Only affects headless=True (and expert=True for the shadow patch). It hits the first document, and its subresources and scripts, of tabs created with a URL by Chrome or zendriver without a prior send on the Tab: new_tab/new_window, create_context(url), and popups or target=_blank. Workaround: open the new tab at about:blank and then call tab.get(url). Passing Config(user_agent=...) sets --user-agent globally, which should also hide the token (assumed, not run). new_tab=True appears in docs/quickstart.md, so stealth users in headless mode can plausibly hit this.

## Lens: fixsafety (verdict confirmed, realism high, severity wrong-result)

### Summary
Confirmed on real headless Chromium: the first document request of Browser.get(new_tab=True) and of Browser.create_context(url) carries 'HeadlessChrome' in its User-Agent, and page JS during load on the new tab sees it too. Later requests and reloads do not. Popups opened with window.open() and target=_blank links also load with HeadlessChrome, and the minimal fix cannot touch those. The minimal fix (create the target at about:blank, then navigate through the tab's own session so _prepare_headless runs first) fixes the UA for get(new_tab) and create_context. It has two side effects: the new tab's history.length goes from 1 to 2, and the slow first navigation is no longer covered by the get() timeout. So the right fix is a design change (browser-level auto-attach with waitForDebuggerOnStart).

### Refinements
Scope is wider than Browser.get/create_context: every popup or target=_blank tab opened by page script loads its first document with HeadlessChrome, because Network.setUserAgentOverride is per target and is applied only on zendriver's first send to that target.

### Fix assessment
- kind: design-api
- prototype: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/BA-fixsafety/R35/pkg
- regression test: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/BA-fixsafety/R35/test_r35.py
- fails on repo: yes; passes on prototype: no; mypy ok: yes
- diff summary: Minimal attempt (diff saved in .../R35/browser.diff). Browser.get(new_tab) creates the target at 'about:blank' and then always does `await connection.send(cdp.page.navigate(url))` (the first send runs _prepare_headless/_prepare_expert before navigating). create_context creates at about:blank, then `tab_ = await self._get_tab(target_id); await tab_.send(cdp.page.navigate(url))`. Recommended design instead: in Browser.start, send Target.setAutoAttach(auto_attach=True, wait_for_debugger_on_start=True, flatten=True) on the browser connection. Handle Target.attachedToTarget by binding the session to the Tab (set session_id instead of a second attachToTarget in _attach_session), applying the UA override and expert script, then Runtime.runIfWaitingForDebugger. This covers createTarget, contexts and popups with no extra history entry and no timeout change.
- risks: Risks of the minimal fix: (a) the new tab's history.length goes from 1 to 2, so tab.back() now returns to about:blank, and the fingerprint changes; (b) the first navigation now sits in Page.navigate, which waits for the response and is outside the get() timeout, so get(new_tab, timeout) can block for the server's full latency (verified 3 s vs 0.5 s); it must be combined with the get-timeout PR putting navigate under the timeout; (c) popups are not fixed. Risks of the auto-attach design: every new target pauses until zendriver resumes it, so a failing or slow attach handler would hang page loads and popups. The Runtime.evaluate fallback in _prepare_headless (used when no headless UA metadata exists) may not answer on a paused target. The handler must run in its own task and never block the listener. It also overlaps with the lazy _attach_session (_attach_lock) and needs care to avoid double attach.
