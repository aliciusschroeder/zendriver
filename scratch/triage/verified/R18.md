## Lens: reproduce (verdict confirmed, realism high, severity wrong-result)

### Summary
Both members reproduce on real headless Chromium (chromium 141) on Python 3.13.16 and 3.11.17. Connection._prepare_expert and Connection._prepare_headless (zendriver/core/connection.py) check their done flag, await one or two _send_oneshot calls, and only then set the flag. Nothing serialises this and nothing checks whether the session is still the same one. (1) When two first sends run at the same time (asyncio.gather, or Tab.set_local_storage with 2 items), Page.addScriptToEvaluateOnNewDocument is registered twice. After the next load, element.attachShadow() throws 'RangeError: Maximum call stack size exceeded'. (2) A detach (tab.aclose()) while the first send is inside the prepare step leaves _prep_headless_done=True, or _prep_expert_done=True, on the detached connection. The next send reattaches a new session but skips the override: navigator.userAgent and the HTTP User-Agent header contain 'HeadlessChrome', or the expert attachShadow override is missing. The same send also starts a Listener on the detached connection; that Listener dies with an unobserved ValueError('no websocket connection'). It also leaves a pending Transaction in mapper, and the next detach fails that Transaction with an exception nobody retrieves.

### Refinements
1) In expert mode the detach race has a second symptom. If the detach lands during the addScript oneshot, the next _send_oneshot (Page.enable, or the headless UA one) raises ValueError('no websocket connection') out of send(), not a ProtocolException, and the flag stays unset. If the detach lands during Page.enable, _prep_expert_done is set on the detached connection and the expert override is missing after reattach. So the leak depends on which await the detach interrupts. 2) The orphan tx does not show up as 'never retrieved' right away. It stays pending in mapper, even across reattach, until the next _detach_session fails it. 3) The gather race does not depend on the Python version: it reproduced the same way on 3.11.17 and 3.13.16. 4) Realism: B14.2 is triggered by normal public API use (set_local_storage with 2 or more items, or any concurrent first calls on a new tab in expert mode). B14.6 needs a detach while the first send is in flight (a concurrent tab.aclose(), 'async with tab', or Target.detachedFromTarget/stop), which is rarer. A fix should serialise preparation per session, for example with an in-progress future or lock, and should not set the flag, or should re-check the session, when the session changed during the awaits. Ideally send() should also not start a Listener, or register a tx, on a connection whose websocket is None.

## Lens: refute (verdict confirmed, realism medium, severity wrong-result)

### Summary
I tried to refute both members and could not. Both reproduce against real headless Chromium 141 on Python 3.13.16 and 3.11.17. B14.2: when the first sends on a fresh tab run concurrently in expert mode, the attachShadow override is registered twice. After the next navigation, every element.attachShadow() call throws 'RangeError: Maximum call stack size exceeded'. B14.6: if Tab.aclose() runs while the tab's first send is inside _prepare_headless, _prep_headless_done is left True. After reattach the override is skipped and navigator.userAgent contains 'HeadlessChrome'. A Listener is also started on the detached connection and dies with an unretrieved ValueError. Nothing upstream serialises these calls, and git history shows the check-then-await is not deliberate. Realism is the weak point: B14.2 needs the opt-in expert=True, and B14.6's UA leak needs the user to call the internal aclose() and then reuse the tab.

### Refinements
B14.2: needs expert=True, which is off by default (Config expert=AUTO). It also needs two or more concurrent sends as the first traffic on a tab that has not been sent to yet: tabs from browser.get(new_tab=True) or create_context, or popups found through targets. browser.tabs[0] driven by browser.get(url) or tab.get(url) is safe, because Page.navigate runs the prepare step first, one call at a time (verified). The only internal trigger is Tab.set_local_storage with 2 or more items, which uses asyncio.gather. 'Open a tab, seed localStorage, reload' is a natural pattern, and it hits exactly this. The damage only shows from the next document on (reload or navigate), not on the current one. It then persists for the life of the session. B14.6: the UA leak needs a local detach in the window between sending the override and getting its reply. In practice that means a user calling Tab.aclose(), whose docstring says 'should not be called manually by users', at the same time as the tab's first send, and then reusing the same Tab. zendriver itself calls aclose() only from Browser.stop, where the browser is going away anyway. A detach from Chrome's side (target closed) hits the window only when the close lands around attach time. That happened 4 of 4 times with an early close and 0 of 3 with a late one. The target is then destroyed, so the UA leak does not matter, and what remains is a cosmetic 'Task exception was never retrieved' log plus one leaked Transaction. Unrelated to R18 and outside this group: on Python 3.11, browser.stop() in the expert probe also logged 'Task exception was never retrieved' from Listener.listener_loop, a ValueError raised while handling a CancelledError.

## Lens: fixsafety (verdict confirmed, realism medium, severity wrong-result)

### Summary
Both members reproduce, browser-free with a fake flat-session peer and on real headless Chromium 141. (1) _prepare_expert and _prepare_headless check their done flag and then await, with no serialisation. Concurrent first sends on a fresh expert tab register the attachShadow wrapper more than once. The second copy wraps the first, so attachShadow calls itself and throws RangeError. (2) A session detached while the first send is preparing it keeps a stale done flag, so the reattached session never gets its UA override or expert script and HeadlessChrome leaks. The same send also starts a Listener on the detached connection, which dies with ValueError('no websocket connection'), and it leaves its Transaction in mapper. A minimal local fix works and holds up under the fix-safety checks: an asyncio.Lock around the prepare calls in send(), the done flag set only if the session is still the same and still attached, an early ProtocolException in send() when the session went away during prepare, and an idempotent expert script. The idempotent script is needed because the lock alone does not cover a first send that is cancelled mid-prepare.

### Refinements
1) The lock alone is not enough for B14.2. If the first send is cancelled (wait_for timeout or task.cancel()) after its addScriptToEvaluateOnNewDocument has reached Chrome, the flag stays unset and the next send registers a second copy. On the fake peer this gives 2 registrations on S1 on both the repo and the lock-only prototype. On real Chromium the lock-only prototype gave RangeError 3/3. Making the injected script idempotent fixes it: wrap the body in `if (!Element.prototype._attachShadow) {...}`. That guard alone also fixes the gather and set_local_storage cases on real Chromium; the lock then only dedups the redundant UA override and Page.enable commands. An in-progress task awaited through asyncio.shield would be the alternative to the JS guard.
2) I confirmed that Chrome drops session-scoped addScriptToEvaluateOnNewDocument scripts on detach. On the repo with no guard, aclose, reattach, re-register and reload gave 'OK open=true'. So re-preparing after reattach is correct and is not itself a double registration.
3) A nearby defect is left unfixed. If the detach hits the first expert oneshot, the second _send_oneshot(page.enable()) raises ValueError('no websocket connection') out of send() instead of ProtocolException. This happens on both repo and prototype; the flag is correctly not set. Optional one-line follow-up: make _send_oneshot return None when websocket is None, so that the new check in send() raises ProtocolException.
4) A different path is also out of scope. A detach during _register_handlers, after tx is already in mapper, makes _detach_session fail the tx and send() raise without awaiting it, which gives 'Transaction exception was never retrieved'.

- kind: minimal-local

- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: zendriver/core/connection.py (diff at .../R18-fixsafety/fix.diff): (a) Connection.__init__ adds self._prepare_lock = asyncio.Lock(), like _attach_lock and _open_lock. (b) In send(), the _prepare_expert()/_prepare_headless() calls run inside `async with self._prepare_lock:`, followed by `if self.websocket is None: raise ProtocolException("target session was detached")` before the Listener and Transaction are created. (c) _prepare_headless and _prepare_expert capture session_id = self.session_id first and only set the done flag when `self.websocket is not None and self.session_id == session_id`. (d) The expert script is wrapped in `if (!Element.prototype._attachShadow) { ... }` so a duplicate registration is a no-op.
- risks: Re-entrancy: the lock covers only the _prepare_* calls. Those call only _send_oneshot, then _send_transaction, then websocket.send, and never call send() or aopen(), so the lock is never acquired twice. It is released before _register_handlers' nested send(). The nested send from aopen->_register_handlers takes the lock before the outer send reaches it, one after the other, not nested.
Lock ordering: tab._attach_lock is held while browser_connection._prepare_lock is taken (through browser_connection.send in _attach_session). Nothing is acquired while tab._prepare_lock is held, so there is no cycle.
Cancel and error paths: `async with` releases the lock. A detach fails the pending oneshot, which _send_oneshot swallows, so the lock is freed promptly. The prepare oneshots have no timeout, so concurrent sends now wait for the first send's prepare. In the repo each of them already awaited its own identical oneshot, so liveness is unchanged.
Caller-visible change: a send whose session was detached during prepare now raises ProtocolException('target session was detached') earlier, with the same message as the existing later check. Previously, a tab with event handlers could silently reattach in _register_handlers' nested send and succeed on an unprepared session, which could also resurrect a session that a concurrent tab.aclose() had just detached. Now it raises, and the next send reattaches and prepares properly.
Remaining small window: if another task reattaches during the prepare, the first send's command may reach the new session before that session's prepare (the waiting task runs it right after). The flag is not left stale.
Not covered: the ValueError path from refinement 3. On a page that defines its own Element.prototype._attachShadow, the JS guard would skip the override (edge case).
mypy on the prototype vs an untouched copy: 332 identical errors in both, all in cdp/ generated code, none in core/connection.py, so no new errors.
The repo was not modified, and git status is clean.
