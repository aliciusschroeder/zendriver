## Lens: reproduce (verdict confirmed, realism medium, severity hang)

### Summary
All three members reproduce with my own scripts, both against a fake CDP peer and against real headless Chromium 141.0.7390.37. A1.5: a successful session reply that is read in the same burst as Target.detachedFromTarget gets thrown away, and the caller gets ProtocolException('target session was detached'). This only happens on Python 3.12 and later; 3.11 is fine. A1.6: cancelling or timing out a fresh tab's first command while _attach_session is waiting for the Target.attachToTarget reply leaves a session attached in Chrome that is never detached, one per cancel. This happens on 3.11 and on 3.13. B14.7: if detachedFromTarget is read in the same burst as the attach reply, it is dropped because the session is not registered yet. _attach_session then registers the dead session, and that send and every later send on the tab hang forever. Chrome answers commands on the dead session with an error that has no sessionId, and the browser listener drops it. This only happens on Python 3.12 and later. On real Chrome, A1.5 and B14.7 both trigger 100% of the time when the event loop is busy for 200 ms right after the writes, and 0% when it is idle.

### Refinements
1) A1.5 and B14.7 depend on the Python version. Both reproduce on 3.12 and 3.13 but not on 3.11, where asyncio.wait_for wraps each recv in a task, so the session listener and _attach_session get to run between frames. A1.6 does not depend on the version.
2) On real Chrome the trigger is ordinary: the event loop is busy for about 200 ms (sync CPU work, time.sleep, a blocking handler) while the target is going away, so Chrome's frames pile up and are read in one burst. With an idle loop, Chrome's frames came in separate reads and zendriver behaved correctly in all trials.
3) The B14.7 hang has two causes that work together. (a) The detach is dropped because the session is not registered yet. (b) Error replies without a sessionId for a command sent on a session go to the browser listener. There, 'message["id"] in self.connection.mapper' misses, so the reply is silently dropped, even though _next_message_id says ids are shared so such replies could be matched. Fixing (b), by looking the id up in the session mappers, would turn this hang and similar ones into a clear 'Session with given id not found' error. The dead sessions also stay in browser.connection._sessions.
4) In the headless config the first stuck await is in _prepare_headless (_send_oneshot), not the user's command.
5) Separate from this group: after a detach, Connection.send can create a new Listener for an already detached connection (send checks the listener again after _prepare_headless, whose _send_oneshot swallows ProtocolException). That listener then dies with 'Task exception was never retrieved ... ValueError(no websocket connection)' from _receive_message. I saw this in the block=0 real-Chrome runs and the 3.11 runs.
6) A1.6: the leak lasts as long as the browser websocket (my assumption, not tested). The next send attaches a new session and works.

## Lens: refute (verdict confirmed, realism medium, severity hang)

### Summary
I could not refute any of the three members. Each one reproduced against real headless Chromium 141 through zendriver's public API. A1.5 and B14.7 need Python 3.12 or later: they reproduced on 3.12.3 and 3.13.16 and never on 3.11.17. A1.6 does not depend on the Python version. Both 3.12-only races need a structural condition. On 3.12+, asyncio.wait_for runs the coroutine inline, and websockets 14.1 Assembler.get returns buffered frames without suspending. So when the reply and the Target.detachedFromTarget frame are read in the same chunk, the browser Listener handles both in one task step. In A1.5 that step discards the reply already queued in session._inbox. In B14.7 it drops the detach, because the session is not yet in _sessions. For page targets Chrome sends the two frames 4-6 ms apart, so they only coalesce when the event loop is busy. For OOPIF removal the gap can be as small as 10 us, so they can coalesce even on an idle loop. A1.6 is a real orphaned Chrome session, but it is bounded: Chrome detaches it when the target closes or the browser websocket closes. 'Never detached' overstates it.

### Refinements
1) A1.5 and B14.7 require Python 3.12 or later. On 3.11, wait_for wraps the read in a task, so the session listener or the _attach_session continuation runs before the next read. They also require the reply and the detach to be parsed from the same socket read. That happens readily for OOPIF teardown, where the gap is 1 ms or less. For page targets the gap is about 4-6 ms, so the event loop must be blocked for at least that long when the reply arrives. 2) B14.7 only hangs if the target dies within about 1 ms after Chrome processed the attach. A slightly later destruction makes the attach fail cleanly with 'No target with given id found'. The hang ends only when the browser websocket closes, through browser.stop() or a connection drop. It defeats select/find(include_frames=True) timeouts, because those check elapsed time between iterations rather than wrapping each send. In headless mode the stuck send is the Network.setUserAgentOverride from _prepare_headless. 3) A1.5 matters mainly for commands that end their own session, such as Page.close or Target.detachFromTarget sent on the same session. For other in-flight commands on a dying target, the exception is usually what the caller would have got anyway. 4) A1.6 is low impact. Only one orphan leaks per attach attempt that is cancelled during the attach round trip, and Chrome reaps it when the target closes or the websocket closes. 5) Side observation outside this group: probes repeatedly logged 'Task exception was never retrieved ... ValueError("no websocket connection")' from Listener tasks. Connection.send recreates a Listener after aopen and _prepare_headless even if the session has just been detached, and that Listener's _receive_message raises with websocket=None.

## Lens: fixsafety (verdict confirmed, realism medium, severity hang)

### Summary
All three ordering bugs in zendriver/core/connection.py reproduce on the repo code. A1.5: a session reply that arrives in the same burst as Target.detachedFromTarget is dropped by Connection._detach_session, which sets self._inbox = None and then fails the tx. B14.7: Connection._attach_session registers the session only after its awaited send() resumes. If the detach arrives in the same burst as the attach reply, the browser listener sees an unknown session and ignores the detach. Every later send on the tab then hangs at Connection.send 'return await tx'. A1.5 and B14.7 depend on Python >= 3.12, where wait_for awaits inline and websockets returns buffered frames without suspending. Both reproduce on 3.12.3 and 3.13.16 and not on 3.11.17. A1.6 does not depend on the Python version and reproduces on real Chromium: a cancelled first command leaves the attach tx cancelled, so the session Chrome creates is never recorded or detached. A small local fix in connection.py fixes all three, and a variant of A1.6 (aclose while the attach is pending) as well.

### Refinements
1. Python version matters. A1.5 and B14.7 show only on Python >= 3.12: they reproduce on 3.12.3 and 3.13.16, and the same test passes on untouched code under 3.11.17. A1.6 shows on every version.

2. Real-Chrome realism differs by member:
- A1.6 is deterministic with small wait_for timeouts on the first command of a fresh tab (browser.get(new_tab=True) does not attach).
- A1.5 and B14.7 need Chrome to coalesce two frames into one read. 15 real trials of each did not hit it, so treat them as load-dependent.
- Triage called the fix 'register before the reply'. Registering before the reply is impossible because the session id is unknown until then. What works is registering while the reply is parsed. Wrapping cdp.target.attach_to_target in a generator does that: Transaction.__call__ resumes the generator synchronously inside the browser listener, before it reads the next frame.

3. A1.6 has two variants the finder did not list, both failing on the repo:
- concurrent first sends where the first is cancelled, which orphans S1;
- tab.aclose() before the late attach reply.
Shielding the attach alone would have resurrected an aclosed tab: session_id=S1, closed=False and S1 not detached. The prototype therefore also makes aclose await a pending attach.

4. Adjacent pre-existing issue, not fixed here: send() and aopen() recreate a Listener for a session that was detached during the send, for example after _prepare_headless. That listener dies with ValueError('no websocket connection') and logs 'Task exception was never retrieved'. In the real-Chrome race loop this happened 15/15 times on both repo and prototype. The prototype adds a 'session_id is None -> raise ProtocolException("target session was detached")' check after the attach so the B14.7 path does not trigger it.

### Fix assessment
- kind: minimal-local
- prototype: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/R22-fixsafety/pkg
- regression test: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/R22-fixsafety/tests/test_r22_session_attach.py
- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: Diff saved at /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/R22-fixsafety/prototype.diff. All changes are in zendriver/core/connection.py:
(1) B14.7: Connection._attach_session sends a new generator Connection._attach_to_target(browser_connection, target_id). It does 'session_id = yield from cdp.target.attach_to_target(...)' and then registers session_id, _session_parent, _inbox, browser_connection._sessions[sid], websocket and Listener. That code runs inside Transaction.__call__ in the browser listener, before the listener reads the next frame. After the attach, _attach_session raises ProtocolException('target session was detached') if session_id is None again.
(2) A1.6: the attach send runs as asyncio.ensure_future, stored in a new self._attaching field and awaited through asyncio.shield. A cancelled caller no longer cancels the attach tx, and a later caller awaits the same attach instead of starting a second one. aclose() first awaits a pending _attaching (shielded, exceptions ignored), so the late session is detached rather than resurrected.
(3) A1.5: _detach_session keeps a reference to the old inbox and, before _fail_pending_transactions, delivers every queued reply whose id is in self.mapper. It calls tx(**message), and a parse error becomes tx.set_exception. Queued events are still dropped.
No lock is added or reordered.
- risks: - Session registration now runs inside Transaction.__call__ in the browser listener. Any exception there would escape tx(**message) and kill the browser listener. The body is trivial (Queue(), dict assignment, create_task), but a real PR should keep it that small.
- A cancelled caller no longer cancels the attach. If Chrome never answers, later callers and aclose() wait on the same pending attach until the browser connection closes and the listener fails it. The repo behaved the same way, because each retry re-sent an attach that also hung. aclose already awaits a detachFromTarget reply, so the exposure matches.
- Browser.stop calls aclose() on each target, so it can wait for a pending attach. That is bounded by the reply or by the connection closing.
- asyncio.Lock is not re-entered: _attach_to_target takes no lock. The only lock order is the tab's _attach_lock, then the browser's _open_lock, unchanged.
- shield marks the inner exception as retrieved when the outer is cancelled. No 'exception never retrieved' warnings appeared in any run.
- Behaviour changes a caller would notice:
  - A command whose reply arrives with the detach now returns its result instead of raising.
  - A send to a target detached during the attach now raises 'target session was detached' instead of hanging.
  - A cancelled first command no longer causes a second attach.
- On Python <= 3.11 there is a theoretical window where wait_for's inner task has already dequeued a reply when the detach runs, and the drain does not cover it. It was not observed: the test passes on 3.11 both before and after the fix. Delivering the detach through the inbox would cover it, at the cost of depending on the session listener running.
- The pre-existing stray-Listener ValueError noise after a detach during send() is not addressed.
