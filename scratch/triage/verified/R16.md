## Lens: reproduce (verdict confirmed, realism medium, severity hang)

### Summary
I reproduced all four members myself, on Python 3.13.16 with websockets 14.1, importing the repo copy (zendriver/__init__.py under /home/user/zendriver). (1) When the peer closes the socket, Listener.listener_loop breaks out on ConnectionClosed but leaves connection.websocket set to a CLOSED ClientConnection. After that, Connection.closed reports False, aopen() returns without reconnecting even though the server still accepts connections, and send() raises ConnectionClosedOK. (2) aclose() called while aopen() is still inside websockets.connect is a no-op. The socket then opens and a listener task starts running after the 'close'. (3) send() cancelled by wait_for leaves a cancelled Transaction in conn.mapper. 200 timeouts left 200 entries, which only aclose cleared. (4) Connection.wait() hangs forever at connection.py Connection.wait:579 `await self.listener.idle.wait()` when the listener stops while the page is busy. This happens with the real headless Chromium after Target.closeTarget, after tab.close(), with `await tab`, and with Tab.get(url) (stuck at tab.py Tab.get:513). It also happens with a fake peer, both on listener.cancel() and on a peer-side websocket close. The same scenarios without the session going away return in about 0.1s.

### Refinements
- B14.5: no session detach is needed. A plain browser-websocket close also hangs wait(), because the ConnectionClosed branch breaks without setting idle. Even after a reattach, the waiter stays stuck on the OLD listener's Event, since a new Listener gets a new Event. Passing a number to wait(t) is not affected because asyncio.wait_for bounds it (I only reasoned this, I did not run it).
- C1: in practice the main visible effects are (a) Connection.closed staying False after the peer closes and (b) send() raising a websockets ConnectionClosed* exception instead of ProtocolException. Browser._stop then tries browser.close on the dead socket and logs a warning. Automatic reconnect would rarely succeed against real Chrome, because the browser websocket only closes when Chrome exits.
- C2: in Browser._stop, an in-progress connect makes `connection.closed` read True, so aclose is skipped entirely and the socket and listener task survive the stop until Chrome dies.
- C3: the leak is bounded by the number of commands that never get a reply, such as an awaitPromise on a promise that never resolves. A late reply pops the entry. _send_oneshot has the same shape, but I did not test it.

## Lens: refute (verdict confirmed, realism medium, severity hang)

### Summary
I could not refute any of the four members; each one reproduces. Only B14.5 is a hang. Connection.wait() awaits the old listener's idle Event (Connection.wait, `await self.listener.idle.wait()`, connection.py:579) with no timeout and no check that the listener is still running. If the session's Listener is cancelled while idle is clear, that Event is never set, so `await tab`, tab.wait() and Tab.get(url) on the same tab (tab.py:513) hang forever. This happens when the tab is closed, on browser.stop() from another task, or when Chrome is killed. The three seeds are real but minor and unlikely to be hit. SEED-C1: after ConnectionClosed every later send fails fast with ConnectionClosedError and never reconnects; nothing hangs. SEED-C2: the race is only reachable by calling Connection.aclose() directly while a connect is in progress. SEED-C3: the leak is small and temporary, about 1.3 KB per entry, and Chrome's late reply clears it, for example on navigation.

### Refinements
B14.5:
- It hangs only if the tab's session listener is busy (idle clear) when the session detaches.
- On a quiet page with no domains enabled, the window is only about the listener's time_before_considered_idle (0.1 s; 0.75 s in interactive mode) after the last session message. wait()'s own Target.getTargetInfo reply counts as such a message, so the window measured 20-80 ms after the call.
- A close that lands before the getTargetInfo reply makes wait() raise ProtocolException instead of hanging. That is the case for an immediate click-to-window.close().
- On pages with a steady stream of events (handlers or manually enabled Network/Runtime/Page domains), the window covers the whole wait.
- Affected: wait() with t=None, `await tab`, Tab.get(url) on the same tab (tab.py:513), and get/set_local_storage when target.url is empty.
- Not affected: wait(t) with a number (it uses wait_for), and Browser.get.
- Triggers: Target.closeTarget, tab.close() from another task, page window.close(), browser.stop() from another task, and a Chrome crash or kill.
- Nothing else ends the wait: websockets keepalive does not touch the Event, and a new Listener created later has a new Event.
- Not specific to a Python version (the Event is simply never set).

SEED-C1:
- Severity is wrong-result/cosmetic, not hang. The connection is permanently dead and `closed` reports False, but later sends raise at once.
- It matters only when Chrome survives the socket close.

SEED-C2:
- Only reachable through a direct Connection.aclose() during the first or re-opening aopen. Browser.stop does not trigger it (stop skips aclose when closed is True), and the process kill bounds it for local browsers.

SEED-C3:
- The entry lives only until Chrome replies, the session detaches or the connection closes. Chrome replies to pending awaitPromise evaluates on navigation or reload.
- Only commands that are never answered accumulate, at about 1.3 KB each.

The group mixes one real hang (B14.5) with three minor state-hygiene issues. The fixes are independent.

## Lens: fixsafety (verdict confirmed, realism medium, severity hang)

### Summary
All four members reproduce on the repo code (branch ccr-9a8a26e1-b0l7bh, HEAD 064148f), both against a fake CDP peer and, for B14.5, against real headless Chromium. (1) B14.5: Connection.wait() has no done check on the listener. When a busy listener is cancelled (session detached: Target.closeTarget, or a browser crash/websocket close) or breaks on ConnectionClosed, its idle Event is never set, so `await tab` / tab.wait() / Tab.get() hang forever. (2) SEED-C1: on ConnectionClosed, Listener.listener_loop breaks but leaves connection.websocket set. As a result `closed` stays False, aopen() never reconnects, and every later send raises ConnectionClosedOK on the dead socket. (3) SEED-C2: aclose() while aopen() is still inside websockets.connect is a no-op, so the socket and a running listener exist after the close. The same happens for a tab whose _attach_session is in progress. (4) SEED-C3: a send() cancelled by wait_for leaves its Transaction in conn.mapper until a reply or close. Each problem has a small local fix in connection.py. Each fix is independent: applying only one fix makes only its own tests pass.

### Refinements
1. SEED-C2 also applies to flat sessions (tabs): aclose() racing _attach_session. The fix must cover both locks, not only _open_lock.
2. B14.5 is reachable not only via tab close but via any browser crash during `await tab` / Tab.get(): the ConnectionClosed branch detaches all sessions, which cancels their listeners. On repo code this hangs forever, as shown with SIGKILL on real Chromium.
3. SEED-C1's most visible effect is the stale `closed` property, more than the missing reconnect. After a browser crash, Browser._stop tries to send browser.close on the dead socket.
4. SEED-C3 is transient retention, low severity. `_send_oneshot` has the same no-pop-on-cancel pattern. The tx is also put in mapper before `_register_handlers`, whose bare `except:` appears to swallow CancelledError. That is a separate issue that I did not verify here.
5. A pre-existing issue on Python 3.10/3.11 only, also on repo code: if a session is detached in the loop iteration where its listener's wait_for inner task has been scheduled but not started, the listener dies with ValueError('no websocket connection'), logged as 'Task exception was never retrieved'. It reproduced 2 times in a 12-iteration sweep, on both the untouched copy and the prototype. The prototype's tab-aclose lock makes the attach-then-close probe land in that window on 3.11, but this is cosmetic and not a regression.

### Fix assessment
- kind: minimal-local
- prototype: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/R16-fixsafety/pkg
- regression test: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/R16-fixsafety/test_r16_connection_close_state.py
- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: zendriver/core/connection.py only (full diff in /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/R16-fixsafety/prototype.diff):
(B14.5) Listener.run: add `self.task.add_done_callback(lambda _: self.idle.set())`. A stopped listener counts as idle, so every exit path wakes wait(): break on cancel, ConnectionClosed, an exception, or a cancel before the first step. A finally inside listener_loop would miss the cancel-before-start case.
(SEED-C1) Listener.listener_loop, ConnectionClosed branch: also set `self.connection.websocket = None` and clear enabled_domains and manually_enabled_domains, mirroring aclose(). After that, `closed` is True and the next aopen() reconnects and re-registers handlers.
(SEED-C2) Connection.aclose: wrap the session branch in `async with self._attach_lock:` and the websocket branch in `async with self._open_lock:` (with `if self.websocket is None: return` inside). An in-progress attach or connect then finishes first and is closed or detached by this call, instead of opening after it.
(SEED-C3) Connection.send: add `finally: self.mapper.pop(tx.id, None)` to the existing try around `return await tx`.
- risks: Locks. asyncio.Lock is not reentrant, but aclose() is never called while the same task holds _open_lock or _attach_lock: aopen's except path only calls listener.cancel(), and __aexit__ and Browser._stop hold no locks. Lock order in tab.aclose is tab._attach_lock then browser._open_lock (via browser_connection.send -> aopen). That is the same order _attach_session uses, and the browser's aclose takes only its own _open_lock and calls the synchronous _detach_session(). So there is no inversion. A stress probe (5 concurrent senders plus 10 aclose cycles, delayed handshake) finished without a deadlock, with mapper empty and 0 server connections left.

Cancel paths. If aclose is cancelled while waiting for the lock, nothing changes and the lock is released (verified). The prototype raises more 'connection was closed' ProtocolExceptions in that stress run (50 vs 25), because connects that complete during a close are now closed too.

Behaviour changes callers would notice:
(a) aclose() can now block until an in-flight websockets.connect finishes (open_timeout defaults to 10s). tab.aclose() can now block until an in-flight Target.attachToTarget round trip finishes.
(b) After a peer close, the next send tries to reconnect to the same URL. If Chrome is dead, callers get OSError/ConnectionRefusedError from websockets.connect instead of websockets ConnectionClosed. Browser._stop now skips browser.close and aclose because closed is True, which removes a spurious warning. A reconnect does not restore Target.setDiscoverTargets autodiscovery; that is a pre-existing limitation.
(c) wait() / `await tab` now returns None when the listener stops, instead of hanging. A caller whose tab was closed carries on and gets an error on its next command. Raising ProtocolException('target session was detached') would be the alternative design.
(d) A dead Listener's repr now shows [idle].

A theoretical stale-listener clobber of a new websocket in the C1 branch cannot happen with C2's lock in place, because a reconnect cannot start before aclose finishes and a cancelled listener gets CancelledError. Not covered by these fixes: _send_oneshot's identical cancel leak, and the pre-existing 3.10/3.11 ValueError listener-death race on detach (cosmetic, reproduces on repo code).
