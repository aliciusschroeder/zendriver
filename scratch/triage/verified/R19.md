## Lens: reproduce (verdict confirmed, realism medium, severity hang)

### Summary
Confirmed by running it. Listener.listener_loop (connection.py, the callback dispatch around line 999-1002) runs every non-coroutine-function handler through asyncio.create_task(asyncio.to_thread(callback, *args)), so it executes in a worker thread with no event loop. (a) Connection.feed_cdp (line 543-556) calls asyncio.ensure_future(self.send(cdp_obj)), which raises RuntimeError "There is no current event loop in thread 'asyncio_N'" in that thread. Fetch.continueRequest is never sent. The only trace is 'Task exception was never retrieved' plus 'coroutine Connection.send was never awaited'. With real headless Chromium, Page.navigate hangs until the request is continued by hand from the loop thread. The same code with an async handler works. (b) A lambda that returns a coroutine, a lambda that calls asyncio.create_task, and an object with an async __call__ all fail inspect.iscoroutinefunction. They are run in the thread, and the returned coroutine is dropped ('never awaited'); the create_task case raises 'no running event loop'. The async work never runs. Reproduced on Python 3.13.16 and on 3.11.17, both with websockets 14.1.

### Refinements
- The shipped example (examples/fetch_domain.py) uses an async handler, which works. The bug appears only with sync defs, lambdas and async-__call__ objects. Those are documented as valid handlers (add_handler docstring), and feed_cdp's docstring stresses that it is a plain method.
- A side effect, not part of this group: when a RequestPaused handler is registered, aopen() -> _register_handlers auto-sends Fetch.enable (id 1) before the explicit cdp.fetch.enable() (id 2). The peer saw Fetch.enable twice, so two requestPaused events (one per enable) reached the handler.
- The B14.4 side claim about asyncio.Event.set from a sync handler was not reproduced: the waiter woke in under 1 ms, with and without debug mode. Only loop-bound calls that need a current or running loop (ensure_future, create_task, get_event_loop) fail outright.
- On 3.12+, _ensure_future may close the coroutine. The 'never awaited' warning still appeared on 3.13 in my run, but do not rely on that warning as the test oracle. Assert that the peer received Fetch.continueRequest.
- A fix only in feed_cdp (capture the loop and use call_soon_threadsafe / run_coroutine_threadsafe when off-loop) fixes (a) but not (b). Fixing (b) also needs the dispatch to await an awaitable returned by a sync callable, or to detect async __call__.

## Lens: refute (verdict confirmed, realism medium, severity hang)

### Summary
I could not refute the core claim. Listener.listener_loop (connection.py, the `else: asyncio.create_task(asyncio.to_thread(callback, *args))` branch, ~L1002) runs every non-coroutine-function handler in a worker thread. Connection.feed_cdp (~L556) calls `asyncio.ensure_future(self.send(...))`, which needs an event loop in the current thread, so it raises `RuntimeError: There is no current event loop in thread 'asyncio_0'` there. Fetch.continueRequest is never sent and the paused request stays paused. I reproduced this on real headless Chromium 141 and against a browser-free fake CDP peer (Python 3.13). The asyncio failure is identical on 3.11 and 3.12. It is a regression: in the zendriver 0.10.1 wheel, sync handlers ran inline on the loop thread, so feed_cdp from a sync handler or lambda worked. The 0.10.2 change ('Refactor to asynchronous handlers to avoid blocking the listening loop') moved them to to_thread and broke it. The lambda/coroutine sub-claim is also real, but the plain 'lambda returning a coroutine' and 'object with async __call__' forms never worked, even in 0.10.1. Only 'lambda: asyncio.create_task(...)' (and any other loop-bound call from a sync handler) is new breakage from the same root cause.

### Refinements
- The failure is deterministic (not a race) for any sync callable handler (def, lambda, bound method) that calls feed_cdp or any other loop-bound asyncio API (ensure_future, create_task, Event.set, Future.set_result) on every Python version from 3.10 up. 3.10 is assumed; I tested 3.11 through 3.13.
- How long the hang lasts depends on the caller. tab.get is bounded by its default timeout=10 and raises TimeoutError. A raw tab.send(page.navigate) or runtime.evaluate(await_promise=True) waits indefinitely, because Chrome keeps the request paused (verified for 28s or more).
- The failure is loud, not silent: asyncio's default exception handler prints the traceback at GC time, and RuntimeWarnings are emitted.
- The 'lambda returning a coroutine' and 'async __call__ object' forms are long-standing design limitations from nodriver and 0.10.1, not regressions. The docstring advertises lambdas, but its example is a sync print lambda, which works. Treat these as lower-priority API polish (await or schedule awaitable results), separate from the feed_cdp regression.
- Fix notes: feed_cdp needs the connection's loop when called off-loop. Nothing in the thread knows the loop, so capture it, for example when the Listener is created. Use run_coroutine_threadsafe off-loop and keep ensure_future/create_task on-loop. Alternatively, run sync handlers on the loop again, which reverts 0.10.2's non-blocking intent.

## Lens: fixsafety (verdict confirmed, realism high, severity hang)

### Summary
Confirmed on Python 3.11 and 3.13, with a fake CDP peer and with real headless Chromium. In Listener.listener_loop, every non-coroutine handler is dispatched as asyncio.create_task(asyncio.to_thread(callback, *args)), so it runs in a worker thread 'asyncio_N' that has no event loop. Connection.feed_cdp is just asyncio.ensure_future(self.send(cdp_obj)). Called from that thread, it raises RuntimeError('There is no current event loop in thread ...'). The error is lost in an unretrieved to_thread task, Connection.send is never awaited, and Fetch.continueRequest is never sent, so the paused request hangs. A sync callable that returns a coroutine (a lambda calling an async function, or an object with an async __call__, for which inspect.iscoroutinefunction is False) has its coroutine dropped with only a RuntimeWarning. The worker-thread dispatch itself is deliberate (CHANGELOG 0.10.2: 'Refactor to asynchronous handlers to avoid blocking the listening loop'; test_sync_handlers_are_each_called uses loop.call_soon_threadsafe), so the right minimal fix keeps the thread and makes feed_cdp thread-safe. It also awaits awaitables that sync handlers return.

### Refinements
1) The hang is browser-side: the request stays paused. No Python task is stuck. The only Python-side traces are the unretrieved to_thread task exception and the never-awaited warning. 2) The worker-thread dispatch is intended (0.10.2 changelog, and an existing test uses call_soon_threadsafe), so the fix should not move sync handlers back onto the loop. Doing that would be a design change: blocking sync handlers would block the listener again. 3) The minimal fix leaves one sub-claim of A2.6 unfixed: `lambda e: asyncio.create_task(...)` and other loop APIs called from a sync handler still fail in the thread (verified on the prototype: 'RuntimeError: no running event loop'). That needs either a doc note in add_handler (sync handlers run in a worker thread; use loop.call_soon_threadsafe) or the design change. 4) feed_cdp on a connection that has never created a listener, called from a non-loop thread, still raises as before. Example: a handler on browser.connection calling feed_cdp on a tab that was never opened. Within the documented pattern the handler's own connection always has a listener, because that listener dispatched the event.

### Fix assessment
- kind: minimal-local

- diff summary: zendriver/core/connection.py only (full diff in /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/R19-fixsafety/fix.diff).
(1) Connection.feed_cdp: the on-loop path is unchanged. Only when asyncio.get_running_loop() raises (the case that currently always fails) does it take the loop from self.listener.task.get_loop() and call loop.call_soon_threadsafe(asyncio.ensure_future, self.send(cdp_obj)). With no listener it falls through to the old ensure_future, which raises the same error as before.
```
loop = None
try:
    asyncio.get_running_loop()
except RuntimeError:
    # synchronous event handlers run in a worker thread (see
    # Listener.listener_loop), which has no event loop of its own
    if self.listener and self.listener.task:
        loop = self.listener.task.get_loop()
if loop is not None:
    loop.call_soon_threadsafe(asyncio.ensure_future, self.send(cdp_obj))
else:
    asyncio.ensure_future(self.send(cdp_obj))
```
(2) New module-level helper `async def _call_sync_handler(handler, *args)`. It runs `result = await asyncio.to_thread(handler, *args)` and then awaits the result if inspect.isawaitable(result). listener_loop's sync branch now does asyncio.create_task(_call_sync_handler(callback, *args)) in place of create_task(asyncio.to_thread(...)). Sync handlers still run off-loop.
ruff format and ruff check pass.
- risks: Re-entrancy and locks: the worker thread only builds the send() coroutine object and schedules it. It does not wait for the result and holds no lock. send() runs on the loop thread and takes _open_lock/_attach_lock there as usual, so there is no new lock ordering and no deadlock. Reading listener.task concurrently is a benign race: any listener of the connection belongs to the same loop.

Errors: call_soon_threadsafe(ensure_future, ...) creates the task on the loop. A failing send therefore still shows up as 'Task exception was never retrieved', the same as the on-loop path (covered by test_feed_cdp_error_is_logged_like_on_loop_path). run_coroutine_threadsafe would have hidden the error in an unread concurrent future. If the loop is already closed, call_soon_threadsafe raises RuntimeError in the handler thread, which matches today's error class.

Behaviour changes callers would notice: (a) feed_cdp from sync handlers now works. (b) An awaitable returned by a sync handler is now awaited on the loop. This covers a lambda calling an async function and an object with an async __call__. A handler that returns a never-completing awaitable leaves one pending task. That task does not block the listener, the same as a hanging async handler. Handlers returning non-awaitables are unaffected.

Not fixed by design: loop APIs such as create_task or Event.set called directly inside a sync handler still fail or are unsafe in the worker thread. Fixing that means running sync handlers on the loop, an API/behaviour change that would undo the 0.10.2 non-blocking intent. Recommend a docstring note in add_handler and feed_cdp instead.

mypy: 332 errors on both the prototype and an untouched copy (same set after normalising line numbers), with 0 in core/connection.py, so no new errors.
