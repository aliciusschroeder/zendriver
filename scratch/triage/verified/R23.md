## Lens: reproduce (verdict confirmed, realism medium, severity crash)

### Summary
Confirmed with real headless Chromium 141 on Python 3.13 (repo copy imported). Browser.start() saves the host/port it picks itself into self.config (start, around lines 530-535), and _stop() never resets them. So start() after stop() takes the connect-existing path. It launches no Chrome, test_connection fails against the dead port, the stale self.info skips the 'Failed to connect' check, and Connection.send raises ConnectionRefusedError after about 2.5 s. After Chrome dies on its own, start() takes the `self._process.poll() is not None` branch and calls self.create(config=self.config). That copies the dead host/port, launches nothing and raises 'Failed to connect to browser'. Even with host/port reset by hand, stale targets stay in self.targets, so browser.get() fails with 'No target with given id found', and the restarted instance is not registered with asyncio_atexit again. For a Browser connected through host/port, `stopped` is True while it is live, the atexit hook skips _stop(), and a second start() opens a second websocket without closing the first. The old socket and its Listener stay alive.

### Refinements
Root cause, read from the code: Browser.start (browser.py around lines 530-535) writes the auto-chosen host/port into self.config, and connect_existing is decided only from `config.host is not None and config.port is not None`. So the config cannot tell user-supplied values from auto-chosen ones. Browser._stop (around lines 874-917) clears _process/_process_pid but not config.host/port, self.info, self.targets or self.connection. Extra findings: (1) The dead-process branch `return await self.create(config=self.config)` returns a new Browser instead of restarting self, so `await b.start()` without using the result leaves b dead even once host/port are fixed. The fresh instance is also registered with atexit while the old one stays in registered_instances. (2) update_targets never prunes the stale targets from the first run, so after a manual host/port reset tabs[0]/main_tab are dead Tab objects. (3) For B16.13, changing `stopped` so the atexit hook runs _stop() for connect-existing browsers would send Browser.close to a Chrome the user launched, which is a behaviour change. A fix should base `stopped` on the connection, and close only the websocket/forwarders at exit, not the remote browser. (4) The start() guard `if self._process or self._process_pid` does not cover connect-existing, so start() is not idempotent there (A3.10). Fix candidates: reset auto-chosen host/port in _stop (or keep a private flag for user-provided values), clear info/targets/connection on stop, and guard start() on `self.connection and not self.connection.closed`.

## Lens: refute (verdict confirmed, realism low, severity crash)

### Summary
I tried to refute all five members and could not; each one reproduced against real headless Chromium 141 on Python 3.13. (1) After stop(), start() never launches Chrome. On the first run, Browser.start set self.config.host='127.0.0.1' and config.port=free_port(), so the second call sets connect_existing=True. It then waits about 2.5 s on test_connection. The stale self.info skips the 'Failed to connect' check, and the call raises ConnectionRefusedError against the dead port. (2) After Chrome dies, start() takes its dedicated branch `return await self.create(config=self.config)`. The new instance inherits the dead host/port, also skips the launch, and raises the misleading 'Failed to connect to browser ... pass sandbox=False' error. (3) Even with host/port reset by hand, the stale Tab in self.targets makes browser.get() fail with 'No target with given id found'. (4) A Browser connected via host/port reports stopped=True while it is live, so _atexit_cleanup skips _stop. (5) A second start() on a live connected browser replaces self.connection without closing the old one. The old websocket and its Listener keep running. Arguments against the bug's practical weight: the library itself never calls start() on an existing instance (create() is the only caller). Docs, README and tests never restart a Browser object; tests/conftest.py creates a new browser when stopped is True. Every restart failure is loud: an exception after about 2.5 s, no hang and no silent wrong result. Workaround: call zd.start() again. The atexit skip for connected browsers has almost no visible effect at exit, because asyncio.run cancels the listener task and the process exit closes the sockets. It even leaves the externally launched Chrome alive, which is arguably what a user who attached to it wants (explicit stop() closes it). Against that, the crash-recovery branch in start() shows the authors meant restart to work, and that branch can never succeed. So the bug is real, but its realism is low.

### Refinements
Only user code that reuses the same Browser object hits this: `await b.stop(); await b.start()`, or `if b.stopped: await b.start()` after a crash. No library path calls start() twice. The most plausible real trigger is crash recovery in long-running scrapers, the case the dedicated create() branch in start() was written for. Even if that branch worked, it returns a NEW Browser, so callers that ignore start()'s return value would keep using the dead object. Failures are deterministic and loud (an exception after browser_connection_max_tries * browser_connection_timeout, about 2.5 s by default), never a hang. A failed stop->start also re-adds the browser to util.get_registered_instances() (start adds it before the failing send) and leaves self.connection pointing at a never-opened Connection. Assumed, not verified: if another process re-binds the stale port between stop() and start(), the restart would silently attach to that foreign browser, and a later stop() would send it Browser.close. That needs a free_port() collision and is unlikely. A3.10 applies only to connect-existing browsers when start() is called while the old websocket is live; after the remote browser closes, the old listener ends by itself. B16.13's atexit consequence is cosmetic at exit; the meaningful part is the wrong stopped value for user code. Related but outside the claims: start() also overwrites a user-supplied port when host is None (both are reset by the else branch). Fix note: a fix must keep connect-existing semantics for user-supplied host/port (remember whether they were user-provided), clear self.info/targets/connection on _stop, and re-register atexit when start() relaunches.

## Lens: fixsafety (verdict confirmed, realism high, severity crash)

### Summary
Confirmed on real headless Chromium with Python 3.13. (1) Browser.start() saves the host and port it picks itself (127.0.0.1 plus free_port()) into self.config. Browser._stop() never resets them. So the next start() treats the browser as connect-existing and never launches Chrome. Because self.info is still stale, the 'Failed to connect' check (`if not self.info`) is skipped, and start() fails with ConnectionRefusedError after about 2.5 s. (2) The branch in start() for a dead process, `return await self.create(config=self.config)`, copies the same dead host and port into a new instance, which fails with 'Failed to connect to browser'. (3) If host and port are reset by hand, the old Tab objects are still in self.targets and browser.get() fails with 'No target with given id found'. The restarted browser is also never registered with asyncio_atexit again. (4) For a browser connected through host/port, `stopped` is always True, and a second start() opens a second websocket. The first one stays open with its Listener running, even after stop(). A minimal local fix in browser.py works and is safe. One version of it, the 'already running' guard, would regress reconnecting. Another, clearing targets too early, adds unretrieved StopIteration task exceptions. The final prototype avoids both.

### Refinements
1) Do not add a 'no-op while connected' guard for host/port browsers (my v1). Connection.closed only becomes True on aclose. After the remote browser dies, stopped stays False, so start() would refuse to reconnect. The repo reconnects in that case, by accident. My non-regression test passes on the repo, fails on v1 and passes on v2/v3. Instead, close the old connection before making the new one, so a second start() reconnects without leaking. 2) Do not clear self.targets right after closing the tabs in _stop (my v2). Events arriving during Browser.close then hit `next(filter(...))` in _handle_target_update and leave 'Task exception was never retrieved: RuntimeError coroutine raised StopIteration'. Seen in 2 of 5 runs of a stop loop on v2, and in 0 of 4 on the repo and 0 of 4 on v3. Clear the targets at the end of _stop. A tolerant `next(..., None)` in _handle_target_update would make this fully robust. 3) This group depends on Q3: if the process died and start() runs before the listener has seen the close (sync kill()+wait() with no yield), the new `await self._stop()` in start() raises ConnectionClosedError from Tab.aclose (detachFromTarget catches only ProtocolException). Calling stop() at that point raises the same way on the repo. A retry succeeds. With a Q3-style `except (ProtocolException, websockets.exceptions.ConnectionClosed)` in Connection.aclose, the first attempt succeeds. 4) Not in this group, but seen: on each start(), _extensions re-adds --load-extension to _browser_args, so a restart duplicates it (harmless).
