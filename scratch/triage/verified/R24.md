## Lens: reproduce (verdict confirmed, realism high, severity crash)

### Summary
Reproduced against a real headless Chromium (141.0.7390.37) on Python 3.13.16. I started Chromium myself by absolute path with --remote-debugging-port, so there was a live DevTools endpoint, and ran with PATH=/usr/bin:/bin, which has no chrome, chromium, brave or msedge binary on it. Under those conditions zendriver.start(host, port), Browser.create(host=, port=), create_from_undetected_chromedriver(driver) and a bare Config(host=, port=) all raise FileNotFoundError('could not find a valid browser binary...'). The error comes from Config.__init__ (config.py line 89-90, `if not browser_executable_path: browser_executable_path = find_executable(browser)`), before any connection attempt. Two controls show the binary is never used on this path. Passing browser_executable_path='/does/not/exist' against the same endpoint connects (Chrome/141.0.7390.37, 1 tab, b._process is None). The same calls with chromium on PATH also connect. Browser.start only checks the executable inside `if not connect_existing:`, so in host+port mode the autodetection in Config.__init__ only gets in the way.

### Refinements
1) The exception happens in Config.__init__, before Browser.start runs. A user-supplied Config(host=..., port=...) therefore cannot be built either, not just the start() and create() helpers. 2) The only workaround today is a dummy browser_executable_path. That works because Browser.start never touches the path when connect_existing is true: the existence check, the _start_process call and the initial-tab wait are all inside `if not connect_existing`. 3) For create_from_undetected_chromedriver the setup is less realistic: undetected_chromedriver itself launched a local Chrome, so the failure only happens when that Chrome is outside PATH and the standard locations (for example, uc was given a custom binary path). The remote or dockerised Chrome case (zd.start(host, port) from a slim client container) is the common one. 4) Side observation, out of scope: one run with a long TMPDIR made my own Chromium fail to bind its singleton socket. That is my test environment, not zendriver. Also, Browser.start's failure path calls stop() with connection=None and _process=None, so _stop returns early and the uc_* temp profile is left behind.

## Lens: refute (verdict confirmed, realism medium, severity crash)

### Summary
I could not refute this. Config.__init__ (zendriver/core/config.py, line 89-90) runs find_executable(browser) whenever browser_executable_path is falsy, and it does so before it looks at host or port. If no local Chrome, Brave or Edge is on PATH (or in the standard Windows or macOS install locations), zd.start(host, port), Browser.create(host=..., port=...), Config(host=..., port=...) and util.create_from_undetected_chromedriver all raise FileNotFoundError('could not find a valid browser binary...'). The failure happens before any connection attempt. Browser.start never needs the binary on this path: it skips the existence check under `if not connect_existing:` (browser.py, Browser.start, around line 537) and only uses `exe` in _start_process under the same guard. A bogus browser_executable_path therefore connects and navigates normally. The only thing that softens the bug is a workaround: the error message itself tells the user to pass browser_executable_path, and any string works.

### Refinements
The bug only triggers when find_executable finds nothing: no chrome, chromium, google-chrome, brave or msedge on PATH (or in PROGRAMFILES/LOCALAPPDATA on Windows, /Applications on macOS, /opt/microsoft/msedge* on Linux). Users connecting to a Chrome on the same machine that has Chrome installed never see it. An easy workaround exists for start(), Browser.create and Config (pass any browser_executable_path; the error message hints at this). There is none for create_from_undetected_chromedriver, which calls bare Config(). The failure is an immediate exception with a clear message, not a hang or data loss.

## Lens: fixsafety (verdict confirmed, realism high, severity crash)

### Summary
Config.__init__ (zendriver/core/config.py, the `if not browser_executable_path: browser_executable_path = find_executable(browser)` block) looks up a local browser binary on every call. When no Chrome, Brave or Edge is installed, connecting to an existing or remote browser fails with FileNotFoundError before any connection is attempted, although Browser.start never uses the executable when connect_existing is true. This was reproduced with real Chromium (launched by absolute path, PATH without any chrome) through zd.start(host, port), Browser.create(host, port) and util.create_from_undetected_chromedriver. create_from_undetected_chromedriver calls Config() with no host or port and sets them afterwards, so skipping the lookup only in Config.__init__ does not fix it: util.py has to pass host and port into Config(...). A minimal local fix was prototyped and checked.

### Refinements
The triage strategy ('defer lookup when host and port are given') is not enough alone. util.create_from_undetected_chromedriver builds Config() with no host or port and assigns conf.host/conf.port afterwards, so it must pass Config(host=host, port=int(port)) instead. Browser.start also reads self.config.browser_executable_path outside the connect_existing guard (`exe = ...` before params). That is harmless at runtime once the value is None, but mypy needs narrowing before util._start_process(exe, ...). Using the same `host is None or port is None` test as Browser.start's connect_existing keeps the two in step.
