## Lens: reproduce (verdict confirmed, realism medium, severity hang)

### Summary
Both members reproduced on real headless Chromium 141 with Python 3.13.16. (1) If a RequestPaused handler exists, a manual Fetch.disable is undone on the next send: _register_handlers re-sends Fetch.enable with {} params, every request gets paused, and Page.navigate never returns. The same thing happens after a tab.intercept() block exits while the user has their own RequestPaused handler. (2) After remove_handlers(cdp.fetch.RequestPaused, h), Fetch is dropped from enabled_domains but Fetch.disable is never sent. The browser keeps pausing every request, so tab.get() raises TimeoutError and evaluate() hangs. An explicit Fetch.disable fixes it immediately.

### Refinements
A2.2 affects every auto-enabled domain, not just Fetch. For Network or Page, a manual X.disable is silently re-enabled on the next send (test_manual_disable_send checks only the lists, right after the disable). It becomes a hang only for Fetch, because a param-less Fetch.enable means pattern '*' at the Request stage. A12.2 has the same leak for Network/Page/etc.: the browser keeps emitting events after the last handler is removed. A side effect is that a later expect_request gets events with no send (this masks R30 A10.7). A12.2 also applies to remove_handlers() with no args and to remove_handlers(cdp.fetch.RequestPaused).

The spy showed [('Fetch.enable', {}), ('Page.navigate', {...'/b'})] and paused requests ['.../b']. ## Lens: refute (verdict confirmed, realism medium, severity hang)

### Summary
I could not refute either member. Both hangs reproduce on real headless Chromium (Python 3.13.16). (1) Connection._register_handlers drops an auto-enabled domain from enabled_domains in its final `for ed in enabled_domains` loop but never sends X.disable. After a RequestPaused handler is removed, Chrome keeps pausing every request and nothing continues them. (2) Connection.send calls _update_manual_domain('disable') after _register_handlers, which removes the domain from both lists. If a RequestPaused handler is still registered, the next send of any kind (aopen() always runs _register_handlers) sends a param-less Fetch.enable, which intercepts every URL.

### Refinements
A12.2: hangs only for Fetch, or another domain whose enable changes browser behaviour. For Network, Page and similar domains, leaving them enabled just keeps events flowing, and R30 shows that this sometimes helps. It hits only users who relied on auto-enable, meaning they never sent Fetch.enable themselves, and who do not send Fetch.disable after removing the handler. Fetch.disable sent before or after remove_handlers avoids it. A2.2: needs a RequestPaused handler still registered after the manual Fetch.disable. It hangs only if that handler does not continue requests outside the user's original pattern; otherwise the result is silent interception of every URL. Any later zendriver call triggers the re-enable, including _is_update ones such as tab.wait(), because aopen() calls _register_handlers.

### Member verdicts
- A12.2: confirmed — Setup: an auto-enabled Fetch handler that continues requests; navigating to /one works. After remove_handlers(RequestPaused, h), tab.get('/two', timeout=5) raises TimeoutError. Only Page.navigate was sent, and Chrome still delivered a raw Fetch.requestPaused for /two. enabled_domains==[], manually_enabled_domains==[], and evaluate() also timed out. A longer run showed Page.navigate still pending after 45s; task.print_stack() shows it stuck in Connection.send at `return await tx`. A manual Fetch.disable releases it.
- A2.2: confirmed — Sequence: add_handler(RequestPaused), fetch.enable(patterns=[*/x]), fetch.disable(), then Page.navigate. The spy shows ('Fetch.enable', {}) sent before Page.navigate and /b gets paused. With a handler that continues only */x, the navigate raises TimeoutError. With a handler that continues everything (the examples/fetch_domain.py style), nothing hangs, but the handler now sees /b and the favicon, so the interception the user turned off is back. The intercept() sub-claim is weaker: a user RequestPaused handler registered before the block had already auto-enabled Fetch({}), so the re-enable after _teardown restores the earlier state. It only adds a new failure when the handler is added inside the block.

## Lens: fixsafety (verdict confirmed, realism medium, severity hang)

### Summary
Both members reproduce, against a fake peer and in real headless Chromium. (1) Connection._register_handlers drops an auto-enabled domain from enabled_domains when its last handler goes, but never sends X.disable. For an auto-enabled Fetch (default '*' pattern, Request stage), every later request stays paused and navigation hangs. (2) A manual X.disable takes the domain out of both lists in _update_manual_domain. On the next send, _register_handlers sees the handler that is still registered and sends a param-less X.enable, so Fetch pauses every request again and Page.navigate hangs. The fix for (1) is a safe local change only if it is limited to Fetch. (2) needs a design decision: a sticky manual disable changes behaviour that zendriver itself depends on.

### Refinements
The fix for A12.2 must not be generic. expect_response's three Network handlers remove themselves before response_body sends Network.getResponseBody, so disabling Network when its last handler goes deletes the body; this was demonstrated in Chrome. DOM.disable would also invalidate node ids. Only Fetch (and arguably Debugger) is harmful when left enabled. The disable only happens on the next send(), not inside remove_handlers (which is sync). A2.2 is a semantics question. My sticky-disable prototype passes the A2.2 test but breaks two behaviours that pass on the repo, shown in tests/test_r26_behaviour_change.py (repo '2 passed', prototype '2 failed'). (a) tab.xpath() sends dom.enable(_is_update=True) and then disable_dom_agent() -> DOM.disable, after which a user's DOM handler would never get DOM re-enabled. (b) A user handler that relied on auto-enabled Fetch loses it after a tab.intercept() block's teardown Fetch.disable.

### Member verdicts
- A2.2: confirmed — Fake peer: after add_handler(RequestPaused), fetch.enable(patterns=['*/x']) and fetch.disable(), the next send emitted [('Fetch.enable', {}), ('Page.reload', {})]. Real Chromium: tab.send(page.navigate(c.html)) TIMED OUT after 6s, with the paused list ['http://127.0.0.1:.../c.html']. Mechanism: _update_manual_domain('disable') removes fetch from both lists, then _register_handlers re-enables it with no params. The intercept()+user-handler variant restores the earlier auto-enabled state, which may be what that user wants. So whether this is a bug depends on the intended semantics.
- A12.2: confirmed — Fake peer: after remove_handlers(RequestPaused, h), the next send emitted only ['Page.reload'] (no Fetch.disable) and enabled_domains was []. Real Chromium: navigation worked while a continuing handler was registered. After remove_handlers, tab.send(page.navigate(b.html)) TIMED OUT after 6s while zendriver reported enabled_domains [].

- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: connection.py: (A12.2, safe and local) in _register_handlers' drop loop, skip domains a concurrent call already removed, and when the dropped domain is cdp.fetch, await self.send(cdp.fetch.disable(), _is_update=True) inside try/except Exception with a debug log.
