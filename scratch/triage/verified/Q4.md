## Lens: reproduce (verdict confirmed, realism high, severity leak)

### Summary
Confirmed with real headless Chromium 141 on Python 3.13.16. Once util._start_process has spawned Chrome and Browser.start has added self to util.get_registered_instances(), any CancelledError (an asyncio.wait_for timeout, or Ctrl+C because asyncio.run cancels the main task) or any exception (update_targets, set_discover_targets, _read_headless_user_agent) leaves start() with no cleanup. Browser.create registers asyncio_atexit only after start() returns, and the caller never gets the instance. So the Chrome process keeps running after the interpreter exits (reparented to ppid 1, still alive 20 s later), the /tmp/uc_* profile is never removed, and the registry keeps the Browser. The only failure path that cleans up is the `if not self.info` branch, which calls self.stop().

### Refinements
1. The failed-to-connect path (`if not self.info`) does clean up. An earlier run that could not connect left no process and no profile, so the leak covers every exit except that one.
2. The leak also happens with a fully unpatched zendriver, triggered by a plain wait_for timeout or a real SIGINT/Ctrl+C. Those are the realistic triggers. On this machine a normal start takes about 0.27 s, so a user-level timeout of 1-2 s only fires on slow or loaded machines or slow first-run profiles.
3. In later-stage failures the leaked Browser also keeps an OPEN websocket Connection, and the registry holds it.
4. The same leak hits the start() re-entry path `return await self.create(config=self.config)`, because it goes through the same code. I did not test that separately.
5. Not Python-version specific: the code paths have no version-dependent behaviour. I ran Python 3.13 only.
6. A fix also has to cover connect_existing (host and port given). There _process is None, so cleanup must not try to kill anything, but it should still discard the registry entry and close the connection.

## Lens: refute (verdict confirmed, realism medium, severity leak)

### Summary
Confirmed with real headless Chromium on Python 3.13. Browser.start() (zendriver/core/browser.py, Browser.start around lines 517-646) spawns Chrome with util._start_process and calls util.get_registered_instances().add(self). After that nothing catches errors: no try/except/finally, and stop() is only called on the `if not self.info` path. Browser.create (around line 196) calls asyncio_atexit.register(instance._atexit_cleanup) only after `await instance.start()` returns. So a CancelledError or any other exception after the spawn leaves three things behind: a live Chrome, the /tmp/uc_* profile, and the registry entry. The orphaned Chrome keeps running after the interpreter exits, reparented to pid 1. My refutation attempts only narrowed the claim. (1) Ctrl+C in a terminal also sends SIGINT to Chrome, because it is in the same process group (no start_new_session). Chrome exits cleanly on SIGINT, so in that case no process is orphaned, but the profile dir still leaks. (2) The time window is short on a healthy machine: start takes about 0.27 s here. (3) There is no await in start() before the spawn, so any cancellation with a positive timeout always lands after Chrome has been spawned.

### Refinements
1) Interactive terminal Ctrl+C does NOT orphan Chrome. Chrome is in the same foreground process group (Popen has no start_new_session/preexec_fn) and exits cleanly on SIGINT (verified). Only the /tmp/uc_* profile dir leaks, plus the registry entry, which no longer matters once the process exits. A live orphan needs the cancellation to come from inside Python (asyncio.wait_for/timeout, task.cancel, a TaskGroup sibling failing, server or app shutdown cancelling tasks, pytest-timeout) or a signal sent to the Python pid only. 2) On a healthy machine start takes about 0.27 s, so a typical user timeout (5-30 s) only fires when start hangs or is very slow. That can happen: Connection.send in set_discover_targets, update_targets or get_version has no timeout, and urlopen in test_connection uses timeout=10 per try. That is exactly when users bound start with a timeout, and retry loops then pile up orphaned Chromes. 3) Since start() has no await before the spawn, cancelling zd.start() with any positive timeout leaks every time. 4) For exceptions after the spawn: a live-process leak needs Chrome to be alive but erroring (shown only with an injected exception). A Chrome crash after /json/version leaks the profile and registry entry only. 5) Not Python-version dependent, as far as I can tell: 3.10 raises KeyboardInterrupt and then asyncio.run cancels the main task, which ends at the same CancelledError path. I only ran 3.13.

## Lens: fixsafety (verdict confirmed, realism high, severity leak)

### Summary
Confirmed. Browser.start (zendriver/core/browser.py) launches Chrome with util._start_process and calls util.get_registered_instances().add(self) before it connects. The code after that point has no try/except/finally; it calls stop() only on the `if not self.info` path. Browser.create registers asyncio_atexit only after `await instance.start()` returns. So a cancel (wait_for timeout, task.cancel, Ctrl+C) or an exception from set_discover_targets, update_targets, _wait_for_initial_tab or _read_headless_user_agent leaves three things behind: the Chrome process (reparented to pid 1 after the interpreter exits), the /tmp/uc_* profile, and a permanent registry entry. The caller never gets the instance, so it cannot stop it. Minimal fix: move the post-registration body into a helper and wrap the call in `except BaseException: stop(); raise`. In attach mode (host+port) the handler must close only the connection: a plain stop() would send Browser.close and shut down the user's existing browser.

### Refinements
1) Attach mode (host+port given): the triage hypothesis, plain stop() then re-raise, is unsafe. _stop sends cdp.browser.close() whenever the connection is open, so a failed attach would close the user's existing browser. I checked this with a variant prototype: test_failed_attach_does_not_close_the_existing_browser fails with `'Browser.close' in ['Target.setDiscoverTargets','Browser.close']`. The prototype closes only the connection when connect_existing. 2) Remaining gap, also present before the fix: _stop returns early when there is neither a connection nor a process (`if not self.connection and not self._process: return`), skipping _cleanup_temporary_profile. In attach mode, a cancel before the connection exists still leaves the empty uc_* dir that self.config() created via mkdtemp (verified: registry 0 but the temp dir exists on the prototype). A failure in _start_process itself also leaks that dir. Both are minor and outside the 'after Chrome is spawned' claim. 3) A second cancel arriving during cleanup interrupts stop() in its terminate/sleep loop: the process was already SIGTERMed (poll -15) and unregistered, but the profile is left. That is still much better than before (process alive, registered=1). 4) coro.close()/GeneratorExit while start() is suspended now raises RuntimeError('coroutine ignored GeneratorExit'); the process still gets SIGTERM. Before the fix close() succeeded silently and leaked the process. This happens only for start() coroutines that are closed or garbage-collected without being cancelled. 5) Suggested hardening: wrap the cleanup in `try: ... except Exception: logger.debug(..., exc_info=True)`, so an error raised inside stop() cannot replace the original exception. Replacing a CancelledError would turn wait_for's TimeoutError into that error.

- diff summary: zendriver/core/browser.py, Browser.start: after `util.get_registered_instances().add(self)`, the rest of start() moves unchanged into a new `async def _connect(self, connect_existing: bool) -> None` (its trailing `return self` is removed). start() now does `try: await self._connect(connect_existing) except BaseException: if connect_existing and self.connection: await self.connection.aclose()  # do not close a browser that was not launched here; await self.stop(); raise` and then `return self`. stop() is idempotent: the second call made after the existing 'Failed to connect' path returns early, and asyncio_atexit.unregister of a callback that was never registered is a no-op. Browser.create is unchanged.
- risks: No locks are on the start/stop path (_update_target_info_mutex is used only in _handle_target_update), so there is no re-entrancy or lock-ordering risk. (b) A Chrome launched by zendriver gets Browser.close on a failed start. (c) In attach mode the connection is closed but the remote browser is left running, and the instance is unregistered. (d) A user who calls `await browser.start()` directly and handles the failure gets an already-stopped instance; calling stop() again is a harmless no-op, and start() can be retried because _process is cleared. Residual risks: a second cancel during cleanup leaves the temp profile (the process is already SIGTERMed); an exception raised inside stop() would replace the original exception or CancelledError (suggest suppressing Exception from the cleanup with a debug log); GeneratorExit via coro.close() now produces RuntimeError('coroutine ignored GeneratorExit'); in attach mode a cancel before the connection exists still leaves an empty uc_* temp dir because of _stop's early return.
