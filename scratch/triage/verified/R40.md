## Lens: refute (verdict confirmed, realism low, severity wrong-result)

### Summary
Both set_window_state members reproduce in real Chromium: headless, and headful under Xvfb with no window manager. A6.6: when the window is not normal, Chrome only restores it and ignores left/top/width/height, so set_window_size after maximize/minimize/fullscreen silently does nothing to the geometry. A6.7: before switching to a non-normal state, Tab.set_window_state calls itself with the defaults 0,0,1280,720, so the restore geometry is overwritten (and in headful mode the window visibly jumps). The two combine: after tab.maximize(), set_window_size(...) ends up at 0,0 1280x720.

### Refinements
The 0,0 1280x720 result seen in A6.6 actually comes from A6.7's reset. The core of A6.6 (requested bounds dropped while the window is non-normal) holds on its own, as the raw-CDP control shows. Through zendriver's own API, A6.7 is visible only as the headful jump/resize before minimize, maximize or fullscreen, or when the window is restored by raw CDP or by the user, because medimize() always sends 0,0,1280,720 anyway. Headful maximize/minimize could not be checked because Xvfb has no window manager; fullscreen was checked headful. It needs a sequence where the size is set after a state change, which is unusual for most scripts.

## Lens: fixsafety (verdict confirmed, realism medium, severity wrong-result)

### Summary
Tab.set_window_state (tab.py, set_window_state) has two bugs, confirmed on headless Chromium. (1) A normal-state request with geometry while the window is maximized, minimized or fullscreen only restores the window; Chrome ignores the bounds and leaves it at the restore geometry. (2) For min, max and full it first calls set_window_state(state='normal') with the defaults 0,0,1280,720. That moves and resizes a normal window and overwrites its restore geometry. The fix is to restore with Bounds(window_state=NORMAL) and no geometry, only when the current state is not normal, and then apply the target.

### Refinements
The headless reset size is the window state's default (1280x720). Getting into the maximized, minimized or fullscreen states still needs the window to be normal first, so the restore step must stay; it just must not carry geometry, and it can be skipped when the window is already normal. Under Xvfb with no window manager, maximize and minimize do nothing in headful mode, but A6.7's move and resize still happens.

### Member verdicts
- A6.6: confirmed — Headless: after maximize, minimize or fullscreen, set_window_size(200,100,900,700) gives state=normal l=0 t=0 w=1280 h=720. Headful under Xvfb (no WM) the fullscreen case reproduces the same way. The prototype ends at 200,100,900,700 in both.
- A6.7: confirmed — Headless: sized to 100,50,800,600, then tab.maximize(), then a raw restore gives 0,0,1280,720. A raw maximize as control restores to 100,50,800,600. Under Xvfb, maximize is a no-op without a WM, yet the window still jumps to 0,0,1280,720.

### Fix assessment
- kind: minimal-local

- diff summary: tab.py set_window_state. The recursive `await self.set_window_state(state='normal')` is replaced. If the current bounds.window_state (from get_window) is not None or NORMAL, send set_window_bounds(window_id, Bounds(window_state=NORMAL)) first, with no geometry. Then send the target: Bounds(left, top, width, height, NORMAL) for normal, or Bounds(window_state=target) otherwise.

A non-normal window costs one extra round trip, as before. Residual risk: a real WM in headful mode may restore asynchronously, and then the bounds would still be ignored silently. Polling get_window until the state is normal, with a bound, would harden that, but it was not tested here. mypy: 332 errors, the same as an untouched copy. ruff is clean.
