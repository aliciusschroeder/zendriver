## Lens: reproduce (verdict confirmed, realism high, severity hang)

### Summary
All four members reproduced on real headless Chromium 141 with Python 3.13.16. (1) A timed-out wait_for on exp.value cancels the shared response_future. A later await raises CancelledError although the task was not cancelled (cancelling()==0), and the event handler hits InvalidStateError. Intercept behaves the same: continue_request raises CancelledError after a timed-out wait on it.request. (2) expect_request on a self-polling page never resolves until an unrelated tab.send enables Network. (3) If the body fails after the headers (ERR_CONTENT_LENGTH_MISMATCH), response_body hangs on loading_finished_future. (4) If the request is refused before any response, exp.value hangs on response_future while request_future is done. Chrome emitted Network.loadingFailed in both failure cases, and nothing handles it.

### Refinements
A10.3 depends on asyncio semantics, not the Python version: on 3.12+ wait_for cancels the current task, and on 3.11 it cancels the wrapper task. Either way the awaited stored future gets cancelled. reset() recovers the expectation, but after it fires the matched event has already gone. A10.7 is masked once Network has been enabled on the tab (the browser never disables it, R26 A12.2). B13.7 and A10.8 are the same root cause (no LoadingFailed handler); A10.8 is a subset of B13.7.

## Lens: refute (verdict confirmed, realism medium, severity hang)

### Summary
All four members reproduce on real headless Chromium. (1) A timed-out asyncio.wait_for on exp.value or interception.request cancels the shared stored future. The behaviour is the same on Python 3.11, 3.12 and 3.13. A later await then raises CancelledError in a task that was not cancelled, and the event handler's set_result raises InvalidStateError. (2) expect_request/expect_response only call add_handler. If the block makes no zendriver call, Network is never enabled and a page-initiated request is never seen. (3) Network.loadingFailed is never handled, so response_body, or value/response for a request blocked before any response, waits forever.

### Refinements
A10.3: needs a timed-out wait followed by another await on the same expectation. Most users give up after a timeout, and reset() gives fresh futures. A10.7: hangs only when the block makes no zendriver call at all (pure await or asyncio.sleep) AND Network was never enabled on that target in Chrome, e.g. the first expect use on a new tab. B13.7/A10.8: needs the matched request to fail (aborted by navigation, truncated body, blocked or unsafe port, DNS error). Unbounded only because the awaitables take no timeout.

### Member verdicts

Leaving the block (Fetch.disable) released it. A pure-asyncio check gives the same result on 3.11.17, 3.12.3 and 3.13.16. ## Lens: fixsafety (verdict confirmed, realism medium, severity hang)

### Summary
All four members reproduce. (1) The expect/intercept properties await the bare stored future, so a timed-out wait_for cancels the shared future and the expectation is dead: later awaits raise CancelledError and the handler's set_result raises InvalidStateError. (2) expect_request/expect_response only add handlers on enter. Network.enable is sent on the next tab.send, so a page-initiated request is never seen while the caller just awaits. (3) Network.loadingFailed is not handled, so response_body hangs when the request fails after headers, and value/response hang when it fails before any response.

### Refinements
A10.8 duplicates B13.7. A10.7 only happens on tabs where Network was never enabled, because zendriver never disables Network after the handlers are removed. A10.3 also covers DownloadExpectation.value, which the claim does not mention. It does not depend on the Python version (reproduced on 3.11, 3.12 and 3.13).

### Member verdicts
- A10.3: confirmed — After wait_for(exp.value, 0.1) times out, exp.response_future is <Future cancelled> with current_task().cancelling() == 0 (3.13). A pure-asyncio check shows the same on 3.11.17 and 3.12.3, and asyncio.shield keeps the future pending. Fake peer test: the second await raised CancelledError at expect.py ResponseExpectation.value 'return await self.response_future'. intercept.py uses the identical '(await self.response_future)' pattern (6 sites); that part was checked only by code reading. DownloadExpectation.value has the same pattern.
- A10.7: confirmed — Real Chromium on a fresh tab (enabled_domains [] []) with a page polling fetch('/poll') every 300ms: expect_request(...).value was 'still pending after 4s' on the repo and resolved on the prototype. The fake peer showed no Network.enable sent by __aenter__ on the repo and ['Network.enable'] on the prototype. Caveat: once Network has been enabled on a tab, it is never disabled (see R26), so the bug only shows on tabs where Network was never enabled.

### Fix assessment
- kind: minimal-local
- prototype: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/BB-fixsafety/R30/pkg
- regression test: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/BB-fixsafety/tests/test_r30.py
- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: expect.py: every property await is wrapped in asyncio.shield (request, response, response_body for both futures, RequestExpectation.value, ResponseExpectation.value, DownloadExpectation.value). _setup also registers a Network.LoadingFailed handler and then awaits self.tab._register_handlers(), so Network is enabled on enter. The new _loading_failed_handler matches request_id, tears down all handlers, and sets ProtocolException(f'loading failed: {event.error_text}') on response_future and loading_finished_future if they are not done. It calls future.exception() so an unawaited future is not logged as never retrieved. _teardown removes the LoadingFailed handler. intercept.py: the 6 '(await self.response_future)' sites are wrapped in asyncio.shield.
- risks: The exception type for a failed load (ProtocolException) is an API choice. Callers that used to catch only TimeoutError now get ProtocolException quickly. One exception instance is shared by two futures, so tracebacks accumulate if both are awaited (cosmetic). __aenter__ now makes a CDP round trip through _register_handlers. That function's bare 'except:' swallows CancelledError during __aenter__, an existing hazard shared with every send(). Re-entrancy: send(_is_update=True) -> aopen -> _register_handlers is nested but does not recurse, since network is appended before the send. No locks are involved. With shield, cancelling the caller no longer cancels the shared future, which is the intended change. Repo tests tests/core/test_tab.py + test_connection.py, including the external-marked expect/intercept tests: 47 passed. No new mypy errors.
