## Lens: refute (verdict confirmed, realism low, severity wrong-result)

### Summary
Confirmed on real headless Chromium 141. With config.autodiscover_targets=False, Chrome sends no TargetInfoChanged, TargetCreated or TargetDestroyed on the browser connection. So Browser.get and Tab.get(new_tab=True) always raise TimeoutError after the full timeout, although the navigation happened, and Tab.close always waits 10s and then raises TimeoutError although the tab closed. update_targets never prunes, so closed tabs stay in browser.tabs and main_tab, and browser.get then fails with 'No target with given id found'. Realism is low: autodiscover_targets is not a Config constructor parameter and is not documented. It is set to True in Config.__init__ and can only be overridden through **kwargs or attribute assignment, and its only user in the repo is a test that never calls get or close.

### Refinements
This only matters to users who set the undocumented knob: cfg.autodiscover_targets=False, or zd.start(autodiscover_targets=False) through **kwargs. It is not listed in the Config docstring or the constructor signature. In the repo, only tests/core/test_browser.py::test_start_waits_for_initial_tab sets it, and that test only checks len(browser.tabs). With the knob set, get and close fail every time: the outcome is deterministic, not a race.

## Lens: fixsafety (verdict confirmed, realism medium, severity wrong-result)

### Summary
Confirmed on real headless Chromium with config.autodiscover_targets=False. Browser.get(url) and Browser.get(new_tab=True) always raise TimeoutError although the navigation succeeded. Tab.close() closes the tab, then waits 10 s and raises TimeoutError. update_targets never drops destroyed targets, so main_tab and tabs[0] stay on the closed tab and browser.get then fails with 'No target with given id found'. A small prototype fixes all four. It always sends Target.setDiscoverTargets(discover=True) but installs the _handle_target_update tracking handlers only when autodiscover_targets is set. update_targets prunes targets that getTargets no longer lists. The TargetInfoChanged/TargetDestroyed lookups in _handle_target_update tolerate a target that is already missing.

### Refinements
Partial: with autodiscover off, a closed tab stays in browser.targets until the next update_targets, because no tracking handler runs. So tab.close() followed by browser.get() without update_targets still fails with 'No target with given id found' (verified on the prototype). If that should work, Tab.close should also drop itself from browser.targets by target_id (not with list.remove/==, since Tab.__eq__ compares TargetInfo). Pruning without the tolerant handler would make a late TargetDestroyed raise StopIteration inside a handler task, so both changes must ship together.

### Fix assessment
- kind: minimal-local
- prototype: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/BA-fixsafety/R25/pkg
- regression test: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/BA-fixsafety/R25/test_r25.py
- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: browser.py only, diff saved in .../BA-fixsafety/R25/browser.diff. (1) Browser.start: move `await self.connection.send(cdp.target.set_discover_targets(discover=True))` out of the `if self.config.autodiscover_targets:` block. The handler installation stays inside it. (2) update_targets: build target_ids from getTargets and remove self.targets entries whose target_id is not in it, before the add/update loop. (3) _handle_target_update: `current_tab = next((t for t in self.targets if t.target_id == ...), None)` and return if None, for both TargetInfoChanged and TargetDestroyed.
- risks: This changes what autodiscover_targets=False means at the protocol level. Target events now reach the browser connection's listener but are dropped, since no handler is installed. The cost is small, but they clear the listener's idle flag. A purist could instead poll Target.getTargetInfo or getTargets in Browser.get and Tab.close (more code); triage called that 'design'. Browser.get waits are owned by the get-timeout PR. Pruned Tab objects are not aclose()d. That is harmless because Chrome already detached their flat sessions (detachedFromTarget triggers _detach_session). A race of prune against a TargetCreated handler for a just-created target is theoretical only: the getTargets reply includes targets created before it, and the update_targets wakeup is scheduled before a later handler task. update_targets takes no lock and the target mutex is unchanged, so no new lock ordering or re-entrancy risk.
