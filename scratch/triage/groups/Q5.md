# Group Q5 (stderr-pipe)

queue: fix  |  triage severity: hang  |  triage fix kind: local

## Claim
Chrome's stdout/stderr are PIPEs that nothing drains while the browser runs; once ~64 KiB accumulate Chrome blocks and every CDP call (and stop()) hangs. The startup-failure stderr capture also always returns empty while Chrome is alive

## Files
zendriver/core/util.py (_start_process, _read_process_stderr), zendriver/core/browser.py (start failure path)

## Triage fix strategy (a hypothesis, not a requirement)
Do not leave undrained pipes: send stdout to DEVNULL and stderr to a temporary file (or drain it) and read that for the failure message.

## Triage test approach
Real Chromium with --enable-logging=stderr and console spam -> evaluate keeps answering past 64 KiB of stderr; failure path still reports stderr content.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### B13.4: Chrome's stdout/stderr are PIPEs that are never drained: once ~64 KiB of logs pile up, Chrome blocks and every CDP call (and stop()) hangs
- where (may drift): zendriver/core/util.py:_start_process:352
- finder severity: hang
- claim: zd.start() spawns Chrome with stdout=PIPE and stderr=PIPE. Nothing reads them during the session; only _read_process_stderr does, and only after start() fails to connect. Chrome logs ERROR lines to stderr. Default flags in a container already leave about 5 KB at startup (dbus errors), and each navigation that hits a certificate error adds about 370 bytes. When the 64 KiB kernel pipe buffer fills, the Chrome thread that logs blocks in write(2). From then on: (a) default flags: after about 157 bad-certificate navigations, Page.navigate is never answered, so tab.get / tab.send / find etc. hang; (b) with a common debugging flag such as browser_args=['--enable-logging=stderr','--v=1'], the browser process stops answering even Browser.getVersion within a few navigations, and browser.stop() hangs too (see the stop() finding). The user sees a browser that just stops responding, with no error.
- finder evidence (unverified): probe_pipe.py with --enable-logging=stderr --v=1: `pipe size 65536 stderr pending after start 44192` ... `iteration 5: TIMEOUT - stderr pending 64361` / `browser process does NOT answer Browser.getVersion` / `stop failed TimeoutError`. probe_pipe4.py with DEFAULT flags, navigating to a self-signed https://127.0.0.1 server: stderr grew 5073 -> 14145 -> 23073 -> ... -> 62046 bytes, then `iteration 157: navigate TIMEOUT stderr pending 64350 after 473s`. In normal navigation without errors (probe_pipe.py, default flags, 400 pages) stderr stayed at 5019 bytes, so the growth comes from Chrome's ERROR logging.
- finder repro idea: Start with browser_args=['--enable-logging=stderr','--v=1'], loop over tab.get(data-url) with a 10 s wait_for, and observe the TimeoutError after about 5 iterations while FIONREAD on browser._process.stderr reads about 64 KiB. Fix: spawn with stdout/stderr=DEVNULL (or a file / a drained reader task) and keep only a bounded tail for the failure message.

### A3.5: Chrome's stdout/stderr are PIPEs that are never drained; once 64 KiB is written Chrome blocks and every CDP command hangs
- where (may drift): zendriver/core/util.py:_start_process (called from Browser.start):348
- finder severity: hang
- claim: `zd.start(browser_args=['--enable-logging=stderr'])` (or `--v=1`, or a build or flags that log a lot), then run a page that logs to the console. Browser.start launches Chrome with stdout=PIPE and stderr=PIPE, and nothing reads them while the browser runs. _read_process_stderr only reads on a failed start. When the kernel pipe buffer fills (64 KiB on Linux), Chrome's write(2) on stderr blocks and the browser stops answering CDP. tab.evaluate('1+1') never returns, and browser.stop() hangs too (see the stop() finding). Default flags write only about 5 KB at startup in this environment, so the trigger needs logging enabled or a chatty build.
- finder evidence (unverified): probe_pipe2.py: 'stderr pending after start: 6124', 'round 0 ok, stderr pending: 56414', 'round 1 TIMEOUT, stderr pending: 64420', 'simple evaluate TIMEOUT: browser hung; pending 64420', 'stop timed out'. probe_pipe.py with default flags: stderr stayed at 5241 bytes after console spam and failed navigations.
- finder repro idea: Start with browser_args=['--enable-logging=stderr'], run `console.log('x'.repeat(100))` 600 times through tab.evaluate, and watch FIONREAD on b._process.stderr reach about 64 KiB. Then `await asyncio.wait_for(tab.evaluate('1+1'), 10)` raises TimeoutError.

### A9.1: Chrome hangs once its stdout/stderr PIPE fills: _start_process opens pipes that nothing reads while the browser runs
- where (may drift): zendriver/core/util.py:_start_process:348
- finder severity: hang
- claim: browser = await zendriver.start(headless=True, browser_args=['--enable-logging=stderr']); then a page that logs to the console in a loop (e.g. tab.get(data: URL with console.error(...)) about 200 times). _start_process launches Chrome with stdout=PIPE and stderr=PIPE. During normal operation nothing reads those pipes (the only reader is _read_process_stderr, on the connect-failure path). Once about 64KB of stderr has piled up, Chrome's next log write blocks in the kernel. The browser process stops servicing CDP, so every tab.get/evaluate/send after that hangs forever unless the caller adds a timeout. With default flags the same thing happens in any session that writes 64KB of Chrome ERROR lines over its lifetime, such as TLS handshake failures, GPU/dbus errors or GCM registration errors.
- finder evidence (unverified): Probe output: 'iteration 180: ok stderr pending=56570', 'iteration 200: ok stderr pending=62170', 'iteration 204: TIMEOUT, stderr pending=63010', 'wchan: anon_pipe_write'. The Chrome browser process was blocked writing to the full stderr pipe, and tab.get/evaluate timed out from then on. Control run with default flags: pending stayed at 4982 bytes for 200 iterations. grep: the only reads of _process.stderr/stdout are in _read_process_stderr (browser.py:589, connect-failure path).
- finder repro idea: Probe in scratch dir probe_pipe.py: start(headless=True, browser_args=['--enable-logging=stderr']). Loop up to 400 times over tab.get(data URL with console.error('x'.repeat(200))) + tab.evaluate('1+1'), each step under wait_for(10). Use ioctl FIONREAD on browser._process.stderr to watch the pending byte count, and read /proc/<pid>/wchan when it hangs.

### B16.1: Chrome stdout/stderr are piped but never read, so Chrome freezes once the stderr pipe fills
- where (may drift): zendriver/core/util.py:_start_process:351
- finder severity: hang
- claim: zd.start(headless=True, browser_args=['--enable-logging=stderr']), then call tab.evaluate("console.log('x'.repeat(2000))") about 15 times. Chrome writes every log line to the stderr pipe, and nothing reads it: Browser.start reads stderr only on the failure path through util._read_process_stderr. When the pipe buffer fills, Chrome's writes block, the browser stops answering CDP, and every later tab call hangs. browser.stop() then hangs too (see the stop() finding). With default args the pipe also fills, more slowly: about 5 KB of dbus/GPU errors at startup plus about 150 bytes for each network or SSL error, so a long crawl can stall the same way.
- finder evidence (unverified): Probe p7_pipe.py: with --enable-logging=stderr, 'evaluate #15 timed out after 5.0s; unread stderr bytes=36931; process alive=True', then 'browser.stop() did not finish within 15s'. With default args: 5073 unread bytes right after start, rising to 5793 after 5 navigations to an expired-certificate page. The fix is stdout/stderr=DEVNULL, or a drain task or temp file kept for the failure message.
- finder repro idea: Start with --enable-logging=stderr, loop tab.evaluate(console.log of 2 KB) wrapped in wait_for(…, 5), and read FIONREAD on browser._process.stderr when it times out.

### B13.8: Startup-failure stderr capture always returns empty while Chrome is still running: blocking read(65536) cannot finish within the 0.25 s wait_for
- where (may drift): zendriver/core/util.py:_read_process_stderr:368
- finder severity: wrong-result
- claim: zd.start() cannot connect while Chrome stays alive, e.g. the DevTools port is taken ('Cannot start http server for devtools.') or Chrome needs more than browser_connection_max_tries*browser_connection_timeout (default 2.5 s) to open the port. Browser.start then calls _read_process_stderr, which runs process.stderr.read(65536) in a thread. BufferedReader.read(n) blocks until n bytes or EOF, and a live Chrome produces neither, so asyncio.wait_for(…, 0.25) always times out. Browser.start logs 'Browser stderr: No output from browser' even though Chrome wrote the exact cause to the pipe. The worker thread stays blocked until stop() terminates the process, and its data is thrown away. Only an already-exited Chrome (EOF) gets its stderr reported.
- finder evidence (unverified): probe_stderr.py: `LOGGED: Browser stderr: No output from browser` / `start failed after 3.2s: Failed to connect to browser`. probe_stderr2.py, same port-conflict setup with a raw Popen: `alive: True bytes waiting in stderr pipe: 6110`, including '[ERROR:content/browser/devtools/devtools_http_handler.cc:310] Cannot start http server for devtools.'
- finder repro idea: Bind (without listening) a socket on a port, monkeypatch zendriver.core.util.free_port to return it, run zd.start(headless=True) and capture logs. Assert the logged stderr contains 'Cannot start http server for devtools'. Fix: read non-blocking / read1 / os.read of the bytes available, or drain stderr continuously.
