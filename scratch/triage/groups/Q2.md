# Group Q2 (timeout-bounds)

queue: fix  |  triage severity: hang  |  triage fix kind: local

## Claim
Polling methods that take a timeout (find/select/find_all/select_all/xpath/wait_for/tab()/verify_cf/cf_* helpers) do not bound their CDP awaits, so they hang forever when the renderer does not answer (alert() open, busy JS)

## Files
zendriver/core/tab.py (find, select, find_all, select_all, xpath, wait_for), zendriver/core/cloudflare.py (cf_wait_for_interactive_challenge, cf_is_interactive_challenge_present, verify_cf)

## Triage fix strategy (a hypothesis, not a requirement)
Bound the whole polling loop with the remaining time (asyncio.wait_for around the loop body/coroutine) while keeping each method's documented outcome on timeout (TimeoutError for find/select/wait_for/verify_cf, [] for xpath, False for cf_is_interactive_challenge_present). xpath: make at least one attempt even with timeout<=0 and do not busy-spin. Tab.get/Browser.get are out of scope (owned by another PR).

## Triage test approach
Fake CDP peer that never answers DOM.getDocument (or real Chromium with alert()) -> each method returns/raises within timeout+small epsilon; outer safety net.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### B13.1: Tab.find/select/find_all/select_all ignore their timeout when one CDP reply never comes, so they hang forever on a page blocked by a dialog or busy JS
- where (may drift): zendriver/core/tab.py:Tab.select (also Tab.find, Tab.find_all, Tab.select_all):351
- finder severity: hang
- claim: tab = browser.main_tab; await tab.get(page); the page then runs alert('x') or a busy loop `while(true){}` (from a setTimeout, an anti-bot script, etc.). await tab.select('#nope', timeout=2) never returns. The same happens with find('x', timeout=2), find_all(..., timeout=2) and select_all(..., timeout=2). Each loop pass awaits query_selector/find_elements_by_text -> self.send(DOM.getDocument), which the blocked renderer never answers. The timeout is only compared after the await returns (`if loop.time() - start_time > timeout`), so it is never checked. include_frames=True adds more unbounded sends (get_frames, per-frame searches), and self.sleep(0.5) adds one more (update_target). This is the same defect fixed for wait_for_ready_state in bd88ccd (#291, 'page stuck behind a dialog'), but the fix was not applied to these methods.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-B13/probe_hang.py against real headless Chromium. In both 'busy' (while(true){}) and 'alert' modes it printed e.g. `busy select: STILL PENDING after 15.0s (timeout=2)` with the stack `Tab.select() running at tab.py:351 wait_for=<Transaction method: DOM.getDocument status: pending>`. Same for find (tab.py:308), find_all (tab.py:382) and select_all (tab.py:423). In the same conditions wait_for_ready_state(timeout=2) correctly raised TimeoutError after 2.0s, and tab.wait(2) returned after 2.0s.
- finder repro idea: Real headless chromium: await tab.get('data:text/html,<p>hi</p>'); await tab.evaluate("setTimeout(()=>alert('x'),200)"); await asyncio.sleep(1); then asyncio.wait({asyncio.ensure_future(tab.select('#nope', timeout=2))}, timeout=15) and assert the task is done with TimeoutError. Or unit-style, like the #291 test: monkeypatch tab.query_selector / find_element_by_text to `await asyncio.Event().wait()` and assert select(timeout=1) raises within an outer 5 s wait_for. Fix: wrap the polling loop in asyncio.wait_for(…, timeout).

### A5.1: select/find/find_all/select_all/xpath ignore their timeout when a CDP reply never comes (open alert() or busy renderer): hang forever
- where (may drift): zendriver/core/tab.py:Tab.select / Tab.find / Tab.xpath (also find_all, select_all):345
- finder severity: hang
- claim: A page opens a JS dialog (setTimeout(()=>alert('x'),100)) or runs a long synchronous script. Then `await tab.select('#missing', timeout=2)` never returns. The loop checks `loop.time() - start_time > timeout` only between attempts, and each attempt awaits `self.send(cdp.dom.get_document(...))` (query_selector line 638, find_elements_by_text line 697) with no deadline. The renderer main thread does not answer DOM.getDocument while the dialog is open. `tab.find('x', timeout=2)` hangs the same way. `tab.xpath('//x', timeout=1)`, whose docstring says 'It will not raise', hangs on `await self.send(cdp.dom.enable(), True)` (line 473). find_all and select_all use the same loop structure, and include_frames adds unbounded per-frame sends.
- finder evidence (unverified): Probe on real headless Chromium, both with alert() and with a 60s busy loop: '[select missing timeout=2] STILL RUNNING after 15.0s' with the task stuck at tab.py:351 `item = await self.query_selector(selector)` waiting on Transaction DOM.getDocument (pending). find(timeout=2) was stuck at tab.py:308 on DOM.getDocument. xpath(timeout=1) was stuck at tab.py:473 on DOM.enable.
- finder repro idea: browser.get(page); await tab.evaluate("setTimeout(()=>alert('blocking'),100)", await_promise=False); await asyncio.sleep(0.5); await asyncio.wait_for(tab.select('#missing', timeout=2), 15) raises the outer TimeoutError at 15s, never the inner one at 2s. Probe: scratchpad/detect-A5/probe3.py with the arg alert or busy.

### B13.2: Tab.wait_for / tab(...) / Tab.xpath hang forever past their timeout when the renderer stops answering
- where (may drift): zendriver/core/tab.py:Tab.wait_for (also Tab.__call__, Tab.xpath):1308
- finder severity: hang
- claim: await tab.wait_for(selector='#x', timeout=2), or await tab(selector='#x', timeout=2), on a page blocked by alert() or a busy loop. The first query_selector before the while loop, and each one inside it, awaits DOM.getDocument with no bound; `loop.time() - start_time < timeout` is only checked after it returns, so the documented 'block for a maximum of <timeout> seconds, then TimeoutError' never happens. Tab.xpath(xpath, timeout=2.5), documented to return [] after the timeout and 'never raise', likewise hangs on its per-pass `await self.send(cdp.dom.enable(), True)` and find_all(timeout=0).
- finder evidence (unverified): probe_hang.py (busy mode): `busy wait_for: STILL PENDING after 15.0s (timeout=2)` stuck at tab.py:1308 on Transaction DOM.getDocument; `busy call: STILL PENDING after 15.0s` at tab.py:1966; `busy xpath: STILL PENDING after 15.0s (timeout=2)` at tab.py:473 on Transaction DOM.enable.
- finder repro idea: Same harness as for select: block the renderer with setTimeout(()=>alert('x')) and assert tab.wait_for(selector='#nope', timeout=2) raises TimeoutError, and tab.xpath('//nope', timeout=2) returns [], both within about 3 s under an outer 15 s safety net.

### A6.5: Tab.wait_for's timeout does not bound query_selector/find_element_by_text: it hangs forever while a JS dialog is open and overshoots on a busy page
- where (may drift): zendriver/core/tab.py:Tab.wait_for:1308
- finder severity: hang
- claim: A page shows alert() (or any JS dialog) and the caller does await tab.wait_for(selector='#x', timeout=2) or tab.wait_for(text='x', timeout=2). The timeout is only checked in the while condition between iterations. The first query_selector call sends DOM.getDocument, which Chrome does not answer while the dialog is open, so wait_for never returns and never raises TimeoutError. The documented contract is 'it will block for a maximum of <timeout> seconds, after which a TimeoutError will be raised'. On a page whose main thread is busy for 12s, wait_for(timeout=2) returns only after about 11.3s. wait_for_ready_state was fixed for exactly this in #291 (CHANGELOG line 27), but wait_for was not.
- finder evidence (unverified): probe5.py: '[alert wait_for selector] STILL RUNNING after 8s; stack: Tab.wait_for() running at tab.py:1308 wait_for=<Transaction method: DOM.getDocument status: pending>'. probe4.py: '[alert: wait_for(selector='#nope', timeout=2)] EXC in 15.00s -> TimeoutError: ' (the empty message is the outer safety net, not wait_for's own message) and '[busy: wait_for(selector='#nope', timeout=2)] EXC in 11.31s'.
- finder repro idea: Page <script>setTimeout(()=>alert('hi'),300)</script>; await asyncio.sleep(1); await asyncio.wait_for(tab.wait_for(selector='#nope', timeout=2), 8) -> outer wait_for cancels it after 8s, still stuck in DOM.getDocument. Fix: wrap the whole polling loop in asyncio.wait_for(..., timeout) as wait_for_ready_state does.

### B13.3: verify_cf / cf_is_interactive_challenge_present timeout does not bound their CDP calls, so they hang on a blocked page instead of raising or returning False
- where (may drift): zendriver/core/cloudflare.py:cf_wait_for_interactive_challenge (reached from Tab.verify_cf and cf_is_interactive_challenge_present):93
- finder severity: hang
- claim: await tab.verify_cf(timeout=15), documented as 'total time for finding and clicking is governed by timeout ... Raises TimeoutError', or await cf_is_interactive_challenge_present(tab, timeout=5). Each pass of cf_wait_for_interactive_challenge awaits cf_find_interactive_challenge -> tab.send(DOM.getDocument), plus get_html() for each shadow root, all with no bound. `while loop.time() - start_time < timeout` is only checked after they return. A challenge page that shows a dialog or spins its main thread hangs verify_cf forever. The later click loop has the same shape (check_input -> query_selector, mouse_click). Each step is unbounded, and the timeout is only checked once per iteration, after the click_delay sleep.
- finder evidence (unverified): probe_hang.py: `alert cf: STILL PENDING after 15.0s (timeout=2)` and `busy cf: STILL PENDING after 15.0s` (stack: cf_is_interactive_challenge_present at cloudflare.py:120, waiting on Transaction DOM.getDocument). `busy verify_cf: STILL PENDING after 15.0s (timeout=2)` at tab.py:1666 on DOM.getDocument.
- finder repro idea: Headless chromium: block the renderer with setTimeout(()=>alert('x')), then assert cf_is_interactive_challenge_present(tab, timeout=2) returns False, and tab.verify_cf(timeout=2) raises TimeoutError, within about 3 s under an outer 15 s safety net.

### A11.4: verify_cf timeout is overrun by up to click_delay (and by any slow CDP call) although the docstring says it governs the total time
- where (may drift): zendriver/core/cloudflare.py:verify_cf:254
- finder severity: wrong-result
- claim: The deadline is checked only at the top of the click loop (line 254). Each iteration then does mouse_click, an unbounded `asyncio.sleep(click_delay)` (line 260), and check_input (getDocument + resolveNode + another getDocument), none of which is bounded by the remaining time. So tab.verify_cf(timeout=1, click_delay=4) on an unsolvable challenge takes about 4s. With the defaults (timeout=15, click_delay=5), a challenge found near the deadline runs about 20s. cf_wait_for_interactive_challenge has the same issue: every full DOM scan (getDocument plus one getOuterHTML per shadow root) runs to completion past the deadline, so cf_is_interactive_challenge_present(tab, timeout=5) can take far longer than 5s, and forever if a CDP reply never comes. This is a different site from the known Tab.get/Browser.get issue.
- finder evidence (unverified): Scratch cf_timeout_probe.py: 'timeout=1 click_delay=4: TimeoutError after 4.00s, clicks=1' (4x the requested timeout) and 'timeout=2 click_delay=0.1: TimeoutError after 2.01s, clicks=20'.
- finder repro idea: Monkeypatch cf_wait_for_interactive_challenge to return a fake iframe, and fake tab.send, query_selector (an input that never gets a value) and mouse_click. Time verify_cf(timeout=1, click_delay=4).

### A5.7: xpath(timeout=0) (or any timeout <= 0) never runs the query and always returns []; otherwise it busy-loops with no sleep
- where (may drift): zendriver/core/tab.py:Tab.xpath:471
- finder severity: wrong-result
- claim: `await tab.xpath("//p[@id='topp']", timeout=0)` returns [] although the element exists. The loop condition `(loop.time() - start_time) < timeout and len(items) == 0` is checked before the first attempt, so with timeout <= 0 the body never runs. The docstring says retries happen only 'if not immediately found', implying at least one attempt. With a positive timeout the loop has no sleep between attempts (find_all(timeout=0) raises immediately, the exception is caught, and the loop spins). One miss with timeout=0.5 issued 1254 Tab.send calls, each attempt including a full-tree DOM.getDocument(depth=-1, pierce=True).
- finder evidence (unverified): Probe: "[xpath default] -> [<p id=\"topp\">...]", '[xpath timeout=0] -> []', '[xpath timeout=0.001] -> [<p id="topp">...]'. probe6: "xpath miss result [] sends in 0.5s: 1254".
- finder repro idea: assert await tab.xpath("//li[@aria-label='Apples (42)']", timeout=0) fails on groceries.html. Probes: scratchpad/detect-A5/probe1.py and probe6.py (send counter).
