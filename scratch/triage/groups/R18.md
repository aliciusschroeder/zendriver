# Group R18 (prep-flags-race)

queue: report  |  triage severity: wrong-result  |  triage fix kind: local

## Claim
_prepare_expert/_prepare_headless check-then-await their done flags: concurrent first sends inject the expert attachShadow override twice (shadow DOM recursion -> stack overflow); a session detached during prepare leaves _prep_headless_done set so the HeadlessChrome UA leaks after reattach

## Files
zendriver/core/connection.py (_prepare_expert, _prepare_headless, send)

## Triage fix strategy (a hypothesis, not a requirement)
Serialise the one-time preparation (lock or in-progress future) and do not mark done when the session went away.

## Triage test approach
Fake peer counting addScriptToEvaluateOnNewDocument under asyncio.gather; real Chromium for the recursion.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### B14.2: Expert mode: concurrent first sends inject the attachShadow override twice, so shadow DOM recurses until the stack overflows
- where (may drift): zendriver/core/connection.py:Connection._prepare_expert:790
- finder severity: wrong-result
- claim: browser = await zd.start(headless=True, expert=True); tab = await browser.get(url, new_tab=True) (no send has gone to the new tab yet); then await tab.set_local_storage({'a':'1','b':'2'}). Tab.set_local_storage uses asyncio.gather internally (tab.py:1898), and asyncio.gather(tab.evaluate('1'), tab.evaluate('2')) behaves the same. Each concurrent send() sees _prep_expert_done unset and awaits _send_oneshot(Page.addScriptToEvaluateOnNewDocument(...)) before any of them sets the flag, so the script is registered twice. On the next document, the second copy does `_attachShadow = attachShadow` (which is now wrapper 1), and wrapper 1 calls this._attachShadow, which is itself. Every page that calls element.attachShadow() then throws 'RangeError: Maximum call stack size exceeded', which breaks web components and many sites. _prepare_headless has the same unguarded check-then-await, so it also sends the UA override twice; that copy is harmless.
- finder evidence (unverified): probe_expert2.py against real Chromium: mode=seq gives title='OK'; mode=gather gives title='ERR:RangeError:Maximum call stack size exceeded'; mode=localstorage gives title='ERR:RangeError:Maximum call stack size exceeded'. The flag is read at connection.py:790 and set at :805, after two awaits, with no lock.
- finder repro idea: Serve a page whose script does try{div.attachShadow({mode:'closed'});document.title='OK'}catch(e){document.title='ERR:'+e}. Start with expert=True, open it with new_tab=True, then gather two evaluates (or call set_local_storage with two items). Reload and check document.title.

### B14.6: A session detached during send()'s awaits leaves _prep_headless_done set (HeadlessChrome UA leaks after reattach) and starts a zombie Listener
- where (may drift): zendriver/core/connection.py:Connection._prepare_headless / Connection.send:787
- finder severity: wrong-result
- claim: Headless browser, first send on a tab: await tab.evaluate('1'). send() -> aopen() attaches the session -> _prepare_headless awaits _send_oneshot(Network.setUserAgentOverride). Meanwhile the session is detached: another task calls tab.aclose(), or the target detaches. _detach_session pops _prep_headless_done and fails the pending oneshot. _send_oneshot swallows that ProtocolException, and _prepare_headless then unconditionally runs setattr(self, '_prep_headless_done', True) for a session that no longer exists. On the next send the tab reattaches to a new session, and _prepare_headless skips the override, so navigator.userAgent and the UA header contain 'HeadlessChrome'. Back in the first send, line 642 `if not self.listener or not self.listener.running: self.listener = Listener(self)` sees the cancelled listener is done and starts a new Listener on the detached connection (websocket None, _inbox None). That listener dies at once with an unobserved ValueError('no websocket connection'). The tx already added to self.mapper at line 648 is then abandoned by the raise at line 658, and later surfaces as 'Transaction exception was never retrieved'. _prepare_expert (line 805) has the same flag-after-await pattern.
- finder evidence (unverified): probe_headless_flag.py: race=0 printed a UA without Headless. race=1 printed 'first send: ProtocolException: target session was detached | _prep_headless_done after detach: True', then 'UA after reattach: ... HeadlessChrome/141.0.0.0 ...', plus 'Transaction exception was never retrieved' and 'Task exception ... Listener.listener_loop ... ValueError(no websocket connection)'. probe_zombie.py (tab closed during its first send): 10/10 iterations created a Listener on a detached connection at connection.py:643 in send, with 9 unretrieved ValueError task exceptions. Medium confidence because the trigger needs a detach while the first send is in flight.
- finder repro idea: Real Chromium, headless. Create a target, then gather(tab.evaluate('1'), closer()), where closer waits until tab.session_id is set and then awaits tab.aclose(). Then check tab.evaluate('navigator.userAgent') for 'HeadlessChrome'. For the zombie listener, record Listener.__init__ calls made while conn.websocket is None.
