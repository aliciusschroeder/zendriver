# Group Q3 (stop-cleanup)

queue: fix  |  triage severity: hang  |  triage fix kind: local

## Claim
Browser.stop()/_stop()/_atexit_cleanup cleanup is not robust: unbounded CDP awaits before terminate/kill, exceptions from Tab.aclose abort cleanup, concurrent stop() crashes, and the atexit path fails at asyncio.to_thread after the executor is shut down

## Files
zendriver/core/browser.py (Browser.stop, _stop, _atexit_cleanup), possibly zendriver/core/connection.py (aclose)

## Triage fix strategy (a hypothesis, not a requirement)
Bound the per-target aclose() and Browser.close sends with a short timeout and catch Exception so later cleanup always runs; snapshot self._process into a local so concurrent stop() calls cannot see None mid-way; replace `await asyncio.to_thread(self._process.wait)` with a poll loop or a fallback that works after the default executor is shut down, so the temp profile is removed on the atexit path.

## Triage test approach
Browser-free where possible: fake connection that never answers Target.detachFromTarget -> stop() returns within a bound and terminates the process; aclose raising ConnectionClosedError -> _stop still cleans up; asyncio.run(main) that never calls stop -> temp profile removed. Real Chromium only where needed.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### B13.5: Browser.stop() waits on unbounded CDP replies before it kills the process, so an unresponsive browser makes stop() hang forever and leaks the process
- where (may drift): zendriver/core/browser.py:Browser._stop:879
- finder severity: hang
- claim: When the browser process stops answering (e.g. the stderr-pipe deadlock above, a wedged or suspended Chrome, a remote browser that hangs), await browser.stop() never returns. _stop first runs `await target.aclose()` for every target. For each attached flat session that does `await browser_connection.send(Target.detachFromTarget)` with no timeout. It then does `await self.connection.send(cdp.browser.close())`, also with no timeout. Only after both does it reach the terminate -> 3 s -> kill fallback, which is the code meant for an unresponsive browser. If the caller bounds stop() with asyncio.wait_for, the process is never terminated and the temp profile is never removed. stop() already called asyncio_atexit.unregister(self._atexit_cleanup) and discarded the instance from the registry before awaiting _stop(), so nothing cleans up at exit either. Tab.close() has the same shape: its `await self.browser.connection.send(close_target)` sits outside the `asyncio.wait_for(future, 10)` that its ':raises asyncio.TimeoutError:' docstring promises.
- finder evidence (unverified): probe_stop.py: `stop() STILL PENDING after 20.0s; process alive: True`, stack `Browser.stop() running at browser.py:872 wait_for=<Transaction method: Target.detachFromTarget status: pending>`. The pipe-deadlock probe also showed `stop failed TimeoutError` with an outer 15 s wait_for. The websocket ping_timeout is 900 s, so the connection would not even fail on its own for over 15 minutes.
- finder repro idea: browser = await zd.start(headless=True); tab = await browser.get(url); await tab.evaluate('1') to attach a session; os.kill(pid, SIGSTOP); then assert asyncio.wait_for(browser.stop(), 20) completes and the process is gone. Fix: bound the detach/Browser.close steps (e.g. wait_for of a few seconds each, or overall) and always fall through to terminate/kill.

### A3.4: Browser.stop() hangs forever on an unresponsive browser and never reaches terminate()/kill()
- where (may drift): zendriver/core/browser.py:Browser._stop:879
- finder severity: hang
- claim: The Chrome process is wedged: frozen, stopped, or blocked writing to its full stderr pipe (see the pipe finding). `await browser.stop()` first runs `for target in self.targets: await target.aclose()`, and each aclose sends Target.detachFromTarget over the browser connection with no timeout. Next comes `await self.connection.send(cdp.browser.close())`, also with no timeout. The websocket stays open but no reply ever arrives, so stop() blocks forever. The terminate/kill block, which exists to handle a stubborn process, is never reached. The obvious workaround, `asyncio.wait_for(browser.stop(), t)`, makes things worse: stop() has already unregistered the atexit callback and removed the instance from the registry before awaiting _stop(), so after the timeout nothing will ever kill Chrome or remove the temp profile.
- finder evidence (unverified): probe_stop_hang.py printed 'stop() still running after 12s; stuck at: Stack for <Task pending ... coro=<Browser.stop() running at browser.py:872> wait_for=<Transaction method: Target.detachFromTarget status: pending>>' and 'process still alive: True'. probe_pipe2.py: `wait_for(b.stop(), 20)` timed out for a browser blocked on stderr.
- finder repro idea: `b = await zd.start(headless=True); await b.get('about:blank'); os.kill(b._process_pid, SIGSTOP); t = asyncio.create_task(b.stop()); await asyncio.wait({t}, timeout=12)`. t is still pending and t.print_stack() shows it waiting on the Target.detachFromTarget Transaction.

### B15.3: Browser.stop() hangs forever on an unresponsive browser, because the CDP detach/close steps have no timeout and the terminate/kill fallback comes after them
- where (may drift): zendriver/core/browser.py:Browser._stop:879
- finder severity: hang
- claim: The Chrome browser process stops responding (hung or suspended) and the user calls `await browser.stop()`. _stop first awaits `target.aclose()` for every target. For attached tabs that sends Target.detachFromTarget through the browser connection and awaits the reply with no timeout. Then it awaits `self.connection.send(cdp.browser.close())`, also with no timeout. The 3s terminate -> kill fallback is never reached, so stop() never returns. If the caller wraps it in wait_for, the cancellation leaves the process running and the profile undeleted.

Probe: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-B15/probe_stop_hang.py, probe_stop_hang2.py

### B16.2: Browser.stop() waits for CDP replies with no timeout before terminate()/kill(), and drops the atexit hook first
- where (may drift): zendriver/core/browser.py:Browser._stop:878
- finder severity: hang
- claim: Start a browser and use a tab, which attaches a flat session. The Chrome process then stops answering: it is hung, SIGSTOPped, or blocked on the full stderr pipe. Calling await browser.stop() first runs asyncio_atexit.unregister (line 870). _stop then awaits target.aclose() for each target (each sends Target.detachFromTarget through the browser connection) and connection.send(Browser.close), and none of these awaits has a timeout. stop() hangs forever and never reaches self._process.terminate()/kill(). If the caller wraps stop() in wait_for, the cancel leaves the process running and the temp profile in place, and because the atexit hook is already gone, nothing cleans up later.
- finder evidence (unverified): Probe p8_stop_hang.py: 'stop done after 8s? False | process terminated? None'. task.print_stack() showed it waiting on a Transaction with method Target.detachFromTarget, status pending.
- finder repro idea: os.kill(browser._process_pid, SIGSTOP) after tab.evaluate('1'), run asyncio.create_task(browser.stop()), and check after 8 s whether the task is done and whether the process was terminated.

### A1.2: Browser.stop() right after Chrome dies raises ConnectionClosedError from Tab.aclose and leaks the process and temp profile
- where (may drift): zendriver/core/connection.py:Connection.aclose:523
- finder severity: crash
- claim: browser = await zd.start(); tab = await browser.get(...); await tab.evaluate('1') (the tab now has a flat session). Chrome crashes or is killed (OOM, watchdog, browser._process.kill()), and then await browser.stop() runs before the listener has seen the close. Browser._stop calls target.aclose() for every tab. The session branch of aclose sends Target.detachFromTarget and catches only ProtocolException. The listener's ConnectionClosed branch fails pending transactions with the ConnectionClosed instance itself (_fail_pending_transactions(e)), and _send_transaction can also raise ConnectionClosed directly. Either way ConnectionClosedError escapes aclose and aborts Browser._stop before the browser.close send (whose broad except would have handled it), before proxy forwarders are closed, before the process is terminated/reaped (browser._process stays set) and before _cleanup_temporary_profile. stop() has already unregistered the atexit cleanup, so the temp profile dir is never removed. A second problem on the same line: the detach round trip has no timeout. With a frozen Chrome (SIGSTOP), stop() hangs inside Tab.aclose (stack: stop -> _stop:879 -> aclose:517 -> send:662) and never reaches the terminate/kill fallback. Before #280, tab.aclose only closed a per-tab websocket.
- finder evidence (unverified): probe_stop_after_crash.py on real headless Chromium printed 'stop RAISED ConnectionClosedError no close frame received or sent | _process still set: True | profile dir still exists: True' in 5 of 5 runs. Traceback: browser.py stop 872 -> _stop 879 -> connection.py aclose 517 -> send 662 -> (exception originated in) listener_loop 925. With a 0.5s sleep between kill and stop, stop succeeds because the listener had already detached the sessions. probe_stop_frozen.py (SIGSTOP) showed stop() still pending after 5s, awaiting inside aclose:517.
- finder repro idea: browser = await zd.start(headless=True); tab = await browser.get('about:blank'); await tab.evaluate('1'); browser._process.kill(); await browser.stop() raises ConnectionClosedError; then check os.path.exists(browser.config.user_data_dir).

### A3.11: Concurrent Browser.stop() calls race in _stop and raise AttributeError: 'NoneType' object has no attribute 'poll'
- where (may drift): zendriver/core/browser.py:Browser._stop:901
- finder severity: crash
- claim: Call stop() from two tasks at once, for example a signal-handler task plus a finally block, or `await asyncio.gather(b.stop(), b.stop())`. Both enter _stop past the `if not self.connection and not self._process` guard and both reach the terminate/poll loop. The first one to see the exit sets `self._process = None` (line 916). The other wakes from `asyncio.sleep(0.25)` and runs `self._process.poll()` or `asyncio.to_thread(self._process.wait)` on None. Its stop() raises AttributeError, and its profile cleanup is skipped.
- finder evidence (unverified): probe_concurrent_stop.py over 7 runs: 2 runs printed "results: ['AttributeError(\"'NoneType' object has no attribute 'poll'\")', 'None']" and the other 5 printed ['None', 'None'].
- finder repro idea: `b = await zd.start(headless=True); await b.get('about:blank'); res = await asyncio.gather(b.stop(), b.stop(), return_exceptions=True)`. Repeat; some runs return an AttributeError.

### A3.1: atexit cleanup always fails under asyncio.run and leaks the temp profile (RuntimeError: Executor shutdown has been called)
- where (may drift): zendriver/core/browser.py:Browser._atexit_cleanup -> Browser._stop:909
- finder severity: leak
- claim: Call `asyncio.run(main())` where main does `b = await zd.start()` (or uses the documented `async with await zd.start() as browser:` from examples/wait_for_page.py) and never calls `b.stop()`. asyncio.run shuts down the default executor (`shutdown_default_executor()`) and only then calls loop.close(). asyncio_atexit runs `_atexit_cleanup` inside that patched loop.close(). `_atexit_cleanup` calls `_stop()`, which terminates Chrome and then runs `await asyncio.to_thread(self._process.wait)`. That call raises RuntimeError('Executor shutdown has been called'). Only ProcessLookupError is caught, so `_cleanup_temporary_profile()` never runs, either inside `_stop` or after it in `_atexit_cleanup`. The /tmp/uc_* profile is left behind on every run, and asyncio_atexit prints 'Unhandled exception in asyncio atexit callback ...' to stderr. Ctrl+C during asyncio.run takes the same path.
- finder evidence (unverified): Probe probe_atexit.py printed 'Unhandled exception in asyncio atexit callback <bound method Browser._atexit_cleanup ...>: Executor shutdown has been called' and then 'after asyncio.run: temp profile exists: True'. probe_atexit_tb.py got the traceback: to_thread -> run_in_executor -> _check_default_executor -> RuntimeError. asyncio_atexit._asyncio_atexit_close runs the callbacks in loop.close(), and Runner.close calls shutdown_default_executor before loop.close().
- finder repro idea: In a script: `async def main(): b = await zd.start(headless=True); d['udd'] = b.config.user_data_dir`, then `asyncio.run(main())`, then assert not os.path.exists(d['udd']). It fails, and stderr shows the RuntimeError. A traceback from a Browser subclass that wraps _atexit_cleanup points to asyncio/threads.py to_thread -> run_in_executor -> _check_default_executor.

### B16.3: atexit cleanup always crashes at asyncio.to_thread(process.wait), leaking the temp profile of every browser not stopped explicitly
- where (may drift): zendriver/core/browser.py:Browser._stop (via _atexit_cleanup):909
- finder severity: leak
- claim: asyncio.run(main()) where main does `b = await zd.start(); await b.get(...)` and never calls stop(). This is the documented fallback that Browser.create registers through asyncio_atexit. asyncio.run shuts down the default executor before loop.close(), and asyncio_atexit callbacks run inside loop.close(). _atexit_cleanup calls _stop, which terminates the process and then calls `await asyncio.to_thread(self._process.wait)`, which raises RuntimeError('Executor shutdown has been called'). _cleanup_temporary_profile never runs, so a /tmp/uc_* Chrome profile (often tens of MB) is left behind on every run. The same failure hits the _cleanup_temporary_profile call in _atexit_cleanup, because _stop raised first.
- finder evidence (unverified): Probe p12_atexit.py printed 'Unhandled exception in asyncio atexit callback <bound method Browser._atexit_cleanup ...>: Executor shutdown has been called' and 'temp profile /tmp/uc_g8gnsv0r still exists'. The shared /tmp held more than 40 leaked uc_* directories from this session's probes.
- finder repro idea: In a script, start a browser, record b.config.user_data_dir, return without stop(), then check after the interpreter exits whether the directory still exists.
