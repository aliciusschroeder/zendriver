# Group R46 (element-design)

queue: design  |  triage severity: wrong-result  |  triage fix kind: design

## Claim
Element/Tab design-level: save_to_dom serialises via an unescaped __repr__ (corrupts DOM); DOM.resolveNode remote objects never released; Element/Tab define __eq__ without __hash__ (unhashable); intercept() cannot be nested; evaluate returns None for unserializable values (NaN/Infinity/-0/BigInt); `async with await zd.start() as browser` never stops the browser

zendriver/core/element.py, zendriver/core/tab.py, zendriver/core/intercept.py

## Triage fix strategy (a hypothesis, not a requirement)
Design/API decisions.

### A8.10: save_to_dom() corrupts the DOM: comments become visible text, escaped text becomes live markup, quotes in attribute values raise
- where (may drift): zendriver/core/element.py:save_to_dom / __repr__:276
- finder severity: wrong-result
- claim: `el.attrs['data-x']='1'; await el.save_to_dom()` sends str(self) (= __repr__) to DOM.setOuterHTML. __repr__ does not escape text or attribute values and renders non-element nodes as tags. (a) <div><!-- c --><i>it</i></div> becomes literal visible text '<#comment >' plus an empty comment. (b) <p>&lt;b&gt;not bold&lt;/b&gt;</p> becomes a real <b> element. (c) title='say "hi"' produces title="say "hi"" and Chrome rejects it with ProtocolException InvalidCharacterError.
- finder evidence (unverified): probe1.py: cmt outerHTML '<div id="cmt" data-x="1">&lt;#comment &gt;<!--#comment--><i>it</i></div>', innerText '<#comment >it'; esc outerHTML '<p id="esc" data-x="1"><b>not bold</b></p>'; q: 'ProtocolException: InvalidCharacterError \'hi""\' is not a valid attribute name ... outerHTML: <div id="q" title="say "hi"" data-x="1">q</div>'.
- finder repro idea: page1.html elements #cmt, #esc and #q: set any attr, call save_to_dom(), then read outerHTML/innerText.

### A8.13: Remote object handles from DOM.resolveNode are never released (unbounded growth per apply/click/update)
- where (may drift): zendriver/core/element.py:apply / click / update / get_position:495
- finder severity: leak
- claim: Every apply(), click(), update(), select_option(), send_keys(), clear_input() and so on calls DOM.resolveNode without an objectGroup and never calls Runtime.releaseObject, and nothing in zendriver/core ever releases objects. Each call adds a new entry to the page's inspector object table, and the entry lives until the execution context is destroyed. A long-running automation that polls an element on a single-page app grows that table without bound.
- finder evidence (unverified): probe6.py: '3000 apply() calls in 1.8s -> 3000 distinct object ids'; 'first object id still alive after 3000 calls: inp None', so the first handle is still valid. grep for release_object/object_group in zendriver/core finds nothing.
- finder repro idea: probe6.py: 3000 inp.apply() calls, then count distinct object_ids and call Runtime.callFunctionOn on the very first id.

### A8.17: Element is unhashable because __eq__ is defined without __hash__
- where (may drift): zendriver/core/element.py:__eq__:1127
- finder severity: crash
- claim: Deduplicating results: `set(await tab.select_all('a'))`, or using elements as dict keys. Defining __eq__ in the class body sets __hash__ = None, so hash(el) raises TypeError: unhashable type: 'Element', although __eq__ already gives a natural key (backend_node_id).
- finder evidence (unverified): probe5.py and probe1.py: "hash: TypeError unhashable type: 'Element'".
- finder repro idea: probe5.py: hash(Element(node, FakeTab())).

### A7.11: Tab defines __eq__ without __hash__, so Tab objects are unhashable
- where (may drift): zendriver/core/tab.py:Tab.__eq__:1968
- finder severity: crash
- claim: Defining __eq__ in Tab sets Tab.__hash__ = None (Connection, the parent class, is hashable). `set(browser.tabs)`, `{tab: result}`, a WeakKeyDictionary, or an lru_cache keyed on a tab all raise `TypeError: unhashable type: 'Tab'`. __eq__ also compares the whole mutable TargetInfo snapshot (url, title, attached...) rather than target_id, so a hash built on it could not be stable anyway. The natural fix is __eq__/__hash__ based on target_id.
- finder evidence (unverified): Probe1: `hash(tab) raised TypeError unhashable type: 'Tab'`. grep shows no __hash__ anywhere in zendriver/core.
- finder repro idea: `hash(browser.main_tab)` or `set(browser.tabs)`

### A10.2: tab.intercept() cannot be nested or combined with other Fetch users: inner enable replaces the outer patterns, the outer handler takes the inner request, and the inner teardown makes Fetch re-enable with no patterns, pausing every request
- where (may drift): zendriver/core/intercept.py:BaseFetchInterception._setup / _teardown / _response_handler:79
- finder severity: hang
- claim: (1) `async with tab.intercept('*a.json*', REQUEST, XHR) as a: async with tab.intercept('*b.json*', REQUEST, XHR) as b: await tab.get(page_fetching_a_and_b)`. The inner Fetch.enable([b]) replaces the tab's pattern list, so a.json is never paused. _response_handler accepts any Fetch.requestPaused without checking its own pattern, so both a and b resolve with b.json. `await a.request` returns b.json, `a.continue_request()` continues b's request, and `b.continue_request()` raises ProtocolException. (2) The inner block exits before the outer one has matched: _teardown sends Fetch.disable, which turns off interception for the whole tab and removes fetch from manually_enabled_domains. The outer RequestPaused handler is still registered, so the next tab.send() goes through Connection._register_handlers, which sends `fetch.enable()` with no patterns. Every request, including the document, now pauses. `tab.get()` hangs, the outer interception resolves with the page document instead of a.json, and the page's XHRs never complete. The same happens when a user-installed RequestPaused handler with its own Fetch.enable coexists with tab.intercept().
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_intercept.py printed: `outer a.request: http://127.0.0.1:41793/b.json`, `b.continue_request: ProtocolException: Invalid state for continueInterceptedRequest`. Scenario 2 printed `fetch in manual domains: False handlers: 1`, `tab.get -> TIMEOUT` (8s), `outer a.request: http://127.0.0.1:41793/page2`, `window.__a/__b inside outer: [None, None]`.
- finder repro idea: Local HTTP server with a page that calls fetch('/a.json') and fetch('/b.json'). Nest two intercepts with ResourceType.XHR and print a.request.url. Separately, exit the inner block first, then call `tab.get` inside the outer block with a timeout.

### A6.9: evaluate() returns None for Infinity, -Infinity, NaN, -0 and BigInt results with the default return_by_value=True
- where (may drift): zendriver/core/tab.py:Tab.evaluate:873
- finder severity: wrong-result
- claim: await tab.evaluate('1/0'), evaluate('Math.max()') (-Infinity), evaluate('NaN'), evaluate('-0') and evaluate('2n**64n') all return None. CDP puts these values in RemoteObject.unserializable_value ('Infinity', 'NaN', '-0', '18446744073709551616n'), and evaluate only reads remote_object.value. The caller cannot tell the result from undefined or null, and a numeric result such as an empty Math.max/min comes back as None. #203 fixed falsy values (0, [], null) but not these.
- finder evidence (unverified): probe1.py: '[evaluate(1/0)] OK -> None', '[evaluate(NaN)] OK -> None', '[evaluate(-0)] OK -> None', '[evaluate(10n)] OK -> None'. With return_by_value=False the same expressions give 'NaN' and '10', so the value is available but evaluate drops it on the by-value path.
- finder repro idea: assert await tab.evaluate('1/0') == float('inf'); assert await tab.evaluate('10n') == 10 -> both fail (None). Fix: when value is None and unserializable_value is set, decode it to float('inf'), float('-inf'), float('nan'), -0.0 or int(x[:-1]).

### B16.10: `async with await zd.start() as browser:` never stops the browser
- where (may drift): zendriver/core/browser.py:Browser.__aexit__:837
- finder severity: leak
- claim: examples/wait_for_page.py shows `async with await zd.start() as browser:`. Browser.__aexit__ only re-raises exceptions; it never calls stop(). After the block the Chrome process, websocket, proxy forwarders and temp profile stay alive until the event loop closes, and the atexit path then leaks the profile (see the atexit finding). A loop that opens one browser per job with `async with` piles up Chrome processes. Connection.__aexit__ (used by `async with tab`) closes only the websocket.
- finder evidence (unverified): Probe p5_aexit.py: 'after async with: stopped? False pid 11844'.
- finder repro idea: async with await zd.start(headless=True) as b: pass; then print(b.stopped, b._process_pid).
