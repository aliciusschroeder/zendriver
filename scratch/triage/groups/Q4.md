# Group Q4 (start-cleanup)

queue: fix  |  triage severity: leak  |  triage fix kind: local

## Claim
Cancelling or failing Browser.start()/zd.start() after Chrome is spawned orphans the Chrome process, its temp profile and the registry entry

## Files
zendriver/core/browser.py (Browser.start, Browser.create)

## Triage fix strategy (a hypothesis, not a requirement)
Wrap the post-spawn part of start() so any exception (including CancelledError) stops/kills the spawned process, removes the temp profile and unregisters the instance, then re-raises.

## Triage test approach
asyncio.wait_for(zd.start(...), small positive timeout) -> afterwards the spawned pid is gone, the temp profile is removed and get_registered_instances() no longer has it. Needs real Chromium (or a fake executable that listens).

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A3.3: Cancelling or failing Browser.start after Chrome is spawned orphans the Chrome process, its temp profile and the registry entry
- where (may drift): zendriver/core/browser.py:Browser.start / Browser.create:572
- finder severity: leak
- claim: `await asyncio.wait_for(zd.start(), 2)` times out on a slow machine. The same happens with Ctrl+C during startup (asyncio.run cancels main) or task.cancel() on shutdown. start() has already spawned Chrome at util._start_process and added self to util.get_registered_instances(). The CancelledError, or any exception after the spawn (from set_discover_targets, update_targets or _read_headless_user_agent), leaves start() with no try/finally. Browser.create registers asyncio_atexit only after start() returns, so no atexit cleanup exists, and the caller never gets the instance to call stop() on. The Chrome process keeps running after the Python interpreter exits (reparented to pid 1). The /tmp/uc_* profile is never removed. The registry set holds the Browser forever.
- finder evidence (unverified): probe_cancel_start.py with timeouts 0.05 and 0.15: 'start timed out', 'registered instances: 1', 'pid 23314 alive True info False connection None', 'new temp profiles left: {/tmp/uc_jqua_ubs}', 'pid 23314 running after asyncio.run: running'. After the script exited, `ps` showed pids 23314 and 23411 with ppid 1, still running. I killed them by hand.
- finder repro idea: Run `asyncio.run(...)` with `await asyncio.wait_for(zd.start(headless=True), 0.05)` inside try/except TimeoutError. Then check psutil.pid_exists() for the pid of the instance left in util.get_registered_instances(), and look for /tmp/uc_* dirs. Check again after the interpreter exits with `ps -o ppid`.

Run `await asyncio.wait_for(zd.start(headless=True), 0.05)`, let asyncio.run() return, then check p.poll() is None and that the user-data-dir still exists. ### B16.4: Cancelling or failing zd.start() after Chrome launches orphans the Chrome process and its temp profile (no atexit hook, Browser pinned in the registry)
- where (may drift): zendriver/core/browser.py:Browser.create / Browser.start:230
- finder severity: leak
- claim: await asyncio.wait_for(zd.start(headless=True), 0.25), as a user would do to bound startup on a slow machine. Browser.start has already called util._start_process and util.get_registered_instances().add(self). The cancel arrives during the connection-retry loop (or later, for example in set_discover_targets or _read_headless_user_agent). Browser.start has no try/except around this section; it calls stop() only on the `if not self.info` path. Browser.create registers asyncio_atexit only after start() returns. As a result the Chrome process keeps running after the Python process exits, the uc_* profile stays, and the registry set holds a strong reference to the Browser. Any exception after launch has the same effect, for example a ProtocolException from set_discover_targets.
- finder evidence (unverified): Probe p2_cancel.py: both starts timed out, and 'registered browser pid 11139 running? True dir exists? True' (same for 11228). After the Python process exited: '11139 alive .../chromium dir exists True' and '11228 alive'. I killed both by hand.
- finder repro idea: Call wait_for(zd.start(headless=True), 0.1) and wait_for(zd.start(headless=True), 0.25); after asyncio.run returns, check /proc/<pid> and the profile directories of util.get_registered_instances().
