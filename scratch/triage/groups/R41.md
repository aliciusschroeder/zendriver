### A4.1: Iterating a Browser with no page tabs, nested or after exhaustion crashes; parallel iterators share one cursor
- where (may drift): zendriver/core/browser.py:Browser.__iter__ / Browser.__next__ / Browser.__reversed__:853
- finder severity: crash
- claim: __iter__ returns self and keeps the cursor in self._i. (a) Close every tab, then call `list(browser)` or `next(iter(browser), None)`: there is no main_tab, so __iter__ never sets _i. __next__ then hits AttributeError, and its handler runs `del self._i`, which raises AttributeError again, so the caller gets AttributeError instead of StopIteration. (b) Only non-page targets remain (e.g. a service worker): main_tab returns that target, and `self.tabs.index(main_tab)` raises ValueError. (c) Nested loops `for a in browser: for b in browser:` crash with AttributeError because the inner loop deletes the shared _i. `zip(browser, browser)` silently returns [(A, B)] instead of [(A, A), (B, B)]. (d) Calling next() again on an exhausted iterator raises AttributeError, which breaks the rule that it must keep raising StopIteration. (e) __reversed__ returns a list, so `next(reversed(browser))` raises TypeError.
- finder evidence (unverified): Probe scratchpad/detect-A4/iter_probe.py printed: 'list(empty): AttributeError 'Browser' object has no attribute '_i''; 'only sw: ValueError <Tab [sw1] [service_worker]> is not in list'; 'nested: AttributeError'; 'zip: [(A, B)]'; 'after exhaustion: AttributeError'; 'next(reversed(b)): TypeError 'list' object is not an iterator'. With real Chromium (misc_probe.py), after closing all tabs: targets == [] and list(browser) raises AttributeError 'Browser' object has no attribute '_i'.
- finder repro idea: Inside asyncio.run, build `b = Browser(Config(browser_executable_path='/bin/true'))` and set b.targets by hand with b._create_tab(TargetInfo(...)). Then check list(b) with no targets, list(b) with only a service_worker target, the nested comprehension, zip(b, b), and next(it, None) after list(it). Alternatively start real Chromium, close all tabs, then call list(browser).

### A4.6: grant_all_permissions always fails with ProtocolException on current Chromium
- where (may drift): zendriver/core/browser.py:Browser.grant_all_permissions:717
- finder severity: crash
- claim: `await browser.grant_all_permissions()` sends every cdp.browser.PermissionType value except CAPTURED_SURFACE_CONTROL in a single Browser.grantPermissions call. Chrome rejects the whole call if any single type is unknown or cannot be granted without an origin. On Chromium 141 (Linux) the call fails with 'Unknown permission type: localNetwork', and no permission is granted. Granting each type alone showed that localNetwork and loopbackNetwork are unknown to this Chromium. handTracking, protectedMediaIdentifier, smartCard and webPrinting are rejected with "Permissions can't be granted in current context." Those four fail even on a Chrome that knows every type, so the method cannot succeed on Linux. The CDP enum was regenerated in April 2026 (#254) and added types that the single exclusion does not cover.
- finder evidence (unverified): Probe scratchpad/detect-A4/misc_probe.py printed 'grant_all_permissions: ProtocolException Unknown permission type: localNetwork command:Browser.grantPermissions'. perm_probe.py printed rejected: [('handTracking', "Permissions can't be granted in current context."), ('localNetwork', 'Unknown permission type'), ('loopbackNetwork', 'Unknown permission type'), ('protectedMediaIdentifier', ...can't be granted...), ('smartCard', ...), ('webPrinting', ...)] on Chromium 141.0.7390.37.
- finder repro idea: b = await zd.start(headless=True); await b.grant_all_permissions(). Then loop over cdp.browser.PermissionType, granting one at a time, to list which types are rejected.

### A4.7: tile_windows only ever uses about one third of the screen width
- where (may drift): zendriver/core/browser.py:Browser.tile_windows:749
- finder severity: wrong-result
- claim: `await browser.tile_windows()` with the default max_columns=0 sets req_cols = int(n * 19/6), about 3.17n columns, and req_rows = 1 for any n >= 1. Each window gets screen_width / (3.17n) of width, so the n windows together always fill about 1/3 of the screen: 1 window gets 639px of 1920, 2 windows get 319px each, and 4 windows get 159px each (narrower than Chrome's minimum window width). The rest of the screen stays empty, and windows never get a second row.
- finder evidence (unverified): Probe scratchpad/detect-A4/tile_probe.py printed: '1 windows -> [[0, 0, 639, 1080]] (total width used 639 of 1920)', '2 windows -> ... used 638 of 1920', '4 windows -> [[0,0,159,1080],...] used 636 of 1920'. The formula comes unchanged from upstream nodriver, so maintainers might call it intended, but it never tiles the screen.
- finder repro idea: Stub sys.modules['mss'] with a fake reporting one 1920x1080 monitor. Stub tab.get_window and tab.set_window_size on n fake tabs, then print the grid returned by browser.tile_windows(tabs) for n = 1, 2 and 4.

### A4.8: tile_windows raises ZeroDivisionError when there are no tabs, and leaks an mss instance (X display connection) on every call
- where (may drift): zendriver/core/browser.py:Browser.tile_windows:750
- finder severity: crash
- claim: (a) `await browser.tile_windows()` (or windows=[]) on a browser with no page tabs: num_windows=0, so req_cols = 0 or int(0) = 0, and `req_rows = int(num_windows / req_cols)` raises ZeroDivisionError instead of returning []. (b) Every call creates `m = mss.mss()` and never closes it. mss 10 has no __del__; on Linux, MSS.__init__ calls XOpenDisplay, which only close() releases. So each tile_windows call leaks an X display connection (a GDI device context on Windows).
- finder evidence (unverified): Probe scratchpad/detect-A4/tile_probe.py printed '0 windows: ZeroDivisionError division by zero' and 'mss instances opened: 4 closed: 0'. In site-packages/mss/linux.py line 316, XOpenDisplay is called in __init__ and XCloseDisplay only in close() (line 335); base.py has close() and __exit__ but no __del__.
- finder repro idea: Use the fake mss module from the previous repro, which records instances. Call tile_windows() with no tabs, then call it several times with tabs and count instances whose close() was never called.

### A12.6: CookieJar.save/load match the pattern against str(cookie.__dict__), so patterns hit field names and enum reprs and select every cookie
- where (may drift): zendriver/core/browser.py:CookieJar.save:1036
- finder severity: wrong-result
- claim: browser.cookies.save(file, pattern='session') to keep only cookies named like 'session_id'. The docstring says it includes cookies whose domain, key or value matches. The code runs re.finditer over str(cookie.__dict__), which contains the literal keys 'name', 'value', 'path', 'secure', 'session' and reprs such as <CookiePriority.MEDIUM: 'Medium'> and <CookieSourceScheme.SECURE: 'Secure'>. So 'session', 'secure', 'path', 'name', 'Medium' and similar patterns match every cookie, and all cookies are saved (or loaded by load(pattern=...)).
- finder evidence (unverified): Offline probe detect-A12/probe6.py on a cdp.network.Cookie printed str(__dict__) = "{'name': 'sid', 'value': 'abc', 'domain': 'example.com', 'path': '/', ..., 'session': True, 'priority': <CookiePriority.MEDIUM: 'Medium'>, 'source_scheme': <CookieSourceScheme.SECURE: 'Secure'>...}", and the patterns session/secure/path/name/Medium all matched True. load() at line ~1067 has the same logic.
- finder repro idea: Set cookies 'a'(value x) and 'b'(value y); save(pattern='session'); unpickle the file: both cookies are saved although neither name, value nor domain contains 'session'.
