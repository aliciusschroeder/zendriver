### A8.12: Element.get('class') returns None for elements that have a class attribute
- where (may drift): zendriver/core/element.py:get / _make_attrs:239
- finder severity: wrong-result
- claim: For <div class='foo bar'>, `el.get('class')` returns None. _make_attrs stores the class attribute under 'class_' (a workaround for the Python keyword in the old attribute-access API), and get() looks up the raw name. Only the undocumented get('class_') works, although get() was added as the string-based replacement for __getattr__.
- finder evidence (unverified): probe2.py (real Chrome): "mir.get('class') = None  attrs keys: ['id', 'class_', 'style']". probe5.py: "get('class') -> None | get('class_') -> a b".
- finder repro idea: Pure Python: Element(cdp.dom.Node(..., attributes=['class','a b']), tab).get('class').

### B16.14: Element.get('class') and element['class'] return None for elements that have a class attribute
- where (may drift): zendriver/core/element.py:Element._make_attrs / Element.get:1120
- finder severity: wrong-result
- claim: elem = await tab.select('.btn'); elem.get('class') returns None. _make_attrs stores the HTML attribute 'class' under the key 'class_', and get(name) looks up attrs.get(name) directly. Element.get's docstring says it 'Returns the value of the attribute with the given name, or None if it does not exist', and 'class_' is not documented anywhere. Code that branches on the class attribute gets the wrong result, while repr(elem) still shows class="...".
- finder evidence (unverified): In-memory probe: "get(class) -> None | get(class_) -> btn primary | e['class'] -> None | repr -> <button class=\"btn primary\" id=\"x\"></button>".
- finder repro idea: Build an Element with attributes ['class','btn primary'] and compare get('class') with get('class_').

### A8.14: Assigning Element.tree never reaches the tree property setter; the value is stored as an HTML attribute
- where (may drift): zendriver/core/element.py:__setattr__:246
- finder severity: wrong-result
- claim: `el.tree = new_doc` (the public @tree.setter). __setattr__ checks `key[1:] not in vars(self)`: for 'tree' it looks up 'ree' (the author intended '_' + key), finds nothing, and forwards to self.attrs['tree']. el.tree is unchanged, and the value later appears as a bogus tree="..." attribute in str(el)/save_to_dom.
- finder evidence (unverified): probe5.py: "after el.tree='SENTINEL': el.tree -> None | el.attrs['tree'] -> SENTINEL". In probe1 with real Chrome, inner2.tree = None left the tree set.
- finder repro idea: probe5.py: el.tree='SENTINEL'; print(el.tree, el.attrs.get('tree')).

### B16.16: Element.__setattr__ checks key[1:] instead of '_'+key, so the Element.tree setter never runs and a bogus HTML attribute is written
- where (may drift): zendriver/core/element.py:Element.__setattr__:246
- finder severity: wrong-result
- claim: elem.tree = doc, the public @tree.setter that create()'s docstring points to as the alternative to update(). __setattr__ checks `key[1:] not in vars(self)`: 'ree' is not there, so the value goes into self.attrs['tree'] and _tree stays None. elem.parent then still raises 'element has no tree set', and repr(elem) and save_to_dom() write tree="Node(...)" into the page's DOM.
- finder evidence (unverified): In-memory probe: 'tree property after setter: None', "attrs: dict_keys(['id', 'tree'])", 'repr (what save_to_dom writes): <div id="a" tree="Node(node_id=NodeId(0)...'.
- finder repro idea: Build an Element without a tree, set e.tree = doc, then print e.tree and e.attrs.

### A8.15: copy.copy / copy.deepcopy / pickle of an Element crash with RecursionError
- where (may drift): zendriver/core/element.py:__getattr__:221
- finder severity: crash
- claim: `copy.copy(el)` (also deepcopy and pickle.loads(pickle.dumps(el))). The copy is created with __new__ and has no _attrs. The copy machinery probes hasattr(y, '__setstate__'), which calls __getattr__, then self.get, then self.attrs, then self._attrs. That attribute is missing, so __getattr__('_attrs') is called and the cycle repeats. hasattr only swallows AttributeError, so RecursionError propagates.
- finder evidence (unverified): probe5.py: 'copy: RecursionError' and 'pickle: RecursionError'. probe1 with a real element also printed '[I] copy RecursionError'.
- finder repro idea: probe5.py: copy.copy(Element(node, FakeTab())).

### A8.16: highlight_overlay() goes through the deprecated __getattr__; it raises under warnings-as-errors and warns otherwise
- where (may drift): zendriver/core/element.py:highlight_overlay:1010
- finder severity: crash
- claim: `await el.highlight_overlay()` in a test suite run with -W error::DeprecationWarning or pytest filterwarnings=error. `getattr(self, '_is_highlighted', False)` misses the instance dict, so Python calls the @deprecated __getattr__, which emits DeprecationWarning. getattr's default only covers AttributeError, so the warning-as-exception escapes and highlight_overlay fails before sending any command. Without -W error the user still gets a 'Call to deprecated method __getattr__' warning they did not cause. Tab.query_selector(_all)'s getattr(_node, '__last', None) retry path hits the same thing when given an Element.
- finder evidence (unverified): probe5.py: 'highlight_overlay under -W error::DeprecationWarning -> DeprecationWarning Call to deprecated method __getattr__. (Use get() instead)'.
- finder repro idea: probe5.py: warnings.simplefilter('error', DeprecationWarning); await el.highlight_overlay().
