### A7.5: get_all_urls(absolute=True) resolves relative URLs against the origin instead of the page URL, and drops many valid links
- where (may drift): zendriver/core/tab.py:Tab.get_all_urls:1635
- finder severity: wrong-result
- claim: On http://host/docs/index.html with <a href="sub/page.html">, <img src="images/a.png">, <a href="other.html">, <link href="style.css"> and <a href="https://example.org/page#frag">, get_all_urls() joins every value with `"/".join(self.url.rsplit("/")[:3])`, which is just scheme://host. It returns http://host/sub/page.html and http://host/images/a.png, which are wrong (the right ones are http://host/docs/...). It drops other.html and style.css completely, because the value contains none of 'http', '//' or '/'. It also drops every URL containing '#', even absolute ones. <base href> is ignored as well.
- finder evidence (unverified): Probe1: get_all_urls() -> ['http://127.0.0.1:43351/sub/page.html', '.../up.html', '.../root.html', 'http://127.0.0.1:43351/images/a.png']. The browser resolves them to ['http://127.0.0.1:43351/docs/style.css', '.../docs/other.html', '.../docs/sub/page.html', '.../up.html', '.../root.html', 'https://example.org/page#frag', '.../docs/images/a.png'].
- finder repro idea: Serve the page above. Compare tab.get_all_urls() with evaluate("[...document.querySelectorAll('a,link,img,script')].map(e=>e.href||e.src)").

### A7.6: set_user_agent without metadata drops the client hints (navigator.userAgentData, Sec-CH-UA*), undoing the headless client-hint fix
- where (may drift): zendriver/core/tab.py:Tab.set_user_agent:1944
- finder severity: wrong-result
- claim: In headless mode, _prepare_headless overrides the UA together with UserAgentMetadata so client hints survive (984bf02, CHANGELOG Unreleased). `await tab.set_user_agent(accept_language='de-DE')` (keep the UA, change only the language) re-reads navigator.userAgent and sends Network.setUserAgentOverride without user_agent_metadata. Chrome then drops all client hints: navigator.userAgentData.brands becomes [], platform becomes '', and the Sec-CH-UA* headers stop. This is the exact giveaway the headless fix removed. Headful browsers lose their client hints the same way.
- finder evidence (unverified): Probe1: `brands before: [{"brand":"Chromium","version":"141"},{"brand":"Not?A_Brand","version":"8"}]`, then after set_user_agent(accept_language=...) `brands after ...: []` and `platform hint after: ` (empty).
- finder repro idea: Headless: evaluate JSON.stringify(navigator.userAgentData.brands), call set_user_agent(accept_language='de-DE'), reload, and evaluate again.

### A7.7: download_file puts url and filename into JS string literals without escaping; a quote or backslash makes it silently do nothing
- where (may drift): zendriver/core/tab.py:Tab.download_file:1450
- finder severity: wrong-result
- claim: `await tab.download_file(url, "O'Reilly.txt")` (or a URL containing ', or a Windows PathLike filename with backslashes such as 'sub\\x.txt') builds `_downloadFile('%s', '%s')` with the raw values. The function declaration becomes a SyntaxError. download_file ignores the exceptionDetails that Runtime.callFunctionOn returns, so it returns normally and no file is ever downloaded. Because the inner async function is neither awaited nor returned (no await_promise), fetch failures such as CORS or network errors are swallowed the same way. A crafted URL can also inject arbitrary JS into the page.
- finder evidence (unverified): Probe2: `after download_file("O'Reilly.txt"): ['downloads/b.txt', 'downloads/fromlink.txt']` (no new file, no exception). Probe4: call_function_on with the same quoting -> `SyntaxError: missing ) after argument list` in exceptionDetails, with no ProtocolException raised.
- finder repro idea: Probe2: set a download path, `await tab.download_file(base+'/docs/data.txt', "O'Reilly.txt")`, wait 2s: no file. Probe4 shows the callFunctionOn result carries a SyntaxError.

### A7.8: save_snapshot writes the CRLF MHTML in text mode, so on Windows every line ends in \r\r\n and the snapshot opens blank
- where (may drift): zendriver/core/tab.py:Tab.save_snapshot:1481
- finder severity: wrong-result
- claim: `await tab.save_snapshot('page.mhtml')` on Windows (a CI target). Page.captureSnapshot returns MIME text with CRLF line endings. `open(filename, 'w')` uses newline=None, which turns each '\n' into os.linesep ('\r\n'), so '\r\n' becomes '\r\r\n'. Chrome can no longer parse the boundaries and headers, and the saved snapshot renders as an empty page.
- finder evidence (unverified): Probe4: snapshot has CRLF (56 occurrences) and is pure ASCII. A TextIOWrapper with newline='\r\n' (the Windows text-mode behaviour) produces b'\r\r\n'. Probe5: `ok.mhtml -> 'Hello Login\nSign in now ...'`, `win.mhtml -> ''`. Fix: write bytes, or open with newline=''.
- finder repro idea: Probe5 (Linux) reproduces the Windows write: save a snapshot, rewrite its bytes with \r\n -> \r\r\n (what text mode does on Windows), open both via file://, and compare document.body.innerText.

### A7.10: Auto-named save_screenshot calls within the same second overwrite each other and return the same path
- where (may drift): zendriver/core/tab.py:Tab.save_screenshot:1548
- finder severity: wrong-result
- claim: The default filename is `{hostname}__{last_path_part}_{%Y-%m-%d_%H-%M-%S}`, which only changes once per second. `p1 = await tab.save_screenshot(); await tab.scroll_down(); p2 = await tab.save_screenshot()` on the same page often runs within one second (each call sleeps only 0.25s). p2 == p1, and the first screenshot is silently overwritten.
- finder evidence (unverified): Probe4: `auto names: 127.0.0.1__intl.html_2026-10-20_19-47-20.jpg 127.0.0.1__intl.html_2026-10-20_19-47-20.jpg same: True`, with only one .jpg in the directory.
- finder repro idea: Call save_screenshot() twice back to back and compare the returned paths and the directory listing.

### A7.12: print_to_pdf(transfer_mode='ReturnAsStream') writes a 0-byte PDF and leaks the IO stream
- where (may drift): zendriver/core/tab.py:Tab.print_to_pdf:1578
- finder severity: wrong-result
- claim: The docstring says kwargs are passed through to cdp.page.print_to_pdf, which includes transfer_mode. With 'ReturnAsStream', Chrome returns data='' plus a StreamHandle. print_to_pdf discards the handle (`data, _ = ...`) and writes b'' to the file, reporting success. The PDF is never read and the stream is never closed with IO.close, so it leaks in the browser.
- finder evidence (unverified): Probe4: `print_to_pdf ReturnAsStream size: 0`.
- finder repro idea: `p = await tab.print_to_pdf('s.pdf', transfer_mode='ReturnAsStream'); os.path.getsize(p)` gives 0.
