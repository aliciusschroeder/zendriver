### A1.4: One ProtocolException instance is shared by all pending commands, and each send() appends its own command to it
- where (may drift): zendriver/core/connection.py:Connection._fail_pending_transactions / Connection.send:664
- finder severity: wrong-result
- claim: Several commands are in flight on one connection (for example asyncio.gather of browser.connection.send(get_targets()), send(create_target(url='https://secret.example/?token=abc')) and send(get_version())), or on one tab session. Then the connection is closed (aclose) or the session is detached (_detach_session: tab closed, or browser connection closed). _fail_pending_transactions sets the same exception object on every pending tx. In send(), `e.message += f"\ncommand:{tx.method}\nparams:{tx.params}"` then mutates that shared instance once per waiter. Every caller gets the identical object, and its str() lists the commands and params of all the other callers. The error for get_targets shows createTarget's URL, token included. The traceback is also re-raised from several tasks.
- finder evidence (unverified): probe_shared_exc.py printed 'same object: True'. str() of task 0's exception was 'connection was closed\ncommand:Target.getTargets\nparams:{}\ncommand:Target.createTarget\nparams:{'url': 'https://secret.example/?token=abc'}\ncommand:Browser.getVersion\nparams:[]', and tasks 1 and 2 got the same text.
- finder repro idea: Use a fake peer that never replies. Start 3 concurrent conn.send(...) calls with different commands, call conn.aclose(), gather with return_exceptions=True, then assert res[0] is not res[1] and that 'Target.createTarget' is not in str(res[0]).

### A1.3: NaN or Infinity in any command param makes the command hang forever (invalid JSON, id-less error reply)
- where (may drift): zendriver/core/connection.py:Transaction.message:101
- finder severity: hang
- claim: tab.send(cdp.emulation.set_device_metrics_override(width=100, height=100, device_scale_factor=float('nan'), mobile=False)). The same applies to tab.mouse_move(float('inf'), 10), or to runtime.call_function_on with CallArgument(value=float('nan')) (for example numpy data). Transaction.message calls json.dumps with the default allow_nan=True, so the frame contains the bare tokens NaN or Infinity, which are not valid JSON. Chrome cannot parse the frame and replies {"error":{"code":-32700,"message":"JSON: invalid token at position N"}} with no id. The listener treats a message without 'id' as an event. parse_json_event fails, the failure is logged at INFO, and the loop continues. The tx stays in mapper and send() never returns. The fix is to serialize with allow_nan=False, which raises ValueError inside _send_transaction's try; that path already pops the tx.
- finder evidence (unverified): probe_nan2.py on real headless Chromium printed 'send HUNG 4s; pending tab.mapper: [9]' and the only frame received was 'recv: {"error":{"code":-32700,"message":"JSON: invalid token at position 110"}}' (no id). The connection was still usable afterwards (evaluate('2+2') -> 4), so only that command is lost.
- finder repro idea: On real Chrome: asyncio.wait_for(tab.send(cdp.emulation.set_device_metrics_override(width=100,height=100,device_scale_factor=float('nan'),mobile=False)), 4) raises TimeoutError, and tab.mapper still holds the id.

### A1.7: remove_handlers(module, handler) silently does nothing after add_handler(module, handler)
- where (may drift): zendriver/core/connection.py:Connection.remove_handlers:424
- finder severity: wrong-result
- claim: tab.add_handler(cdp.network, h) is documented ('if event_type_or_domain is a module ... it will find all available events and add the handler') and registers h under each of the 44 cdp.network event classes. The natural inverse, tab.remove_handlers(cdp.network, h) or tab.remove_handlers(cdp.network), looks up self.handlers[cdp.network] (or pops it). That key never exists, so nothing is removed and no error is raised. h keeps firing on every network event, and the Network domain stays auto-enabled. The only ways to undo the add are to remove each of the 44 event classes by hand or to clear every handler with remove_handlers().
- finder evidence (unverified): probe_handlers.py printed 'event types with h after add_handler(cdp.network, h): 44', 'after remove_handlers(cdp.network, h): 44', 'after remove_handlers(cdp.network): 44'. Confidence is medium only because remove_handlers is annotated Optional[type], although add_handler explicitly accepts modules.
- finder repro idea: conn.add_handler(cdp.network, h); conn.remove_handlers(cdp.network, h); then count the handler lists that still contain h. Expected 0, actual 44.

### A1.8: ProtocolException drops the CDP error 'data' field, hiding the actual reason for 'Invalid parameters'
- where (may drift): zendriver/core/connection.py:ProtocolException.__init__:51
- finder severity: cosmetic
- claim: tab.send(cdp.page.navigate(url=None)), or any call that sends bad params. Chrome replies {code:-32602, message:'Invalid parameters', data:'Failed to deserialize params.url - BINDINGS: string value expected at position 12'}. ProtocolException keeps only 'message' and 'code', so str(e) is 'Invalid parameters\ncommand:Page.navigate\nparams:{'url': None} [code: -32602]' and the explanation in 'data' is missing. It is reachable only through e.args[0].
- finder evidence (unverified): probe_err_data.py on real Chromium printed str(e): "Invalid parameters\ncommand:Page.navigate\nparams:{'url': None} [code: -32602]" while e.args[0] was {'code': -32602, 'message': 'Invalid parameters', 'data': 'Failed to deserialize params.url - BINDINGS: string value expected at position 12'}.
- finder repro idea: On real Chrome: try tab.send(cdp.page.navigate(url=None)) and catch ProtocolException as e. Then assert 'Failed to deserialize' in str(e); it fails.
