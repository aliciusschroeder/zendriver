# Group Q9 (aexit-reraise)

queue: fix  |  triage severity: wrong-result  |  triage fix kind: local

## Claim
Browser.__aexit__ and Connection/Tab.__aexit__ re-raise exc_type(exc_val): multi-argument exceptions and ExceptionGroups become TypeError, attributes (ProtocolException.code) and traceback are lost

## Files
zendriver/core/browser.py (Browser.__aexit__), zendriver/core/connection.py (Connection.__aexit__)

## Triage fix strategy (a hypothesis, not a requirement)
Do not rebuild the exception; return and let Python propagate the original.

## Triage test approach
Browser-free: `async with` a Connection (and a Browser-like instance) raising json.JSONDecodeError / ExceptionGroup / ProtocolException -> the original exception object propagates unchanged.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A2.7: Connection.__aexit__ rebuilds the exception as exc_type(exc_val): multi-arg exceptions become TypeError, and ProtocolException loses .code
- where (may drift): zendriver/core/connection.py:Connection.__aexit__:599
- finder severity: wrong-result
- claim: `async with tab: await tab.send(cdp.dom.resolve_node(node_id=999999))` -> the caught ProtocolException has code=None (originally -32000). With `async with tab: raise UnicodeDecodeError(...)`, a websockets ConnectionClosedError, or an ExceptionGroup from a TaskGroup, the caller instead gets TypeError ('function takes exactly 5 arguments', "ConnectionClosed.__init__() missing 1 required positional argument: 'sent'", 'BaseExceptionGroup.__new__() takes exactly 2 arguments'). KeyError('k') becomes KeyError(KeyError('k')). Returning None would already propagate the original exception. Browser.__aexit__ (browser.py:837) has the identical `raise exc_type(exc_val)`, and examples/wait_for_page.py uses it via `async with await zd.start() as browser`.
- finder evidence (unverified): probe_aexit.py printed: '1. caught ProtocolException code=None ...', '2. raised UnicodeDecodeError -> caught TypeError: function takes exactly 5 arguments (1 given)', '2. raised ConnectionClosedError -> caught TypeError: ConnectionClosed.__init__() missing 1 required positional argument: 'sent'', '2. raised ExceptionGroup -> caught TypeError: BaseExceptionGroup.__new__() takes exactly 2 arguments (1 given)', "3. KeyError args: (KeyError('k'),)".
- finder repro idea: Inside `async with tab:` raise each of ProtocolException (from a real failing command), UnicodeDecodeError, ConnectionClosedError(None, None) and ExceptionGroup, then assert the caught type and attributes. The fix is to drop the re-raise (return None).

### A3.8: Browser.__aexit__ rebuilds the exception as exc_type(exc_val): many exceptions turn into TypeError, attributes and traceback are lost, and the browser is never stopped
- where (may drift): zendriver/core/browser.py:Browser.__aexit__:841
- finder severity: wrong-result
- claim: `async with await zd.start() as browser:` is the documented pattern in examples/wait_for_page.py. Any exception inside the block goes through `raise exc_type(exc_val)` instead of propagating unchanged. websockets ConnectionClosedError(rcvd, sent) and json.JSONDecodeError(msg, doc, pos) both need more than one constructor argument, so the user gets 'TypeError: ... missing ... required positional argument' instead of the real error. A ProtocolException comes back as a new instance with .code None, and the original traceback is replaced. The `async with` block also never calls stop(), so Chrome keeps running until loop close, where atexit cleanup then fails (see the atexit finding).
- finder evidence (unverified): probe_aexit.py: 'raised ConnectionClosedError -> caught TypeError: ConnectionClosed.__init__() missing 1 required positional argument: 'sent'', 'raised JSONDecodeError -> caught TypeError: JSONDecodeError.__init__() missing 2 required positional arguments', 'raised ProtocolException -> caught ProtocolException: No node with given id found [code: -32000] | code=None'. Connection.__aexit__ in connection.py has the same pattern.
- finder repro idea: `b = zd.Browser(zd.Config(headless=True))` inside a running loop, then `async with b: raise websockets.exceptions.ConnectionClosedError(None, None)` and check that TypeError is caught. Do the same with ProtocolException({'code': -32000, 'message': 'm'}) and check that e.code is None.

### B15.5: Browser.__aexit__ and Connection/Tab.__aexit__ replace the user's exception with exc_type(exc_val): TypeError for multi-arg exceptions and ExceptionGroup, wrong exit status for sys.exit, and ProtocolException.code lost
- where (may drift): zendriver/core/browser.py:Browser.__aexit__ (also Connection.__aexit__ at zendriver/core/connection.py:599, inherited by Tab):841
- finder severity: wrong-result
- claim: The documented pattern `async with await zd.start() as browser:` (examples/wait_for_page.py, expect_download.py), or `async with tab:`. When the body raises, __aexit__ runs `raise exc_type(exc_val)` instead of returning and letting Python re-raise. (1) json.loads('{bad') in the body: the caller gets TypeError("JSONDecodeError.__init__() missing 2 required positional arguments"), so `except json.JSONDecodeError` no longer matches. The same happens for UnicodeDecodeError, CalledProcessError, IncompleteReadError and websockets ConnectionClosed. (2) A failing asyncio.TaskGroup in the body: TypeError('BaseExceptionGroup.__new__() takes exactly 2 arguments'), and except* no longer matches. (3) sys.exit(3) in the body: SystemExit(SystemExit(3)) prints '3' and the process exits with status 1. (4) ProtocolException({'code':-32000,...}) comes back with code=None and the code folded into the message.
- finder evidence (unverified): probe_aexit.py (py3.13.16): '[Browser] json: caller sees TypeError: "JSONDecodeError.__init__() missing 2 required positional arguments..."', '[Browser] group: caller sees TypeError: BaseExceptionGroup.__new__() takes exactly 2 arguments (1 given)', '[Browser] proto: ... code=None', '[Tab] json: caller sees TypeError ...'. probe_sysexit.py printed '3' and 'exit status: 1', while plain sys.exit(3) gives status 3. The code has been unchanged since the initial import (5c1a005).
- finder repro idea: In `async with browser:` run json.loads('{x'), a failing TaskGroup, or raise ProtocolException({'code':-32000,'message':'m'}), and print the type and .code the caller sees. Separately, a script with `async with Browser-like: sys.exit(3)` exits with $? = 1. Probes: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-B15/probe_aexit.py and probe_sysexit.py

### B16.11: Browser/Connection __aexit__ rebuild the exception as exc_type(exc_val), turning JSONDecodeError, ExceptionGroup and similar errors into TypeError
- where (may drift): zendriver/core/browser.py:Browser.__aexit__:841
- finder severity: wrong-result
- claim: async with browser: json.loads('x') raises JSONDecodeError, whose constructor requires (msg, doc, pos). __aexit__ runs `raise exc_type(exc_val)`, which raises "TypeError: JSONDecodeError.__init__() missing 2 required positional arguments", so `except json.JSONDecodeError` around the block never matches. An asyncio.TaskGroup failure inside the block becomes "TypeError: BaseExceptionGroup.__new__() takes exactly 2 arguments", so except* handlers miss it. Connection.__aexit__ (connection.py:599, used by `async with tab`) has the same pattern. Exceptions that keep their type also lose their attributes and traceback.
- finder evidence (unverified): Probe p5_aexit.py: 'instead got TypeError JSONDecodeError.__init__() missing 2 required positional arguments: 'doc' and 'pos'' and "instead got ['TypeError'] BaseExceptionGroup.__new__() takes exactly 2 arguments (1 given)". The fix is to return None and let Python propagate the original exception.
- finder repro idea: Raise JSONDecodeError and a TaskGroup error inside `async with await zd.start()` and check which exception type escapes.
