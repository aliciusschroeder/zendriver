# Group R28 (iframe-tree-recursion)

queue: report  |  triage severity: wrong-result  |  triage fix kind: local

## Claim
util.filter_recurse/filter_recurse_all never descend into content_document, so elements inside same-origin iframes lose .parent, cannot update()/query/remove_from_dom, and text search returns raw #text nodes plus duplicates

## Files
zendriver/core/util.py (filter_recurse, filter_recurse_all), zendriver/core/tab.py, zendriver/core/element.py

## Triage fix strategy (a hypothesis, not a requirement)
Descend into content_document.

## Triage test approach
Real Chromium with a same-origin srcdoc iframe.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A9.4: filter_recurse/filter_recurse_all never descend into content_document, so iframe elements lose .parent and remove_from_dom() silently does nothing
- where (may drift): zendriver/core/util.py:filter_recurse:173
- finder severity: wrong-result
- claim: Page with a same-origin iframe: <iframe srcdoc="<div id=box><p id=inner>...</p></div>">. Get the element with iframe = await tab.select('iframe'); inner = await iframe.query_selector('#inner'); here inner.parent is the div. Then call await inner.remove_from_dom(). That calls update(), which fetches the top-level document with get_document(-1, True). filter_recurse walks only .children and shadow_roots[0]. The iframe's DOM sits under the IFRAME node's .content_document, which it never visits. So the node is not found, _tree is replaced by the top document, and remove_from_dom's own filter_recurse also finds nothing. No DOM.removeNode is sent, no error is raised, and inner.parent is None from then on. Elements from tab.select_all(..., include_frames=True), which go through query_selector_all(_include_frames=True) with tree=top doc, have parent None right away. tab.query_selector_all works around this by collecting content_doc_nodes by hand, which shows the helper does not handle frames.
- finder evidence (unverified): probe_iframe3: 'found via iframe.query_selector: p inner parent: box', 'parent after remove_from_dom (which calls update): None', 'inner <p> still in iframe after remove_from_dom(): True'. probe_iframe2 (query_selector_all(_include_frames=True)): 'inner.parent before update: None', inner still present after remove_from_dom, while the top-level 'outer <p> still in page after remove_from_dom(): False'.
- finder repro idea: Probe probe_iframe3.py: data: page with the srcdoc iframe. iframe.query_selector('#inner') -> remove_from_dom(), then check with JS that the iframe's #inner still exists. Control: a top-level <p> is removed correctly.

### A5.4: Elements found inside same-origin iframes can never be queried: elem.query_selector_all() returns [] and elem.query_selector() returns None
- where (may drift): zendriver/core/tab.py:Tab.query_selector_all / Tab.query_selector (stale-node retry with _node):575
- finder severity: wrong-result
- claim: `inner = await tab.select('#inner', include_frames=True)`, where #inner is in a same-origin iframe and contains <span> and <b>. `await inner.query_selector_all('b')` returns [] and `await inner.query_selector('b')` returns None, yet inner.children shows the <b>. Element.query_selector_all first calls update(). update() does DOM.getDocument, which invalidates all node ids, then looks the node up with util.filter_recurse by backend id. filter_recurse never descends into content_document, so the node is not found and keeps its now-stale node_id (43 before and after update). DOM.querySelectorAll(stale id) fails with 'Could not find node'. The retry calls update() again (same no-op), sets __last, fails again, and returns []/None silently. Every query scoped to an element inside a same-origin iframe therefore returns nothing.
- finder evidence (unverified): Probe: '[inner.query_selector_all b] -> []', '[inner.query_selector b] -> None', '[inner.children] -> [<span ...>, <b >bold inner</b>]'. probe6: 'node_id before/after update: NodeId(43) NodeId(43)' and 'direct qsa after update: Could not find node with given id'.
- finder repro idea: Page with <iframe src='/same'> holding <div id=inner><span>a</span><b>b</b></div>; inner = await tab.select('#inner', include_frames=True); assert await inner.query_selector('b') is not None fails. Probes: scratchpad/detect-A5/probe1.py and probe6.py.

### A8.9: Element.update() cannot find elements inside same-origin iframes: attrs stay stale, .parent is lost, remove_from_dom() is a silent no-op
- where (may drift): zendriver/core/element.py:update / remove_from_dom:323
- finder severity: wrong-result
- claim: `iframe = await tab.select('#fr'); x = await iframe.query_selector('#x')` (this works and x.parent is the iframe body). The page then changes x's attribute and the user calls `await x.update()` (also called implicitly by `await x`, x.query_selector, set_text and remove_from_dom). update() fetches get_document(-1, pierce=True) and searches it with util.filter_recurse, which descends only .children and .shadow_roots, never .content_document. The node is not found, _node keeps the old snapshot, and _tree is replaced with the main document. x.get('data-v') returns the old value, x.parent becomes None, and remove_from_dom() finds nothing in the main tree and returns without removing or raising.
- finder evidence (unverified): probe4.py: before update the parent is '<body >...'; after setting data-v=2 and update(): get('data-v') = 1, parent after update: None, 'still in iframe after remove_from_dom(): True'. Control: remove_from_dom on a main-document element removed it (True).
- finder repro idea: page3.html with <iframe srcdoc="<div id='x' data-v='1'>">: setAttribute('data-v','2') via JS, x.update(), x.get('data-v'), x.parent, x.remove_from_dom(), then check that the element still exists.

### A5.9: find()/find_all() on text inside a same-origin iframe return a raw #text node and a duplicate of the match
- where (may drift): zendriver/core/tab.py:Tab.find_elements_by_text (reached via Tab.find / Tab.find_all):714
- finder severity: wrong-result
- claim: `await tab.find_all('hello same origin')`, where the text is in a same-origin iframe, returns [#text 'hello same origin', <span>]: two entries for one match. DOM.performSearch also searches same-process child documents. The node is not in `doc` as seen by filter_recurse (which never enters content_document), so describe_node gives a parentless text node. elem.parent is None and update() cannot find it either, so the text node itself is appended. The explicit iframe loop (lines 748-772) then adds the enclosing <span> again. As a result, `await tab.find('hello same origin', best_match=False)` returns a node_type 3 #text node, even though find's return_enclosing_element defaults to True and the docstring promises the containing element.
- finder evidence (unverified): Probe: '[find_all same origin text] -> [hello same origin, <span class="s">hello same origin</span>]' with backend ids [30, 29]; '[find best_match=False same-origin text] -> hello same origin  node_type 3 node_name #text'.
- finder repro idea: Page with <iframe src='/same'> holding <span>hello same origin</span>; r = await tab.find_all('hello same origin'): len(r) is 2 and r[0].node_type == 3; (await tab.find('hello same origin', best_match=False)).node_name == '#text'. Probes: scratchpad/detect-A5/probe1.py and probe4.py.

### A6.3: Text matches inside same-origin iframes come back as raw #text nodes, plus a duplicate of the parent; find_element_by_text/wait_for(text=) return the text node and click() silently does nothing
- where (may drift): zendriver/core/tab.py:Tab.find_elements_by_text:715
- finder severity: wrong-result
- claim: The page contains <iframe src='inner.html'> (same origin) with <button onclick=...>inner needle</button>. DOM.performSearch also returns nodes inside same-process iframes. For each node id, line 715 runs util.filter_recurse(doc, ...), which only walks .children and .shadow_roots and never .content_document, so the node is not found. The code falls back to DOM.describeNode and builds the Element with the main-document tree. elem.parent is then None even after elem.update(), so the raw text node is appended (lines 734-740).
