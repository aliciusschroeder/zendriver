# Group R23 (restart-state)

queue: report  |  triage severity: crash  |  triage fix kind: local

## Claim
Browser restart/state: start() stores the auto-chosen host/port in config, so start() after stop() or after a crash takes the connect-existing path and never launches Chrome; for host/port-connected browsers `stopped` is always True and a second start() leaks the first connection

## Files
zendriver/core/browser.py (start, stopped, _stop)

## Triage fix strategy (a hypothesis, not a requirement)
Remember whether host/port were user-provided; reset auto-chosen values and stale info on stop; base `stopped` on the connection for connect-existing.

## Triage test approach
Real Chromium restart.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A3.2: Restarting a stopped or crashed Browser never relaunches Chrome: stop() leaves config.host/port set, so start() takes the connect-existing path
- where (may drift): zendriver/core/browser.py:Browser.start:531
- finder severity: crash
- claim: `b = await zd.start(); await b.stop(); await b.start()`. The first start() wrote host='127.0.0.1' and port=free_port() into self.config. stop() clears _process and _process_pid but not host or port. So the second start() sees host and port both set and sets connect_existing=True: no executable check, no process spawn. test_connection then fails every retry against the dead port. The `if not self.info` check uses the stale self.info from the first run instead of the `connected` flag, so the clear 'Failed to connect' error is skipped. Connection(stale ws url).send(...) then raises ConnectionRefusedError. The crash case is broken too: when the process died, start() calls `self.create(config=self.config)`, which copies the same host/port into a new instance, and that instance fails with 'Failed to connect to browser'. Even with host/port reset by hand, stop() leaves the old Tab objects in self.targets, so tabs[0] is a dead target and browser.get() fails with 'No target with given id found'. A restarted browser is also never registered with asyncio_atexit again, because only create() registers it.
- finder evidence (unverified): probe_restart.py: 'after stop: host/port 127.0.0.1 48621 info is stale: True targets: 1' and 'restart raised after 2.52s: ConnectionRefusedError [Errno 111] Connect call failed ('127.0.0.1', 48621)'. probe_restart_crash.py: 'start after crash raised after 2.52s: Exception [... Failed to connect to browser ...]'. probe_restart2.py, with host/port reset by hand: 'first tab is stale: True' and 'get after restart raised ProtocolException No target with given id found command:Target.attachToTarget'.
- finder repro idea: `b = await zd.start(headless=True); await b.stop(); await b.start()` raises ConnectionRefusedError after about 2.5 s. `b._process.kill(); b._process.wait(); await b.start()` raises 'Failed to connect to browser'.

### B16.7: Restarting a Browser never relaunches Chrome: start() saves the auto-chosen host and port in self.config and later treats them as 'connect to existing'
- where (may drift): zendriver/core/browser.py:Browser.start:526
- finder severity: crash
- claim: (1) b = await zd.start(); await b.stop(); await b.start(). The first start wrote config.host='127.0.0.1' and config.port=free_port() (lines 534-535). On restart, `host is not None and port is not None` sets connect_existing=True, so no process is launched. test_connection fails, but self.info still holds the old /json/version data, so the `if not self.info` failure check is skipped. A Connection to the old ws URL then raises ConnectionRefusedError. (2) If the Chrome process died (crash, or the user closed the window), b.start() takes the branch built for exactly this case, `return await self.create(config=self.config)`. The new instance inherits host and port, also connects to the dead port, and raises 'Failed to connect to browser'. stop() also leaves self.targets, self.connection and self.info stale.
- finder evidence (unverified): Probe p4_restart.py: 'stopped; config host/port still 127.0.0.1 59477 targets kept: 1', then 'restart after stop failed: ConnectionRefusedError(111, "Connect call failed ('127.0.0.1', 59477)") process launched? None', and 'restart after crash failed: Exception('... Failed to connect to browser ...')'.
- finder repro idea: Run stop() then start(); separately, kill the process, call start(), and check whether a new pid appears.

### A12.4: Browser.start cannot restart a browser: after stop() it reuses the stale port and info, and the 'process died' branch never launches Chrome
- where (may drift): zendriver/core/browser.py:Browser.start:526
- finder severity: crash
- claim: (a) browser = await zd.start(); await browser.stop(); await browser.start(). The first start stored config.host/port, so connect_existing is True and Chrome is not launched. self.info is never cleared, so the 'Failed to connect' check passes, and Connection(old webSocketDebuggerUrl).send raises ConnectionRefusedError. (b) Chrome dies on its own, then browser.start() takes the dedicated branch `if self._process.poll() is not None: return await self.create(config=self.config)`. The new instance deep-copies a config that still holds the dead host/port, so it also skips launching and raises 'Failed to connect to browser'.
- finder evidence (unverified): Probe detect-A12/probe3.py printed: `stopped True host/port 127.0.0.1 51199`, `restart raised ConnectionRefusedError ["[Errno 111] Connect call failed ('127.0.0.1', 51199)"]`, and `start after external death raised Exception ['---------------------', 'Failed to connect to browser', ...]`. In start, connect_existing = host is not None and port is not None. _stop never resets config.host/port, self.info or self.connection.
- finder repro idea: b = await zd.start(headless=True); await b.stop(); await b.start() raises ConnectionRefusedError. Separately: b = await zd.start(); b._process.kill(); b._process.wait(); await b.start() raises Exception('Failed to connect to browser').

### A3.10: For a host/port-connected Browser, `stopped` is always True and start() is not idempotent: a second start() leaks the first websocket connection and listener
- where (may drift): zendriver/core/browser.py:Browser.start / Browser.stopped:524
- finder severity: leak
- claim: `b = await zd.start(host='127.0.0.1', port=9222)` attaches to a running browser. `b.stopped` returns True right away, because it only looks at self._process, which is None when connecting. The atexit cleanup therefore skips _stop(). A later `await b.start()` (for example retry or reconnect logic) passes the `if self._process or self._process_pid` guard, because both are None, and builds a new Connection over self.connection without closing the old one. The old websocket and its Listener task stay open for the life of the loop.
- finder evidence (unverified): probe_remote.py with chromium on PATH: 'connected: ws://127.0.0.1:9557/devtools/browser/... stopped property: True' and 'second start(): connection replaced: True old still open: True old listener running: True'.
- finder repro idea: Launch chromium by hand on a port and connect with zd.start(host, port). Assert b.stopped is True. Keep `old = b.connection`, call `await b.start()`, then check that `not old.closed and old.listener.running`.

### B16.13: Browser.stopped is True for a live browser connected through host/port, so the atexit hook skips _stop
- where (may drift): zendriver/core/browser.py:Browser.stopped:325
- finder severity: wrong-result
- claim: b = await zd.start(host=h, port=p) connects to a running browser with an open websocket and tabs. stopped is `not (self._process and self._process.poll() is None)`, which is always True when there is no local process. User code such as `while not browser.stopped:`, or the conftest-style `if browser is None or browser.stopped:` recreate check, treats a live browser as dead. _atexit_cleanup (`if not self.stopped: await self._stop()`) never closes this browser's connection or its ProxyForwarders.
- finder evidence (unverified): Probe p9_remote.py: 'connected; stopped property says: True tabs: 1'.
- finder repro idea: Connect to an externally launched chromium and print b.stopped and len(b.tabs).
