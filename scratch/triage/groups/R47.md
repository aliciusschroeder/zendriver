### A13.2: Generator downloads the spec into the current directory but reads it from REPO_ROOT, so running it from anywhere but the repo root deletes zendriver/cdp and fails with a misleading error
- where (may drift): scripts/generate_cdp.py:main / dl_file:998
- finder severity: crash
- claim: A developer runs `cd scripts && ./generate_cdp.py`, or `uv run /abs/path/scripts/generate_cdp.py` from another directory. main() checks `(REPO_ROOT/'browser_protocol.json').exists()` and gets False, then calls `dl_file(p.name)`. That runs `urllib.request.urlretrieve(url, filename='browser_protocol.json')`, a relative path, so the file lands in the current directory. main() then runs `shutil.rmtree(REPO_ROOT/'zendriver/cdp')` and opens REPO_ROOT/browser_protocol.json in parse(), which raises FileNotFoundError. The `finally:` then calls `.unlink()` on REPO_ROOT/browser_protocol.json, which raises a second FileNotFoundError that hides the first. End state: zendriver/cdp is deleted and left empty, so `import zendriver` breaks until git restores it. Both spec JSON files are left as stray files in the current directory, and the traceback points at the cleanup line rather than the real cause.
- finder evidence (unverified): I ran a scratch copy (REPO_ROOT patched to /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A13/regen/root2) from root2/scripts. The traceback ended at line 1060 `list(map(lambda x: x.unlink(), json_paths))` with `FileNotFoundError: ... root2/browser_protocol.json`. Afterwards `ls root2/zendriver/cdp` showed an empty directory (the sentinel page.py was gone), and root2/scripts contained browser_protocol.json and js_protocol.json. Code: line 998 calls `dl_file(p.name)` with no path; line 1066 `filename=path or filename` is therefore relative; lines 1002-1003 do the rmtree before the try; line 1060 unlinks without missing_ok.
- finder repro idea: Copy the script to a scratch tree with REPO_ROOT pointing there and a sentinel file in <root>/zendriver/cdp. Run it with the scratch scripts/ directory as the current directory. The sentinel is deleted, the JSON files appear in scripts/, and the run ends with FileNotFoundError raised from the finally block. Fix: `dl_file(p.name, p)` (or pass REPO_ROOT / name). Also make the finally block use unlink(missing_ok=True), and do the rmtree only after parsing succeeds.

### A13.1: Top-level array alias types whose items are $ref (Target.TargetFilter, DOMSnapshot.ArrayOfStrings) never convert their items, so typed TargetFilter values cannot be sent
- where (may drift): scripts/generate_cdp.py:CdpType.generate_primitive_code:361
- finder severity: crash
- claim: `await browser.connection.send(cdp.target.get_targets(filter_=cdp.target.TargetFilter([cdp.target.FilterEntry(type_="page")])))`, or the same with set_discover_targets / set_auto_attach / auto_attach_related. Generated get_targets does `params["filter"] = filter_.to_json()`. TargetFilter.to_json (zendriver/cdp/target.py:168) is `return self`, so it hands back the list of FilterEntry dataclass instances unchanged. Transaction.message then calls json.dumps, which raises `TypeError: Object of type FilterEntry is not JSON serializable`. The typed API for the filter parameter on all four Target commands is therefore unusable. The only call that works is the mis-typed `TargetFilter([{"type": "page"}])`. The reverse direction is wrong too. TargetFilter.from_json is `cls(json)`, which returns raw dicts instead of FilterEntry. DOMSnapshot.ArrayOfStrings.from_json (dom_snapshot.py:422) leaves its elements as plain ints rather than StringIndex (it is used in NodeTreeSnapshot.attributes and LayoutTreeSnapshot.styles, returned by dom_snapshot.capture_snapshot).
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A13/probe_filter.py against Chromium 141 printed: `to_json -> TargetFilter([FilterEntry(exclude=None, type_='page')]) FilterEntry`; `typed ERR get_targets TypeError Object of type FilterEntry is not JSON serializable`; `typed ERR set_discover_targets TypeError Object of type FilterEntry is not JSON serializable`; `dict workaround OK: ['page']`; `from_json elem type: dict`; `ArrayOfStrings elem is StringIndex: False`. Generator: the items.ref branch (lines 344-350) only builds the annotation `typing.List[FilterEntry]`, while the to_json/from_json bodies at 361-374 are identical to the scalar case. I regenerated from devtools-protocol 0.0.1612613 with a scratch copy of the generator and the output is byte-identical to zendriver/cdp, so the shipped code is exactly what the generator emits. A spec scan found only two such array-of-$ref aliases: Target.TargetFilter (items are objects) and DOMSnapshot.ArrayOfStrings (items are integer aliases).
- finder repro idea: With real headless Chromium: send cdp.target.get_targets(filter_=TargetFilter([FilterEntry(type_='page')])) and expect TypeError. Send the same with TargetFilter([{'type':'page'}]) and it succeeds. Also check type(TargetFilter.from_json([{'type':'page'}])[0]) is dict and isinstance(ArrayOfStrings.from_json([1])[0], StringIndex) is False. Fix: in generate_primitive_code, when items.ref is set, emit `[i.to_json() for i in self]` and `cls([Ref.from_json(i) for i in json])`.

### A13.3: Generated __repr__ on int/float alias types also changes str()/f-strings: str(NodeId(5)) == 'NodeId(5)'
- where (may drift): scripts/generate_cdp.py:CdpType.generate_primitive_code:376
- finder severity: wrong-result
- claim: `el = await tab.select('#b'); str(el.backend_node_id)` returns 'BackendNodeId(6)', not '6'. `wid, _ = await tab.get_window(); f'{wid}'` returns 'WindowID(1190458396)'. The generator overrides only __repr__. int and float have no __str__ of their own, so str(), '%s' and an empty format spec all fall through to that __repr__. Affected classes: NodeId, BackendNodeId, WindowID, ExecutionContextId, StringIndex, CertificateId, network/input/runtime/media TimeSinceEpoch, MonotonicTime, Timestamp and TimeDelta (12 classes), plus the list/dict aliases (Headers, Quad). So any user code that stringifies an id or timestamp gets wrong text: logging, building a JS snippet or selector, or writing ids to a file and later calling int() on them (ValueError). Zendriver's own debug log does it too (cloudflare.py:169 logs 'node_id: NodeId(5)'). str subclasses such as FrameId are unaffected because str defines __str__.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A13/probe_str.py against Chromium 141 printed: `str(el.backend_node_id) = BackendNodeId(6) | f'{wid}' = WindowID(1190458396) | json: {"w": 1190458396}` and `int(str(id)) -> ValueError invalid literal for int() with base 10: 'BackendNodeId(6)'`. An offline check printed `NodeId(5) NodeId(5) NodeId(5) TimeSinceEpoch(1.5) TimeSinceEpoch(1.5) abc ExecutionContextId(3)` for str / f-string / %s on NodeId and TimeSinceEpoch and str() on FrameId. Generated example: zendriver/cdp/dom.py BackendNodeId.__repr__ (around lines 49-50).
- finder repro idea: assert str(zendriver.cdp.dom.NodeId(5)) == '5' fails, and f'{cdp.network.MonotonicTime(1.5)}' == '1.5' fails. Fix: also emit `def __str__(self): return super().__repr__()` for int/float aliases, or emit __repr__ only (keeping super().__str__) by delegating str to the base type.

### A13.4: Optional 'any'-typed fields treat None as 'omit', so CallArgument cannot pass JavaScript null (it arrives as undefined)
- where (may drift): scripts/generate_cdp.py:CdpProperty.generate_to_json:276
- finder severity: wrong-result
- claim: `await tab.send(cdp.runtime.call_function_on('function(x){return x===null}', object_id=..., arguments=[cdp.runtime.CallArgument(value=None)], return_by_value=True))` returns false, and typeof x is 'undefined'. For every optional property the generator emits `if self.value is not None: json['value'] = ...`. For a field typed `any` (Runtime.CallArgument.value at runtime.py:577, also RemoteObject.value and DeepSerializedValue.value), None is the natural Python spelling of JSON null, but it is dropped. The CDP spec says an empty CallArgument means undefined. The typed API therefore cannot express null as a primitive value. The only workaround is the undocumented UnserializableValue('null'), whose spec only lists -0, NaN, Infinity, -Infinity and bigint literals.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A13/probe_null.py against Chromium 141 printed: `CallArgument(value=None).to_json() -> {}`, `value=None -> 1:undefined`, `value=0 -> 1:number`, `value='' -> 1:string`, and `unserializable null -> 1:null`. Falsy values (0, '') are correctly kept, so only null is lost. Low confidence because this follows from the generator's None-means-absent convention, and a workaround exists.
- finder repro idea: call_function_on('function(x){return arguments.length+":"+(x===null?"null":typeof x)}', arguments=[CallArgument(value=None)]) returns '1:undefined'. Fix: for any-typed optional fields use a sentinel default, distinct from None, to mean 'omitted'.
