# Group R25 (autodiscover-off)

queue: design  |  triage severity: wrong-result  |  triage fix kind: design

## Claim
With Config.autodiscover_targets=False, Browser.get/Tab.get(new_tab) always raise TimeoutError and Tab.close waits 10 s then raises, because the awaited Target events are never emitted; update_targets never prunes destroyed targets

## Files
zendriver/core/browser.py (get, update_targets), zendriver/core/tab.py (close)

## Triage fix strategy (a hypothesis, not a requirement)
Design: either always enable target discovery or fall back to polling; prune in update_targets. Browser.get is owned by another PR.

## Triage test approach
Real Chromium with autodiscover_targets=False.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### B13.6: With autodiscover_targets=False, Browser.get always raises TimeoutError and Tab.close always waits 10 s then raises TimeoutError, even though both succeeded
- where (may drift): zendriver/core/browser.py:Browser.get (wait_for_navigation) / Tab.close:431
- finder severity: wrong-result
- claim: config = zd.Config(headless=True); config.autodiscover_targets = False (a supported setting, used by tests/core/test_browser.py::test_start_waits_for_initial_tab); browser = await zd.Browser.create(config). Then: await browser.get(url) (and tab.get(url, new_tab=True), which delegates to it) navigates fine but always raises asyncio.TimeoutError after `timeout`. await tab.close() closes the tab but then always waits 10 s and raises TimeoutError. Browser.get waits for Target.targetInfoChanged and Tab.close for Target.targetDestroyed on the browser connection. Chrome only emits those after Target.setDiscoverTargets(discover=True), which Browser.start sends only when autodiscover_targets is set. Adding the handlers does not make up for it: Connection._register_handlers skips cdp.target ('by default enabled', connection.py:698), so nothing ever enables discovery.
- finder evidence (unverified): probe_nodisc.py (real headless Chromium): `Browser.get TimeoutError after 3.0s: TimeoutError()` / `but tab actually navigated? url: data:text/html,<p>hi</p>`; `Browser.get(new_tab) TimeoutError after 3.0s`; `Tab.close TimeoutError after 10.0s: TimeoutError()` / `closed target still exists: False`.
- finder repro idea: With config.autodiscover_targets=False: assert await browser.get('data:text/html,<p>hi</p>', timeout=3) returns without raising, and assert await asyncio.wait_for(tab.close(), 5) returns without raising.

### A4.3: Browser.get always raises TimeoutError when autodiscover_targets=False, even though navigation succeeded
- where (may drift): zendriver/core/browser.py:Browser.get (get_handler / wait_for_navigation):455
- finder severity: wrong-result
- claim: `b = await zd.start(autodiscover_targets=False)` (Config accepts it through kwargs; tests use config.autodiscover_targets=False). Then `await b.get(url)` or `await b.get(url, new_tab=True)`. get() only finishes when the browser connection receives Target.targetInfoChanged for the tab. Those events are only delivered after Target.setDiscoverTargets(discover=True), which start() sends only when autodiscover_targets is True. So every Browser.get waits the full timeout (10s by default) and raises TimeoutError, even though Page.navigate or createTarget has already completed. Tab.get(new_tab=True) is affected too, because it delegates to Browser.get. Tab.close() fails the same way: its TargetDestroyed wait times out after 10s (tab.py, outside this scope).
- finder evidence (unverified): Probe scratchpad/detect-A4/nodisc_probe.py printed 'get(data url) autodiscover off: TimeoutError after 3.01s' and 'get(new_tab) autodiscover off: TimeoutError after 3.02s'. Right after, b.tabs showed both tabs already at their new URLs, so navigation had succeeded. 'close tab2: TimeoutError after 10.00s'.
- finder repro idea: cfg = zd.Config(headless=True); cfg.autodiscover_targets = False; b = await zd.start(cfg); then time `await b.get('data:text/html,hi', timeout=3)` and `await b.get('data:text/html,two', new_tab=True, timeout=3)`.

### A12.5: With Config.autodiscover_targets=False, every Browser.get / Tab.get(new_tab) raises TimeoutError and Tab.close times out after 10 s, even though both succeed
- where (may drift): zendriver/core/browser.py:Browser.get:457
- finder severity: crash
- claim: config = zd.Config(headless=True); config.autodiscover_targets = False; browser = await zd.start(config); await browser.get(url). Browser.get waits for a Target.targetInfoChanged event and Tab.close waits for Target.targetDestroyed. Chrome only emits these after Target.setDiscoverTargets(discover=True), and start() sends that only when autodiscover_targets is set (_register_handlers skips cdp.target as 'enabled by default'). So wait_for_navigation never finishes: get() raises TimeoutError after the full timeout although the page loaded, and close() raises TimeoutError after 10 s although the tab closed.
- finder evidence (unverified): Probe detect-A12/probe5.py printed: `get raised TimeoutError after 4.0s`, `but page title: Grocery List`, `new_tab raised TimeoutError after 4.0s`, `close raised TimeoutError after 10.0s`. This is a different problem from the known partial-timeout issue: here the awaited event can never arrive.
- finder repro idea: Start with autodiscover_targets=False. browser.get(sample_file('groceries.html'), timeout=4) raises TimeoutError, yet browser.tabs[0].evaluate('document.title') == 'Grocery List'.

### A4.4: update_targets never removes destroyed targets, so browser.tabs, main_tab and get() keep using closed tabs
- where (may drift): zendriver/core/browser.py:Browser.update_targets:821
- finder severity: wrong-result
- claim: update_targets only adds targets or updates them in place; it never drops entries missing from Target.getTargets. Removal happens only in the TargetDestroyed event handler, so whenever that event is not delivered, closed tabs stay in browser.targets forever. That is always the case with autodiscover_targets=False, where update_targets is the only way to sync. Example: start with autodiscover_targets=False, open a second tab, close the first tab, then call `await browser.update_targets()`. browser.tabs still lists the dead tab first, main_tab returns it, and `await browser.get(url)` navigates tabs[0], failing immediately with ProtocolException 'No target with given id found'. get_tab(), tile_windows() and CookieJar can also pick the dead tab.
- finder evidence (unverified): Probe scratchpad/detect-A4/stale_probe.py printed: Chrome's live targets were ['F3E5...'], while browser.tabs was ['4DC6...', 'F3E5...']; 'main_tab is closed first tab: True'; 'browser.get -> ProtocolException after 0.00s: No target with given id found'.
- finder repro idea: Start with autodiscover_targets=False. Send Target.createTarget, then update_targets. Close the first tab with Target.closeTarget, then update_targets again. Compare browser.tabs with Target.getTargets, and call browser.get(url).
