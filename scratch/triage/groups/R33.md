### A8.6: Element.apply() swallows JavaScript exceptions and returns None or {} instead of raising
- where (may drift): zendriver/core/element.py:apply:512
- finder severity: wrong-result
- claim: `await el.apply('(e) => { throw new Error("boom") }')` returns None. With await_promise=True a rejected promise returns {}. Runtime.callFunctionOn always returns a RemoteObject (the exception object), so `if result and result[0]` takes the success branch and result[1] (exceptionDetails) is ignored. Tab.evaluate raises ProtocolException(errors) in the same situation. Consequences: clear_input on textarea is a silent no-op (above); get_js_attributes() on any element with a circular expando (e.g. React's __reactFiber$ on every React-rendered node) crashes with a misleading 'TypeError: the JSON object must be str, bytes or bytearray, not NoneType'; user scripts fail silently.
- finder evidence (unverified): probe1.py: '[C apply throw] OK -> None', '[C2 apply reject] OK -> {}', '[C3 get_js_attributes circ] EXC TypeError: the JSON object must be str, bytes or bytearray, not NoneType'.
- finder repro idea: page1.html: inp.apply throwing; inp.apply(async throw, await_promise=True); circ.get_js_attributes() where #circ has a self-referential __fiber expando.

### B15.8: Element.apply drops JavaScript exceptions: a throwing function returns None, and the exception_details branch is dead
- where (may drift): zendriver/core/element.py:Element.apply:516
- finder severity: wrong-result
- claim: `await elem.apply("(e) => { throw new Error('boom') }")` returns None, the same as a function returning undefined. Runtime.callFunctionOn returns (RemoteObject of the thrown error, ExceptionDetails). result[0] is always a truthy RemoteObject, so `if result and result[0]: return result[0].value` returns the error object's value (None). `elif result[1]: return result[1]` can never run. Callers built on apply (clear_input, React value setters, user scripts) cannot detect failures, while Tab.evaluate raises ProtocolException(errors) for the same JS.
- finder evidence (unverified): probe_swallow.py printed 'box.apply(throwing fn) returned: None' and 'tab.evaluate(throwing) -> raises ProtocolException (for contrast)'. Confidence is medium because the code may have meant to return rather than raise the details, but even that path is dead.
- finder repro idea: On any page: `await (await tab.select('div')).apply("(e)=>{throw new Error('x')}")` returns None. Compare with tab.evaluate of a throwing IIFE, which raises. Probe: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-B15/probe_swallow.py

### A8.7: apply(return_by_value=False) is ignored; the returned RemoteObject has no object_id
- where (may drift): zendriver/core/element.py:apply:507
- finder severity: wrong-result
- claim: `handle = await el.apply('(e) => e.parentElement', return_by_value=False)`, expecting a remote handle as documented. apply hard-codes return_by_value=True in the call_function_on command and only uses the Python flag to choose between result[0] and result[0].value. The caller gets RemoteObject(value={}, object_id=None), which cannot be passed to any later CDP call.
- finder evidence (unverified): probe1.py: '[D apply rbv False] OK -> RemoteObject(type_=\'object\', ..., value={}, ..., object_id=None ...)'.
- finder repro idea: page1.html: r = await inp.apply('(e) => e.parentElement', return_by_value=False); print(r.object_id).

### A8.5: clear_input()/clear_input_by_deleting() silently do nothing on <textarea> (regression from b506c8f)
- where (may drift): zendriver/core/element.py:clear_input / clear_input_by_deleting:657
- finder severity: wrong-result
- claim: `ta = await tab.select('textarea'); await ta.clear_input()`. The JS calls Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set.call(el,''), which throws TypeError 'Illegal invocation' for HTMLTextAreaElement (and select/contenteditable). apply() swallows the exception (see the apply finding), so the call returns normally and the textarea keeps its text. clear_input_by_deleting dispatches one Backspace keydown, then throws at nativeSetter.call and also returns silently. Before b506c8f, `element.value = ""` cleared textareas.
- finder evidence (unverified): probe1.py: '[B clear_input textarea] OK -> None', ta.value = 'some text'; '[B2 clear_input_by_deleting textarea] OK -> None', ta.value = 'some text'. The <input> control case cleared correctly. git show b506c8f shows the previous `element.value = ""` implementation.
- finder repro idea: page1.html <textarea id=ta>some text</textarea>: call clear_input(), then evaluate document.getElementById('ta').value.
