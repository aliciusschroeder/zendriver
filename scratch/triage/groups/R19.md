# Group R19 (sync-callback-thread)

queue: report  |  triage severity: hang  |  triage fix kind: local

## Claim
Sync event handlers run in a worker thread (asyncio.to_thread), so the documented feed_cdp() from a sync handler raises 'no current event loop' and the paused request is never continued; lambdas returning coroutines are never awaited

## Files
zendriver/core/connection.py (Listener.listener_loop dispatch, Connection.feed_cdp)

## Triage fix strategy (a hypothesis, not a requirement)
Make feed_cdp schedule onto the connection's loop thread-safely (call_soon_threadsafe / run_coroutine_threadsafe) when called off-loop.

## Triage test approach
Browser-free: sync handler calling feed_cdp on a fake peer -> the command is sent.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A2.6: Sync event handlers run in a worker thread via asyncio.to_thread: feed_cdp() from them raises RuntimeError (paused request never continued), and lambdas returning coroutines are silently never awaited
- where (may drift): zendriver/core/connection.py:Listener.listener_loop (callback dispatch) / Connection.feed_cdp:1002
- finder severity: hang
- claim: (a) feed_cdp's docstring presents it as the non-async way to answer cdp.fetch.RequestPaused. With `def on_paused(ev): tab.feed_cdp(cdp.fetch.continue_request(request_id=ev.request_id))`, `tab.add_handler(cdp.fetch.RequestPaused, on_paused)` and `await tab.send(cdp.fetch.enable())`, the handler runs in thread 'asyncio_N'. There, asyncio.ensure_future -> get_event_loop() raises 'There is no current event loop in thread', the Connection.send coroutine is never awaited, the request stays paused, and the page fetch hangs. (b) `tab.add_handler(cdp.runtime.ConsoleAPICalled, lambda e: process(e))` with an async process: inspect.iscoroutinefunction(lambda) is False, so to_thread calls it and drops the returned coroutine ('coroutine was never awaited'), and the handler silently does nothing. The same applies to `lambda e: asyncio.create_task(...)` (no running loop in the thread) and to objects with an async __call__. The add_handler docstring advertises lambdas as handlers.
- finder evidence (unverified): probe_sync.py printed: 'page fetch HUNG: request stayed paused (handler ran in thread ['asyncio_1','asyncio_0'])', loop errors 'RuntimeError("There is no current event loop in thread 'asyncio_1'.") | Task exception was never retrieved', 'RuntimeWarning: coroutine 'Connection.send' was never awaited', and 'async work scheduled by lambda ran: 0' with 'coroutine main.<locals>.process was never awaited'. Confidence is medium only because the thread dispatch itself is deliberate. The feed_cdp and lambda breakage contradicts the documented usage.
- finder repro idea: Real Chromium plus a local http.server: register a sync RequestPaused handler that calls feed_cdp, run Fetch.enable, then `await wait_for(tab.send(runtime.evaluate("fetch('/x').then(r=>r.status)", await_promise=True)), 5)`, which times out. Separately, register a lambda that returns a coroutine and check that the coroutine never runs. A fix is to call sync handlers on the loop thread (or use run_coroutine_threadsafe in feed_cdp), and to await the result when it is awaitable.

### B14.4: Sync event handlers run in worker threads, so the documented feed_cdp() from a sync handler raises RuntimeError and the paused request hangs
- where (may drift): zendriver/core/connection.py:Connection.feed_cdp:556
- finder severity: hang
- claim: tab.add_handler(cdp.fetch.RequestPaused, lambda ev, t: t.feed_cdp(cdp.fetch.continue_request(request_id=ev.request_id))); await tab.send(cdp.fetch.enable()); await tab.send(cdp.page.navigate(url)). Listener.listener_loop runs non-coroutine callbacks through asyncio.create_task(asyncio.to_thread(callback, *args)) (connection.py:1002), so the lambda runs in thread 'asyncio_0', which has no event loop. feed_cdp calls asyncio.ensure_future(self.send(...)), and that raises 'RuntimeError: There is no current event loop in thread asyncio_0' on 3.10 through 3.13. The error is lost in the unobserved to_thread task ('Task exception was never retrieved'), the send coroutine is never awaited, and Fetch.continueRequest is never sent. The paused request stays paused and the navigation hangs. feed_cdp's docstring says it is the non-async way to answer cdp.fetch.RequestPaused and stresses that it is 'not an async method, just a regular method', which is the sync-handler case. Any other sync handler that touches the loop (asyncio.Event.set, Future.set_result, create_task) is likewise unsafe from that thread.
- finder evidence (unverified): probe_feed.py: kind=async printed 'handler calls=2 title=OK'. kind=sync printed 'feed_cdp raised in handler thread: RuntimeError There is no current event loop in thread asyncio_0.', then 'Task exception was never retrieved ... to_thread()', then 'RuntimeWarning: coroutine Connection.send was never awaited', and finally 'kind=sync handler calls=1 -> navigation HUNG (timeout)'.
- finder repro idea: With real Chromium, add a sync RequestPaused handler that calls tab.feed_cdp(continue_request), enable Fetch, navigate with a timeout, and assert that navigation completes. Compare with the async-handler version, which works.

### A12.3: Sync event handlers run in a worker thread, so the documented feed_cdp() call from a handler raises RuntimeError and the paused request is never continued
- where (may drift): zendriver/core/connection.py:Listener.listener_loop / Connection.feed_cdp:999
- finder severity: hang
- claim: tab.add_handler(cdp.fetch.RequestPaused, lambda ev, conn: conn.feed_cdp(cdp.fetch.continue_request(request_id=ev.request_id))). The feed_cdp docstring describes exactly this: a non-async way to answer RequestPaused. listener_loop runs non-coroutine callbacks with asyncio.to_thread(callback, *args). Inside the worker thread, feed_cdp's asyncio.ensure_future(self.send(...)) raises 'RuntimeError: There is no current event loop in thread asyncio_0'. The send coroutine is never awaited, the request stays paused, and tab.get() times out. The only trace is an unretrieved task exception in the log.
- finder evidence (unverified): Probe detect-A12/probe4.py printed the traceback `connection.py line 556 in feed_cdp: asyncio.ensure_future(self.send(cdp_obj)) ... RuntimeError: There is no current event loop in thread 'asyncio_0'`, then `RuntimeWarning: coroutine 'Connection.send' was never awaited` and `nav raised TimeoutError handler saw ['file:///.../groceries.html']`. Sync handlers have run in threads since 5c1a005 (#176).
- finder repro idea: Register a sync RequestPaused handler that calls conn.feed_cdp(continue_request). tab.get(sample_file('groceries.html'), timeout=5) raises TimeoutError, and stderr shows the RuntimeError traceback from ensure_future.
