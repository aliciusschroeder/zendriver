# Group R30 (expect-futures)

queue: report  |  triage severity: hang  |  triage fix kind: local

## Claim
expect.py futures: a timed-out wait on exp.value/request/response cancels the shared future (expectation dead); expect_request/expect_response never enable Network on enter (page-initiated requests hang until some unrelated send); Network.loadingFailed is ignored so response/response_body hang forever for failed requests

## Files
zendriver/core/expect.py, zendriver/core/intercept.py

## Triage fix strategy (a hypothesis, not a requirement)
asyncio.shield the stored futures; enable Network in __aenter__; handle LoadingFailed by failing the futures.

## Triage test approach
Fake peer / real Chromium.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A10.3: Timing out a wait on expectation.value/request/response/response_body cancels the shared future, so later awaits raise CancelledError and the expectation is dead
- where (may drift): zendriver/core/expect.py:ResponseExpectation.value / RequestExpectation.value / BaseRequestExpectation.request, response, response_body; BaseFetchInterception.request, response_body, continue_request, fulfill_request, fail_request, continue_response:189
- finder severity: wrong-result
- claim: `async with tab.expect_response(r'.*/page1') as exp: try: await asyncio.wait_for(exp.value, 0.5) except TimeoutError: pass; await tab.get(url_page1); await exp.value` → raises CancelledError, although the response arrived and nothing cancelled the caller (`current_task().cancelling() == 0`). The property awaits the bare stored future (`return await self.response_future`). When wait_for cancels the waiting task, asyncio also cancels that future. When the event arrives later, the handler's set_result raises InvalidStateError in a background task. This applies to intercept.py as well: after a timed-out `wait_for(interception.request, t)`, `interception.continue_request()` raises CancelledError. The paused request can then only be released by leaving the block, and the CancelledError tends to escape `except Exception` blocks and look like task cancellation. The repo's own tests use exactly this pattern (`asyncio.wait_for(request_info.value, timeout=3)`).
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_cancel.py printed `response_future state after timeout: <Future cancelled>`, `LOOP ERR: InvalidStateError('invalid state')`, and `second wait raised CancelledError although the response arrived ... cancelling(): 0`. The first run of the intercept probe showed `intercept.py line 123, in continue_request ... asyncio.exceptions.CancelledError` after an earlier timed-out `wait_for(a.request, 5)`.
- finder repro idea: As in the scenario: wait_for(exp.value, 0.5) with nothing loading, then trigger the navigation and await exp.value again. Expect CancelledError plus a loop-handler InvalidStateError.

### A10.7: expect_request/expect_response never enable the Network domain on enter, so expecting a page-initiated request hangs until some unrelated tab.send happens
- where (may drift): zendriver/core/expect.py:BaseRequestExpectation._setup / __aenter__:100
- finder severity: hang
- claim: `await tab.get(polling_page)` (no Network handlers yet, so enabled_domains == []). Then `async with tab.expect_request(r'.*/poll.*') as r: await r.value`. The page calls fetch('/poll') every 300 ms, but `r.value` never resolves. _setup only calls add_handler. Network.enable is sent only by Connection._register_handlers inside the next tab.send(). If the awaited request is triggered by the page itself (timers, polling, SSE fallback, a request started from another tab or connection) and the user's next action is to await the expectation, no send ever happens and the await hangs forever. An unrelated `await tab.evaluate('1')` makes it resolve immediately.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_poll.py: `enabled domains before: [] []`, `expect_request on a self-polling page: nothing after 5s (Network domain not enabled)`, `after an unrelated tab.send: http://127.0.0.1:39587/poll`.
- finder repro idea: Page with setInterval(fetch('/poll')). Load it, then enter expect_request and wait_for(shield(r.value), 5), which times out. Then call tab.evaluate('1'), after which it resolves.

### B13.7: expect_response/expect_request awaitables hang forever when the matched request fails (Network.loadingFailed is never handled)
- where (may drift): zendriver/core/expect.py:BaseRequestExpectation.response_body (also .response, ResponseExpectation.value):142
- finder severity: hang
- claim: async with tab.expect_response(r'.*/api') as exp: await tab.get(page); body = await exp.response_body. If the matched request fails after headers arrive (connection reset, Content-Length mismatch, aborted by a navigation), Chrome sends Network.loadingFailed instead of Network.loadingFinished. loading_finished_future is never resolved, so response_body hangs forever. If the request fails before any response (connection refused, DNS error, blocked), response_future is never resolved, so `await exp.value` / `await exp.response` hang forever, even though request_future already resolved. Only RequestWillBeSent, ResponseReceived and LoadingFinished handlers are registered. Nothing listens for LoadingFailed to fail the pending futures, and these awaitables take no timeout.
- finder evidence (unverified): probe_expect.py (real headless Chromium): `got response 200 http://127.0.0.1:34507/broken` then `response_body still pending after 10.0s (Network.loadingFailed was ignored)`. For the refused fetch: `expect_response.value still pending after 5.0s; request_future done=True`.
- finder repro idea: Local HTTP server whose /broken endpoint sends Content-Length: 100000, writes 10 bytes and closes. Page fetches /broken. Assert `await asyncio.wait_for(exp.response_body, 10)` raises a ProtocolException-like error quickly instead of TimeoutError. A second case uses fetch('http://127.0.0.1:1/x') with expect_response.

### A10.8: response_body hangs forever when the request fails after its response headers (Network.loadingFailed is ignored)
- where (may drift): zendriver/core/expect.py:BaseRequestExpectation.response_body:149
- finder severity: hang
- claim: `async with tab.expect_response(r'.*/api\.json') as r: await tab.get(page); body = await r.response_body`. The server sends headers (200, Content-Length: 1000) and then closes the connection early, or the page aborts the fetch, or the navigation cancels it. Chrome emits responseReceived and then Network.loadingFailed (net::ERR_CONTENT_LENGTH_MISMATCH). response_body awaits loading_finished_future, which only LoadingFinished can resolve, and nothing listens for LoadingFailed. The await never returns and has no timeout, although the browser has already reported the failure.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_body_fail.py: `response received: 200`, then `response_body still pending after 10s; LoadingFailed events seen: ['net::ERR_CONTENT_LENGTH_MISMATCH', ...] page err: TypeError: Failed to fetch`.
- finder repro idea: Local server that answers /api.json with Content-Length 1000 and an 11-byte body, then closes. Inside expect_response, wait_for(shield(r.response_body), 10) and record LoadingFailed events with a separate handler.
