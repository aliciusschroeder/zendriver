### A4.2: HTTPApi sends the local DevTools /json/version request through the http_proxy env var, so start() fails behind a proxy
- where (may drift): zendriver/core/browser.py:HTTPApi._request:1133
- finder severity: crash
- claim: A user has http_proxy (or HTTP_PROXY) set in the environment and no no_proxy entry for 127.0.0.1, as on many corporate machines. They call `await zd.start()`. HTTPApi._request uses urllib.request.urlopen, which uses the default ProxyHandler. That handler sends GET http://127.0.0.1:<port>/json/version to the corporate proxy, which cannot reach the user's loopback. Every test_connection attempt fails, and start() stops the browser and raises 'Failed to connect to browser ... you are running as root, pass sandbox=False', even though Chrome started and is listening. (urllib.request.proxy_bypass_environment only skips the proxy when no_proxy is set.)
- finder evidence (unverified): Probe scratchpad/detect-A4/proxy_probe.py printed 'start failed after 1.4s: Exception Failed to connect to browser'. The dummy proxy recorded b'GET http://127.0.0.1:57639/json/version HTTP/1.1' four times, so zendriver's DevTools discovery request went through the env proxy. Fix idea: build an opener with urllib.request.ProxyHandler({}). Note: pyproject allows websockets>=14.0, and websockets>=15 also reads env proxies for ws://, so the CDP socket will hit the same problem on upgrade.
- finder repro idea: Start a dummy TCP 'proxy' on 127.0.0.1 that records the request line and answers 502. Remove no_proxy/NO_PROXY from os.environ and set http_proxy to the dummy. Then call `await zd.start(headless=True, browser_connection_max_tries=3)`.
