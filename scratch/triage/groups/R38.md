### A10.5: send_keys raises ProtocolException mid-typing for emoji graphemes of 4+ UTF-16 units (skin tones, flags, ZWJ sequences)
- where (may drift): zendriver/core/keys.py:KeyEvents.from_text / to_cdp_events (CHAR path for emoji/unknown graphemes):306
- finder severity: crash
- claim: `await elem.send_keys('Thanks 👍🏽')` (or '🇩🇪', or the family emoji '👨‍👩‍👧‍👦') types 'Thanks ' and then raises `ProtocolException: Invalid 'text' parameter`. from_text splits the text into graphemes and sends each emoji or unknown grapheme as one Input.dispatchKeyEvent(type='char', text=<whole grapheme>). Chrome rejects text of 4 or more UTF-16 code units (WebKeyboardEvent::kTextLengthCap = 4). So any grapheme that is a skin-toned emoji, a flag or a ZWJ sequence aborts the call, leaving the field partly filled. KeyPressEvent's docstrings advertise CHAR/DOWN_AND_UP as the way to send non-ASCII text, and from_mixed_input has the same failure.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_keys3.py: `'👍' utf16 units: 2 -> OK`, `'👍🏽' utf16 units: 4 -> EXC ProtocolException Invalid 'text' parameter`, `'🇩🇪' utf16 units: 4 -> EXC ...`, `family utf16 units: 11 -> EXC ...`.
- finder repro idea: For each s in ['👍', '👍🏽', '🇩🇪', '👨‍👩‍👧‍👦'], call textarea.send_keys('x'+s+'y') and catch ProtocolException.

### A10.9: Modifier combos release the modifiers before the main key and in the same (not reverse) order, so the main key's keyup carries no modifiers (Shift+A keyup reports key 'a', Ctrl+Enter keyup has ctrlKey=false)
- where (may drift): zendriver/core/keys.py:KeyEvents.to_down_up_sequence:488
- finder severity: wrong-result
- claim: `await elem.send_keys(KeyEvents.from_mixed_input([(SpecialKeys.ENTER, KeyModifiers.Ctrl)]))` dispatches Control↓, Enter↓, Control↑, Enter↑(modifiers=0). `from_mixed_input(['A'])` dispatches Shift↓, 'A'↓, Shift↑, 'a'↑. The docstring says modifier key-up events are sent after the main key, and the step-3 comment says 'in reverse order'. The code releases all modifiers first (step 3), in press order, and only then sends the main keyup (step 4), computed with the cleared modifiers. Page handlers bound to keyup that check e.ctrlKey/e.shiftKey/e.key (e.g. Ctrl+Enter-to-send on keyup) never see the combination, and multi-modifier combos release in the wrong order.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_keys.py: `keydown:"Shift"..., keydown:"A":KeyA:65:shift=true, keypress:"A", keyup:"Shift":ShiftLeft:16:shift=false, keyup:"a":KeyA:65:shift=false`. probe_keys3.py Ctrl+Enter: `keydown Control, keydown Enter, keypress Enter, keyup Control, keyup Enter`.
- finder repro idea: Document-level keydown/keypress/keyup logger that records key, code and shiftKey/ctrlKey. Send from_mixed_input(['A!']) and (ENTER, Ctrl) and inspect the order.

### A10.10: Reusing a KeyEvents object gives different events: to_cdp_events overwrites self.key with the normalised key, so a second press of 'A' or '!' types 'a' or '1'
- where (may drift): zendriver/core/keys.py:KeyEvents.to_cdp_events:332
- finder severity: wrong-result
- claim: `ev = KeyEvents('A'); p1 = ev.to_cdp_events(KeyPressEvent.DOWN_AND_UP); p2 = ev.to_cdp_events(KeyPressEvent.DOWN_AND_UP)`. p1's keyDown has text 'A', but p2's keyDown has text 'a' and no Shift events. The DOWN_AND_UP branch assigns `self.key, override_modifiers = self._normalise_key(self.key, cur_modifier)`, which permanently replaces 'A' with 'a' ('!' with '1', '_' with '-'), while self.modifiers keeps its original value without Shift. _get_key_and_text's CHAR path likewise rewrites a SpecialKeys key into a str. Any caller that builds a key once and sends it repeatedly (a public class exported from zendriver) types the wrong character from the second time on.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_keys3.py printed `reuse first keyDown text: [None, 'A'] second: ['a']` (first list: Shift keyDown text None, then 'A').
- finder repro idea: Call to_cdp_events twice offline on KeyEvents('A') and compare the keyDown text fields.

### A10.11: SpecialKeys.SPACE (and ' ' in DOWN_AND_UP text) is sent with code ' ' instead of 'Space', so KeyboardEvent.code is empty
- where (may drift): zendriver/core/keys.py:SpecialKeys.SPACE / KeyEvents._handle_special_key_lookup, _handle_string_key_lookup:26
- finder severity: wrong-result
- claim: `await elem.send_keys(SpecialKeys.SPACE)` or `from_mixed_input([' '])`. SpecialKeys values are used as (code, windowsVirtualKeyCode). For SPACE that pair is (' ', 32), so Input.dispatchKeyEvent gets code=' '. Chrome does not recognise that as a DOM code, and the page sees e.code === '' instead of 'Space'. Handlers keyed on e.code === 'Space' (video players, games, custom toggles) never fire. Every other SpecialKeys entry carries a valid code.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_keys3.py: `SPACE log: ['keydown:" "::32:shift=false', 'keypress:" "::32', 'keyup:" "::32']`, with an empty code field. Compare TAB, which logged `keydown:"Tab":Tab:9`.
- finder repro idea: keydown logger that records e.code, then send_keys(SpecialKeys.SPACE).
