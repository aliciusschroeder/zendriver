### A11.5: ContraDict.update(), setdefault() and |= store plain dicts unconverted, so nested attribute access breaks
- where (may drift): zendriver/core/_contradict.py:ContraDict (no update/setdefault/__ior__ override):46
- finder severity: wrong-result
- claim: The docstring promises 'recursive action. dict assignments will be converted too', but only __setitem__ and __setattr__ run _wrap. dict.update, dict.setdefault and dict.__ior__ on a subclass do not call __setitem__. So `cd = zendriver.cdict(); cd.update({'a': {'b': 1}}); cd.a.b` raises AttributeError: 'dict' object has no attribute 'b'. The same happens with cd.setdefault('s', {'b': 1}) and `cd |= {'o': {'b': 1}}`. ContraDict and cdict are exported in zendriver.__all__, and Element.attrs and Browser.info are ContraDicts that users may update.
- finder evidence (unverified): Scratch cd_probe.py: 'after update, c2.a.b -> RAISES AttributeError', 'after setdefault, c2.s.b -> RAISES AttributeError', 'after |=, c2.o.b -> RAISES AttributeError'.
- finder repro idea: c = ContraDict(); c.update({'a': {'b': 1}}); c.a.b

### A11.6: copy.copy() or pickling a ContraDict gives an object that still returns deleted keys as attributes
- where (may drift): zendriver/core/_contradict.py:ContraDict.__init__ / __getattribute__:41
- finder severity: wrong-result
- claim: __init__ makes the instance __dict__ the dict itself (`super().__setattr__('__dict__', self)`). copy.copy and pickle rebuild through __reduce_ex__ without calling __init__: they create a separate real __dict__ and copy every item into it as state (the state is the dict itself), then set the items again. After `c = copy.copy(cd); del c['a']`, `'a' in c` is False but `c.a` still returns the old value, because __getattribute__ falls through to object.__getattribute__, which finds the stale entry in the separate __dict__. `c.pop('a')` behaves the same, and vars(c) is stale. This affects e.g. copy.copy(element.attrs), copy.copy(browser.info), or a ContraDict sent through multiprocessing.
- finder evidence (unverified): Scratch cd_probe.py: 'after del c5['a'] (copy.copy), c5.a -> {'b': 1}', 'after del c7['a'], c7.a -> {'b': 1}' (pickle), 'vars(copy) is copy -> False'. deepcopy is not affected (memo makes the state the new object).
- finder repro idea: c = copy.copy(ContraDict({'a': {'b': 1}})); del c['a']; print(c.a)  # prints {'b': 1} instead of raising AttributeError. pickle.loads(pickle.dumps(...)) does the same.

### A11.8: Assigning an existing ContraDict or list to a ContraDict stores a copy, so later changes to the original are not seen
- where (may drift): zendriver/core/_contradict.py:_wrap:62
- finder severity: wrong-result
- claim: _wrap always rebuilds mappings (cls(v)) and non-str sequences (a new list), even when v is already a ContraDict or a list. So `inner = cdict(); cd.child = inner; inner.x = 1; cd.child` gives {} and `cd.child is inner` is False. Likewise `lst = []; cd.l = lst; lst.append(1); cd.l` gives []. Plain dict assignment keeps the reference, which the docstring ('directly inherited from dict') suggests is also what ContraDict does. copy.copy() also turns into a deep copy for nested mappings (c.a is not cd.a).
- finder evidence (unverified): Scratch cd_probe.py: 'c3.child after inner.x=1 -> {}', 'c3.l after lst.append -> []', 'copy.copy is shallow? c5.a is c4.a -> False'.
- finder repro idea: inner = ContraDict(); c = ContraDict(); c.child = inner; inner.x = 1; assert c.child == {}  # surprising
