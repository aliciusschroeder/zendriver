# Group Q1 (listener-robustness)

queue: fix  |  triage severity: hang  |  triage fix kind: local

## Claim
Listener dies or leaves a Transaction unresolved when a reply fails to parse, a handler raises, or an unexpected exception is raised

## Files
zendriver/core/connection.py (Transaction.__call__, Listener.listener_loop, Connection.send/aopen for session tabs)

## Triage fix strategy (a hypothesis, not a requirement)
Make Transaction.__call__ set_exception on the future for any parse error instead of raising; in listener_loop isolate per-callback dispatch errors (log, do not re-raise) and handle unexpected exceptions from _receive_message without silently dying (fail pending transactions so callers do not hang); make a flat-session tab's send/aopen restart the parent browser connection's listener when it is not running.

## Triage test approach
Browser-free: fake websocket/peer that replies with a result the generated parser rejects (missing key / unknown enum) -> send() raises within a bound instead of hanging; handler with wrong arity -> later sends still answered; parent listener dead -> tab send still answered.

### A1.1: A response the cdp parser rejects kills the listener and leaves send() hanging forever
- where (may drift): zendriver/core/connection.py:Transaction.__call__:126
- finder severity: hang
- claim: tab.send(cmd) or any helper built on it (tab.evaluate, get_cookies, update_targets, get_frames). Chrome's reply has a shape the generated parser does not accept: a required field is missing or an enum value is newer than the generated protocol (Chrome version skew). The Listener pops the tx from mapper and calls tx(**message) at listener_loop line 973. Transaction.__call__ catches only StopIteration around self.__cdp_obj__.send(response['result']), so the KeyError or ValueError from from_json propagates out of __call__ and out of listener_loop. The future is never resolved. The same happens if 'result' is missing (KeyError) and on the explicit `raise ProtocolException('could not parse...')` at line 130. Result: the awaiting send() hangs with no timeout, and the listener task dies. Other in-flight commands on that connection also hang until some later send() starts a new Listener. For a session tab, events pile up in the unbounded _inbox with nothing reading them.
- finder evidence (unverified): probe_parse.py against a fake CDP peer printed: 'send() HUNG (timed out after 3s) / listener done: True exception: KeyError('targetInfo') / mapper after: {}'. For the cookie: 'send() HUNG ... listener done: True exception: ValueError("'SomeFutureValue' is not a valid CookieSameSite")'. A later send worked only because send() recreates the dead listener.
- finder repro idea: Run a fake websockets peer that answers Target.getTargetInfo with {"id":N,"result":{}}, or Storage.getCookies with a cookie whose sameSite is 'SomeFutureValue'. Then call asyncio.wait_for(conn.send(cdp.target.get_target_info()), 3), which times out, and check that conn.listener.task.exception() is the KeyError or ValueError.

### A2.3: An exception while parsing a command response kills the Listener without failing the Transaction, so the awaiting send() hangs forever
- where (may drift): zendriver/core/connection.py:Listener.listener_loop:973
- finder severity: hang
- claim: Any send() whose response fails parsing in Transaction.__call__ hangs forever. Causes include a generated from_json KeyError/ValueError (protocol drift, an unknown enum value) or a custom command generator as allowed by the send() docstring. Example: `def cmd(): j = yield {'method':'Runtime.evaluate','params':{'expression':'1'}}; return j['x']`, then `await tab.send(cmd())` never returns. `tx(**message)` runs outside every try block. The exception escapes listener_loop, the task dies with 'Task exception was never retrieved', and tx (already popped from mapper) is never set_result/set_exception'd. Any concurrent tab.wait() blocked on that listener's idle event also hangs. This is a different site from the known issue: that issue covers the try around _receive_message, and here the receive succeeded and the response dispatch is what fails.
- finder evidence (unverified): probe_fake.py (fake peer, generated cdp.runtime.evaluate) printed "C: send() hung; listener running: False listener exc: KeyError('exceptionId')". probe_parse.py (real Chromium, custom generator) printed 'send() HUNG: timed out after 5s instead of raising KeyError', old listener task exception 'notThere', mapper size 0 (tx popped but never completed).
- finder repro idea: Use a fake websockets.serve peer that answers Runtime.evaluate with {'id':n,'result':{'result':{'type':'object'},'exceptionDetails':{'bogus':1}}}. `await asyncio.wait_for(conn.send(cdp.runtime.evaluate('1')), 3)` times out instead of raising KeyError. The fix is to wrap tx(**message) and set_exception on the tx.

### B15.1: A command reply that fails to parse kills the Listener, and the send() waiting for it hangs forever (aclose() cannot release it either)
- where (may drift): zendriver/core/connection.py:Listener.listener_loop (tx(**message)) / Transaction.__call__:973
- finder severity: hang
- claim: Any tab.send()/connection.send() whose result the generated cdp parser rejects. This happens when Chrome's protocol differs from the bundled cdp: a required key is missing (KeyError), or there is a new enum value, e.g. a cookie sameSite value unknown to CookieSameSite (ValueError). listener_loop pops the Transaction from conn.mapper and then calls tx(**message) outside any try. Inside Transaction.__call__, cdp_obj.send(result) raises something other than StopIteration, and the exception leaves listener_loop, so the listener task dies. The Future is never resolved. It is already gone from mapper, so _fail_pending_transactions in aclose()/_detach_session can never fail it, and send() hangs forever. Its own explicit `raise ProtocolException('could not parse the cdp response')` also kills the listener instead of failing the tx. On the browser connection this also starves every flat-session tab, because no one reads the websocket until another browser-level send() creates a new Listener. Event parsing on the same loop does catch these errors (parse_json_event in try/except -> logger.info; continue), which shows the intended behaviour.
- finder evidence (unverified): probe_tx_parse.py printed: 'send done within 3s: False | listener running: False | listener exc: KeyError('targetInfo')' with the task stuck at connection.py:662 `return await tx`. The same happened for Storage.getCookies with sameSite 'SomeFutureValue': listener exc ValueError("'SomeFutureValue' is not a valid CookieSameSite"). probe_tx_parse2.py: 'after aclose(): send finished? False | tx in mapper: 0'. The only trace is 'Task exception was never retrieved' at GC. Related to the known 'listener only catches Timeout/Cancelled/ConnectionClosed' lead, but this site is outside that try. The fix belongs in result dispatch (tx.set_exception), and the tx is lost permanently.
- finder repro idea: Run a fake websockets.serve peer that answers Target.getTargetInfo with {"id":N,"result":{}}. Call conn.send(cdp.target.get_target_info()) as a task, wait 3s, then call conn.aclose() and check that the task is still pending. Probe: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-B15/probe_tx_parse.py and probe_tx_parse2.py

### B15.4: One event handler that raises when called (e.g. wrong arity) kills the Listener through an explicit re-raise, so commands already in flight hang
- where (may drift): zendriver/core/connection.py:Listener.listener_loop (callback dispatch):1011
- finder severity: hang
- claim: A user registers `async def on_target(): ...` (no parameters) via browser.connection.add_handler(cdp.target.TargetCreated, on_target) or tab.add_handler(...). _accepts_connection_argument returns False, so the loop calls callback(event), which raises TypeError synchronously while the coroutine object is created. The dispatch block logs a warning and then `raise`s (the outer `except Exception: raise` passes it on too), so the listener task dies. The reply to a command that is already in flight, and is queued right behind the event, is never read: that send() hangs until some later send() happens to create a new Listener. Every other handler for every event also stops firing. On the browser connection this starves all flat-session tabs, since nothing reads the shared websocket.
- finder evidence (unverified): probe_bad_handler.py printed: 'get_version finished within 3s: False' and 'listener running: False exc: TypeError('main.<locals>.bad_handler() takes 0 positional arguments but 1 was given')'. This is a distinct site from the known receive-side lead: the loop raises on purpose after logging, rather than isolating the faulty callback.
- finder repro idea: Run a fake CDP peer that, for Browser.getVersion, first sends a Target.targetCreated event and then the reply. Register a good handler plus `async def bad(): pass`, then call conn.send(cdp.browser.get_version()) with a 3s timeout. Probe: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-B15/probe_bad_handler.py

### A2.4: Once the browser connection's Listener stops, every flat-session Tab command hangs because the tab path never restarts the parent listener
- where (may drift): zendriver/core/connection.py:Connection.aopen / Connection._attach_session / Connection.send:432
- finder severity: hang
- claim: After browser.connection.listener dies (for example from the response-parse failure above on a browser-level command, or from the known ConcurrencyError), `await tab.send(cdp.runtime.evaluate('1'))` and `await tab.evaluate('1+1')` hang forever. For a Tab, aopen() calls only _attach_session(), which returns early when session_id is set and never calls browser_connection.aopen(). send() then restarts only the tab's own Listener, which reads tab._inbox. Nothing reads the websocket, so nothing fills that inbox. A self-heal exists for the browser connection (send restarts its listener), but tab traffic never reaches it. Tabs recover only when unrelated code happens to send on browser.connection.
- finder evidence (unverified): probe_parse2.py printed: 'browser.connection.send HUNG instead of raising KeyError', 'browser listener running: False', 'tab.send HUNG too: tab listener running: True inbox size 0', 'tab.evaluate HUNG', then 'after a browser-level send, tab send ok: 6'. Confidence is medium only because the trigger depends on a listener death, which is either the known issue or the finding above. The missing revival is a separate defect.
- finder repro idea: Real Chromium: `await asyncio.wait_for(browser.connection.send(bad_custom_cmd()), 5)` (it times out and the browser listener dies). Then `await asyncio.wait_for(tab.send(cdp.runtime.evaluate('2+2')), 5)` also times out. After `await browser.connection.send(cdp.target.get_targets())`, the tab send works again. The fix is to have the flat-session aopen ensure that the parent's listener is running.
