# Group R26 (domain-lifecycle)

queue: design  |  triage severity: hang  |  triage fix kind: design

## Claim
Auto-enabled domains are never disabled when their handlers are removed (Fetch keeps pausing every request), and a manual X.disable is undone by a param-less X.enable on the next send

## Files
zendriver/core/connection.py (_register_handlers, _update_manual_domain)

## Triage fix strategy (a hypothesis, not a requirement)
Design: decide whether removing the last handler should disable the domain, and whether manual disable should suppress auto-enable.

## Triage test approach
Fake peer recording sent methods.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A2.2: A manual X.disable is undone on the next command: RH re-sends param-less X.enable (Fetch.enable() pauses every request, and navigation hangs)
- where (may drift): zendriver/core/connection.py:Connection.send / Connection._update_manual_domain / Connection._register_handlers:655
- finder severity: hang
- claim: tab.add_handler(cdp.fetch.RequestPaused, h); await tab.send(cdp.fetch.enable(patterns=[RequestPattern(url_pattern='*/x')])); await tab.send(cdp.fetch.disable()); await tab.send(cdp.page.navigate(url)) -> the navigate send first emits 'Fetch.enable' with {} params (default pattern '*' at Request stage). Every request is paused, h does not continue it, and Page.navigate never returns. Trace: on 'disable', _update_manual_domain removes fetch from both enabled_domains and manually_enabled_domains. On the next send, RH sees a RequestPaused handler with fetch in neither list and calls fetch.enable() with no params. This is the param-less re-enable that #253 / test_handler_wont_reenable_without_params says 'will hang'. It also happens when a user's own RequestPaused handler coexists with tab.intercept(): intercept's _teardown sends Fetch.disable, and the next command re-enables Fetch for every URL.
- finder evidence (unverified): Probe probe_disable.py printed: after disable: enabled [] manual []; TIMEOUT; sent after disable: [('Fetch.enable', {}), ('Page.navigate', {...'/b'})]; paused requests: ['http://127.0.0.1:.../b']. The navigation request was paused by the param-less auto enable and never released.
- finder repro idea: Spy on tab._send_transaction (instance attribute). Add a fetch handler, enable fetch with a pattern, disable it, then navigate with wait_for(…, 5). The navigate times out and the spy shows ('Fetch.enable', {}) before Page.navigate.

### A12.2: remove_handlers stops tracking an auto-enabled domain but never disables it; after removing a Fetch handler every request stays paused and navigation hangs
- where (may drift): zendriver/core/connection.py:Connection._register_handlers:716
- finder severity: hang
- claim: tab.add_handler(cdp.fetch.RequestPaused, h). The next send auto-enables Fetch with no patterns, so it intercepts every request, and h continues each one. Later tab.remove_handlers(cdp.fetch.RequestPaused, h) or remove_handlers(). On the next send, _register_handlers drops the empty handler list and runs `self.enabled_domains.remove(ed)` for fetch, but it never sends Fetch.disable. The browser keeps pausing every request and nothing continues them, so the next tab.get() raises TimeoutError and later evaluate() calls also time out. zendriver meanwhile reports enabled_domains == [].
- finder evidence (unverified): Probe detect-A12/probe2.py printed: `with handler: paused 1 enabled [<module 'zendriver.cdp.fetch'>]`, `after remove: handlers {RequestPaused: []}`, `second nav raised TimeoutError`, `enabled_domains [] manual []`, `evaluate raised TimeoutError`. The only domain disable calls in core are the explicit ones in element.py, intercept.py and tab.py:200. _register_handlers has none.
- finder repro idea: Add an async RequestPaused handler that continues requests, then get(groceries.html) (works). remove_handlers(cdp.fetch.RequestPaused, h). get(profile.html, timeout=5) raises TimeoutError.
