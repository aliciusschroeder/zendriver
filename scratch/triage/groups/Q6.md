# Group Q6 (expect-pairing)

queue: fix  |  triage severity: wrong-result  |  triage fix kind: local

## Claim
expect_request/expect_response pair the request with a different request's response/body when several matching events are dispatched before the self-removing handler runs (request_id overwritten; InvalidStateError in handler tasks)

## Files
zendriver/core/expect.py (BaseRequestExpectation._request_handler/_response_handler/_loading_finished_handler)

## Triage fix strategy (a hypothesis, not a requirement)
Ignore events once the corresponding future is done (check before mutating request_id), so only the first matching request is tracked.

## Triage test approach
Browser-free: drive the handlers directly (or a fake peer) with two matching RequestWillBeSent events dispatched back-to-back -> request, response and body all belong to the first request; no InvalidStateError.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### B14.3: expect_request/expect_response: buffered matching events overwrite request_id, so .response and .response_body come from a different request than .value
- where (may drift): zendriver/core/expect.py:BaseRequestExpectation._request_handler:43
- finder severity: wrong-result
- claim: async with tab.expect_request(r'.*/pix\d+\.gif') as exp: await tab.get(page_with_30_images); req = await exp.value; resp = await exp.response. Chrome sends several Network.requestWillBeSent frames in one read. On Python >= 3.12, Listener.listener_loop drains buffered websocket frames without yielding: wait_for no longer creates a task, and websockets' SimpleQueue.get does not suspend when data is queued. So it calls asyncio.create_task(_request_handler(ev)) once per matching event before the first task runs and removes the handler. The first task sets request_future to request R1. Every later task overwrites self.request_id with its own id (Rn), and its request_future.set_result raises InvalidStateError inside an unobserved task. _response_handler then matches Rn. The result: exp.value / exp.request describe pix0.gif, while exp.response, exp.response_body and loading_finished_future describe pix9.gif (for example). BaseFetchInterception._response_handler and DownloadExpectation._handler have the same unguarded set_result, which produces the lost InvalidStateError tasks.
- finder evidence (unverified): probe_expect.py on real Chromium with Python 3.13: 5/5 trials mismatched. Sample: 'value.url=pix0.gif request_id(attr)=28835.11 value.request_id=28835.2 response.url=pix9.gif match=False'. The loop exception handler caught 55 lost InvalidStateError('invalid state') task exceptions.
- finder repro idea: Serve a page that loads 30 small images. Use a pattern that matches all of them. Assert (await exp.value).request_id == (await exp.response_future).request_id, and that no 'Task exception was never retrieved' is logged.

### A2.8: Events already dispatched still reach a handler after it removes itself; expect_request pairs request A with the response and body of a later match B
- where (may drift): zendriver/core/expect.py:BaseRequestExpectation._request_handler (dispatched by Listener.listener_loop):44
- finder severity: wrong-result
- claim: Use `async with tab.expect_request(r'.*/img\d\.png') as req: await tab.get(page_with_8_imgs)`. `await req.request` returns img0, while `await req.response` and `req.response_body` belong to img7. Listener.listener_loop drains the burst of RequestWillBeSent events from the inbox without yielding and create_task()s one handler call per event. The first task matches, removes the handler and set_result(img0). The later tasks still run, overwrite self.request_id with their own ids, then fail on set_result with InvalidStateError ('Task exception was never retrieved'). _response_handler then matches the last request_id. The same self-removing-handler pattern exists in _response_handler, _loading_finished_handler, DownloadExpectation._handler and BaseFetchInterception._response_handler. The fix is either a guard in the handlers (return if future.done()) or a dispatch-time check that the callback is still registered.
- finder evidence (unverified): probe_expect.py printed 10/10 'MISMATCH request .../img0.png response .../img7.png' (one ...img6.png) and 69 InvalidStateError('invalid state') loop errors.
- finder repro idea: Run a local server whose page has 8 <img> tags matching the pattern. Loop 10 times comparing (await req.request).url to (await req.response).url.

### A10.1: Request/response expectation pairs the request with the wrong response when matching events arrive in a burst (request_id overwritten by a second handler task)
- where (may drift): zendriver/core/expect.py:BaseRequestExpectation._request_handler:44
- finder severity: wrong-result
- claim: `async with tab.expect_request(r'.*/img\d+\.png') as exp: await tab.get(page_with_many_images)`, then `await exp.request` and `await exp.response` (or `response_body`). Listener.listener_loop starts every callback with asyncio.create_task and drains queued inbox messages without yielding. So several matching Network.requestWillBeSent events each get their own _request_handler task before the first one runs and removes the handler. Task 1 sets request_id=A and resolves request_future with A. Task 2 then sets request_id=B (line 44) before set_result raises InvalidStateError. From then on _response_handler and _loading_finished_handler match request B. `exp.request`/`RequestExpectation.value` return request A while `exp.response`, `ResponseExpectation.value` and `response_body` return B's response and body. Each extra task also ends in an unretrieved InvalidStateError. DownloadExpectation._handler (line 206) and BaseFetchInterception._response_handler (intercept.py:35) use the same self-removing pattern and get the same InvalidStateError tasks on bursts. examples/wait_for_page.py uses exactly this kind of broad pattern (`https://github.githubassets.com/assets/.*`).
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_expect_race.py against real headless Chromium: 8/8 trials mismatched (e.g. `request: img0.png?t=0 response: img15.png?t=0 MISMATCH`), and the loop exception handler logged 89 `InvalidStateError('invalid state')`. Code path traced: connection.py Listener.listener_loop calls `asyncio.create_task(callback(*args))` for each event, and _receive_message uses `self._inbox.get()`, which returns without suspending while items are queued.
- finder repro idea: Serve a page with 40 <img src=/imgN.png?t=..>. Inside `tab.expect_request(r'.*/img\d+\.png\?t=.*')`, compare `(await exp.request).url` with `(await exp.response).url`, and install a loop exception handler to count InvalidStateError.

### B15.9: expect_request/expect_response: two matching requests in one burst cause InvalidStateError in a handler task and make .response/.response_body belong to a different request than .request
- where (may drift): zendriver/core/expect.py:BaseRequestExpectation._request_handler:44
- finder severity: wrong-result
- claim: `async with tab.expect_response(r'.*\.json') as exp:` while the page fires two matching fetches together, e.g. Promise.all([fetch('a.json'), fetch('b.json')]). Both Network.requestWillBeSent events are drained back-to-back. On Python 3.12+, wait_for/Queue.get do not yield when data is already buffered. The listener schedules _request_handler twice before the first task can call _remove_request_handler. Task 1 sets request_id=R1 and resolves request_future. Task 2 overwrites request_id=R2, then set_result raises InvalidStateError ('Task exception was never retrieved'). response_future then resolves with R2's ResponseReceived, so exp.request is a.json but exp.response/response_body are b.json. DownloadExpectation._handler and BaseFetchInterception._response_handler have the same unguarded set_result.
- finder evidence (unverified): probe_expect_race.py (py3.13.16) printed: 'expectation .request url : http://x/a.json', 'expectation .response url: http://x/b.json | request_id: R2', "unhandled task errors: [\"InvalidStateError('invalid state')\"]". Not yet probed on 3.10/3.11, where wait_for's inner task may yield and hide the race.
- finder repro idea: Run a fake CDP peer that, after one reply, sends requestWillBeSent(R1,a.json), requestWillBeSent(R2,b.json), responseReceived(R1), responseReceived(R2) in one burst. Await exp.request and exp.response and compare the URLs. Probe: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-B15/probe_expect_race.py

### B16.8: expect_request/expect_response mix two requests: request is the first match, response and body are the last, and the handler task raises InvalidStateError
- where (may drift): zendriver/core/expect.py:BaseRequestExpectation._request_handler:44
- finder severity: wrong-result
- claim: async with tab.expect_request(r'.*/data\?n=.*') as exp: await tab.get(page that starts 5 fetches at once). The Listener drains the session inbox without yielding and creates one handler task per RequestWillBeSent before any task runs, so _request_handler runs once per matching request. Self-removal does nothing for tasks already created. The first task sets request_future. Each later task overwrites self.request_id and then raises InvalidStateError from set_result. As a result exp.value/exp.request returns request n=0, while exp.response, response_body and loading_finished match request_id n=4. The user gets one request's headers together with another request's response and body. expect_response has the same mismatch.
- finder evidence (unverified): Probe p6_expect.py, five trials: 'request.url=data?n=0 response.url=data?n=4 body='payload for /data?n=4' req_id=12211.2 exp.request_id=12211.6'. Result: 'mismatches 5'; the loop exception handler logged 20 InvalidStateError('invalid state').
- finder repro idea: Serve a page with 5 parallel fetch('/data?n=i') calls, then compare (await exp.value).request.url with (await exp.response).url and record loop exception-handler calls.
