# Group R14 (temp-profile-lifecycle)

queue: report  |  triage severity: leak  |  triage fix kind: local

## Claim
Config.__repr__ (and Browser.__init__'s eager debug formatting) materialises the lazy temp user_data_dir on the template, so browsers started from one Config share a profile (the second fails and its stop() deletes the first one's live profile); failed starts leak temp profiles

## Files
zendriver/core/config.py (__repr__, user_data_dir), zendriver/core/browser.py (__init__ debug log, _stop early return)

## Triage fix strategy (a hypothesis, not a requirement)
Keep __repr__ from creating the dir; make the debug log lazy; clean the temp profile on the early-return path of _stop.

## Triage test approach
Browser-free for repr/leak; real Chromium for the shared-profile scenario.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A3.6: Browsers made from one Config share a single temp profile once its user_data_dir has been materialized (e.g. by print(config)); a failed browser then deletes the live browser's profile
- where (may drift): zendriver/core/browser.py:Browser.__init__ (deepcopy) / Browser._cleanup_temporary_profile:927
- finder severity: wrong-result
- claim: `config = zd.Config(headless=True); print(config)` (or `config()`, or reading config.user_data_dir). Then `b1 = await zd.start(config); b2 = await zd.start(config)`. Config.__repr__ calls the user_data_dir property getter, which runs mkdtemp on the template, and _custom_data_dir stays False. Browser.__init__ deep-copies the template, so every browser gets the same temp path and treats it as its own temporary profile. Chrome's process singleton hands b2's launch to b1's process, and b2 fails with 'Failed to connect to browser'. b2's failure path calls stop() -> _cleanup_temporary_profile(), which runs shutil.rmtree on the directory b1 is actively using. Without a failure, the first stop() of either browser deletes the profile of the other, still-running one.
- finder evidence (unverified): probe_shared_profile.py: 'template repr touches user_data_dir: True', 'b1 udd /tmp/uc_tjiysmh9', 'b2 failed: Exception [... Failed to connect to browser]', 'b1 still running: True b1 profile dir exists: False'.
- finder repro idea: `config = zd.Config(headless=True); repr(config); b1 = await zd.start(config)`. Then `zd.start(config)` raises. After that, `os.path.exists(b1.config.user_data_dir)` is False while b1 is still running.

### A9.3: repr(config), config() or reading config.user_data_dir creates a temp profile on the template Config, and every Browser started from it then shares that profile
- where (may drift): zendriver/core/config.py:Config.__repr__ / Config.user_data_dir:255
- finder severity: crash
- claim: config = zd.Config(headless=True); print(config) (or config(), which the docstring recommends for inspecting args, or reading config.user_data_dir). Then b1 = await zd.start(config); b2 = await zd.start(config). __repr__ calls getattr(self, 'user_data_dir') for each property. The lazy user_data_dir getter runs mkdtemp, stores the path in _user_data_dir and leaves _custom_data_dir False. Browser.__init__ deep-copies the config, so every copy now carries the same temp dir. The second Chrome sees the first one's profile lock, so b2 fails with 'Failed to connect to browser'. Because uses_custom_data_dir is False, b1.stop() rmtree's the shared profile. If the template is never used, repr alone leaves an orphan uc_* dir behind.
- finder evidence (unverified): Probe without repr: 'b1 udd /tmp/uc_3mi1my8l', 'b2 udd /tmp/uc__tzrmyar pid 8597 poll None'. Probe with repr(config): 'b1 udd /tmp/uc_0wkdq3ys', 'b2 start failed: Exception --- Failed to connect to browser ---', 'after b1.stop, profile exists? False'. A standalone probe also showed _user_data_dir going from None to /tmp/uc_egnia1dk after repr(), with a new temp dir created.
- finder repro idea: Probe probe_repr2.py: Config(headless=True); optionally call repr(config); start two browsers from the config with wait_for(60). Without repr both start with distinct dirs. With repr the second start raises 'Failed to connect to browser' and the profile is gone after b1.stop().

### B16.5: Printing or logging a template Config creates its temp user_data_dir, so browsers started from it share one profile; the second fails and its stop() deletes the first one's live profile
- where (may drift): zendriver/core/config.py:Config.__repr__:255
- finder severity: wrong-result
- claim: config = zd.Config(headless=True); print(config) (or logger.info('%s', config)); b1 = await zd.start(config); b2 = await zd.start(config). __repr__ calls getattr(self, k) on every property, including user_data_dir, whose getter runs mkdtemp and stores the path on the template. Config.__init__ deliberately defers this 'so config can be used/reused as a template for multiple browser instances', and test_multiple_browsers relies on that. After repr, every deepcopy carries the same path with _custom_data_dir False. Chrome's process singleton makes b2's Chrome exit, so zd.start raises 'Failed to connect to browser', and b2's stop() then rmtree's the profile directory that b1 is still using.
- finder evidence (unverified): Probe p3_repr.py: 'template before repr: None', 'template after repr: /tmp/uc_lygxj1ie custom? False', 'b2 start failed: Exception Failed to connect to browser', 'b1 profile dir still exists? False'.
- finder repro idea: Run repr(config), then start two browsers from that config and check os.path.isdir(b1.config.user_data_dir) after the second start fails.

### A3.7: Every Browser.create that fails before spawning Chrome (e.g. bad browser_executable_path) leaks a temp profile directory
- where (may drift): zendriver/core/browser.py:Browser.__init__ / Browser.start / Browser._stop:274
- finder severity: leak
- claim: `await zd.start(browser_executable_path='/nonexistent/chrome')` in a retry loop. Browser.__init__ runs `logger.debug("Session object initialized: %s" % vars(self))`. The % formatting happens even when debug logging is off. It calls Config.__repr__, which calls the user_data_dir getter, which runs mkdtemp. start() then raises FileNotFoundError at the executable check with no cleanup, and create() never returns the instance. Even if the caller held it, stop() -> _stop() returns early (`if not self.connection and not self._process: return`) before _cleanup_temporary_profile. Each failed call leaves one /tmp/uc_* directory behind.
- finder evidence (unverified): probe_exe_missing.py: 'temp profiles leaked by 3 failed starts: 3 ['/tmp/uc_6y2b1hkp', '/tmp/uc_jcsk9199', '/tmp/uc_k388terb']'.
- finder repro idea: Call `zd.start(browser_executable_path='/nonexistent/chrome')` three times, catching FileNotFoundError each time, and diff glob('/tmp/uc_*') before and after.

### B16.6: Temp profile dir leaks when start() fails before launch (bad executable) or cannot connect to an existing browser
- where (may drift): zendriver/core/browser.py:Browser._stop / Browser.__init__:875
- finder severity: leak
- claim: (a) zd.start(browser_executable_path='/nonexistent/chrome'): Browser.__init__ runs `logger.debug('Session object initialized: %s' % vars(self))` (line 274). The string is formatted even when debug logging is off, which runs Config.__repr__ and creates a uc_* directory. start() then raises FileNotFoundError and nothing removes the directory. (b) zd.start(host='127.0.0.1', port=<nothing listening>): start() calls self.config() (creating the temp dir), cannot connect, and calls self.stop(). _stop returns early at `if not self.connection and not self._process: return`, which skips _cleanup_temporary_profile. Each failed attempt (for example a retry loop) leaks one directory.
- finder evidence (unverified): Probe p1_leak.py: after the FileNotFoundError, one uc_g8d2vmf5 directory existed; after the 'Failed to connect to browser' attempt on port 1, a second one (uc_v76fong7) existed.
- finder repro idea: Set TMPDIR to an empty directory, attempt both failing starts, and list uc_* afterwards.
