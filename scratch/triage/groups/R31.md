# Group R31 (download-state)

queue: design  |  triage severity: hang  |  triage fix kind: design

## Claim
Download behaviour is browser-context-wide but tracked per Tab and sent without browser_context_id/events_enabled: download_file inside expect_download disables download events (ex.value hangs); context tabs ignore set_download_path; one tab's download_file/expect_download clobbers another tab's path

## Files
zendriver/core/tab.py (set_download_path, download_file), zendriver/core/expect.py (DownloadExpectation)

## Triage fix strategy (a hypothesis, not a requirement)
Design: track download behaviour per browser context.

## Triage test approach
Real Chromium.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A7.2: set_download_path / download_file / expect_download ignore the tab's browser context, so they do nothing for tabs from Browser.create_context()
- where (may drift): zendriver/core/tab.py:Tab.set_download_path:1595
- finder severity: hang
- claim: `ctx_tab = await browser.create_context(url)`, then `await ctx_tab.set_download_path(d)`, then clicking a download link. Browser.setDownloadBehavior is sent without browser_context_id. Chrome then applies it to the DEFAULT browser context, not the context the tab belongs to. The download is not saved to d (or anywhere). DownloadExpectation.__aenter__/__aexit__ use the same call, so `async with ctx_tab.expect_download() as ex: click(); await ex.value` never gets DownloadWillBegin and hangs. Meanwhile those calls change the download behaviour of the default context (other tabs) instead.
- finder evidence (unverified): Probe3 output: `1 set_download_path on ctx tab, click: []`, `2 with browser_context_id, click: ['dirCtxExplicit/fromlink.txt']`, `3 DownloadWillBegin with browser_context_id: fromlink.txt`. Probe2: `ctx expect_download: TIMEOUT, no DownloadWillBegin`.
- finder repro idea: Probe3: create_context tab, set_download_path(dirCtx), click <a download>: no file. Sending the same command with browser_context_id=ctx_tab.target.browser_context_id saves the file and DownloadWillBegin fires.

### A7.3: download_file inside expect_download turns off download events, so ex.value hangs forever and the 'deny' is undone
- where (may drift): zendriver/core/tab.py:Tab.download_file / Tab.set_download_path:1418
- finder severity: hang
- claim: DownloadExpectation.__aenter__ sends setDownloadBehavior(deny, events_enabled=True). On a tab with no download path set, `async with tab.expect_download() as ex: await tab.download_file(url); await ex.value` makes download_file call set_download_path. That sends setDownloadBehavior(allow, path) WITHOUT events_enabled, which turns download events off. DownloadWillBegin is never sent, so `await ex.value` hangs forever. The file is also written to ./downloads although the expectation meant to deny it. Calling set_download_path inside the block has the same effect.
- finder evidence (unverified): Probe7 output: control link click -> `fromlink.txt`. Then `download_file in expect_download: DownloadWillBegin never delivered (would hang without wait_for)`, `files: ['downloads/x.txt']`, and `set_download_path inside expect_download: no event`.
- finder repro idea: Probe7: a fresh tab, `async with tab2.expect_download() as ex: await tab2.download_file(base+'/docs/data.txt','x.txt'); await asyncio.wait_for(ex.value, 5)` -> TimeoutError, and files show downloads/x.txt.

### A7.4: Download path is tracked per Tab but set browser-wide, so download_file on a second tab silently moves every download to ./downloads
- where (may drift): zendriver/core/tab.py:Tab.download_file:1415
- finder severity: wrong-result
- claim: `await tab_a.set_download_path('/my/dir')` sets Browser.setDownloadBehavior for the whole (default) context, but records it only in tab_a._download_behavior. Then `tab_b = await browser.get(url, new_tab=True)` and `await tab_b.download_file(u, 'b.txt')`. tab_b sees no _download_behavior, warns 'no download path set', and resets the browser-wide path to cwd/downloads. From then on tab_a's downloads also land in ./downloads instead of /my/dir. DownloadExpectation.__aexit__ restores from the one tab's _download_behavior the same way, so it also clobbers a path another tab set.
- finder evidence (unverified): Probe2 output: warning `no download path set, so creating and using a default of.../work2/downloads`, then `after tab_a link click (tab_a set dirA): ['downloads/b.txt', 'downloads/fromlink.txt']`, so dirA got nothing.
- finder repro idea: Probe2: tab_a.set_download_path(dirA), tab_b.download_file(...), then click a download link in tab_a. The file appears in downloads/, not dirA.

### A10.6: expect_download() on one tab silently undoes another tab's set_download_path, because __aexit__ restores the browser-wide download behavior from its own tab's cached value
- where (may drift): zendriver/core/expect.py:DownloadExpectation.__aexit__ (state captured in __init__):227
- finder severity: wrong-result
- claim: `await tab_b.set_download_path(dir_b)` makes Browser.setDownloadBehavior allow downloads into dir_b, and that setting is browser-context-wide. Later `async with tab_a.expect_download(): ...` on a tab that never called set_download_path captured default_behavior='default' and download_path=None. On exit it sends Browser.setDownloadBehavior(behavior='default') for the whole browser context. tab_b._download_behavior still says ['allow', dir_b], so tab_b.download_file() skips set_download_path, and the next download goes to ~/Downloads instead of dir_b, with no error.
- finder evidence (unverified): Probe /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/detect-A10/probe_download.py: `after first download in tab B: ['first.bin']`, `tab_b._download_behavior still: ['allow', '.../dl_b']`, `after second download in tab B: ['first.bin']`. second.bin (14 bytes, written seconds earlier) appeared in ~/Downloads instead; I removed that stray file afterwards.
- finder repro idea: Two tabs. Tab B: set_download_path(tmpdir) and download_file('/file1'), which lands in tmpdir. Then `async with tab_a.expect_download(): pass`. Then tab B: download_file('/file2') and list tmpdir.

### B16.9: DownloadExpectation restores the browser-wide download behavior from per-tab state, wiping another tab's set_download_path
- where (may drift): zendriver/core/expect.py:DownloadExpectation.__aexit__:229
- finder severity: wrong-result
- claim: await tab1.set_download_path(dir) records the setting only on tab1 as tab1._download_behavior. Then tab2 = await browser.get(url, new_tab=True); async with tab2.expect_download(): click a download link. Browser.setDownloadBehavior applies to the whole browser context, but __init__ reads tab2._download_behavior (None), so __aexit__ resets the context to behavior='default' with no path. tab1._download_behavior still says ['allow', dir], so tab1.download_file() skips re-applying it, and tab1's downloads silently go to ~/Downloads instead of dir. Element.record_video sets 'allow' without updating _download_behavior, so its state also drifts.
- finder evidence (unverified): Probe p10_download.py: before the expectation, 'before.bin' landed in dl_target. Afterwards 'tab1._download_behavior still says: ['allow', .../dl_target]', but the dl dir held only ['before.bin'] and after.bin appeared in ~/Downloads (removed after the probe).
- finder repro idea: Call set_download_path on tab1, run expect_download on tab2, then tab1.download_file(...) and list dir and ~/Downloads.
