# Group R36 (find-text-semantics)

queue: report  |  triage severity: wrong-result  |  triage fix kind: local

## Claim
find_elements_by_text result semantics: duplicates when attribute and text both match; tag_hint ignored; return_enclosing_element ignored; iframe query errors print()ed and dropped by select_all(include_frames=True)

## Files
zendriver/core/tab.py (find_elements_by_text, find_element_by_text, query_selector_all)

## Triage fix strategy (a hypothesis, not a requirement)
Dedup by backend id; honour tag_hint/return_enclosing_element; log/raise instead of print.

## Triage test approach
Real Chromium.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A6.4: find_elements_by_text/find_all return the same element several times (no dedup when an attribute and the text both match, or when the element has several matching text nodes)
- where (may drift): zendriver/core/tab.py:Tab.find_elements_by_text:714
- finder severity: wrong-result
- claim: <button title='Login'>Login</button>: DOM.performSearch returns the BUTTON (attribute-value match) and its text node. The text node is replaced by its parent, so the BUTTON goes into `items` twice. Likewise <p>needle <b>x</b> needle</p> has two matching text nodes and the same <p> is added twice. await tab.find_all('Login') returns [button, button], so callers that count or iterate the results get double counts and act twice (e.g. clicking every result).
- finder evidence (unverified): probe9.py: "find_all Login: [('button', BackendNodeId(7)), ('button', BackendNodeId(7))]" and "find_all needle: [('p', BackendNodeId(9)), ('p', BackendNodeId(9))]".
- finder repro idea: Page: <button title="Login">Login</button><p>needle <b>x</b> needle</p>; r = await tab.find_all('Login'); assert len({e.backend_node_id for e in r}) == len(r)  # fails.

### A6.10: find_elements_by_text ignores its documented tag_hint parameter
- where (may drift): zendriver/core/tab.py:Tab.find_elements_by_text:684
- finder severity: wrong-result
- claim: The docstring says 'tag_hint: when provided, narrows down search to only elements which match given tag eg: a, div, script, span', but tag_hint is never referenced in the function body. await tab.find_elements_by_text('needle', tag_hint='a') returns <p> as well as <a>, and scripts/meta etc. elsewhere, so callers relying on the filter act on the wrong element.
- finder evidence (unverified): probe1.py: "[find_elements_by_text tag_hint=a] OK -> [<p id="p1">Hello needle world</p>, <a href="#">needle link</a>]   tags: ['p', 'a']". grep shows tag_hint only in the signature and docstring (tab.py lines 684, 692).
- finder repro idea: Page <p>Hello needle world</p><a href='#'>needle link</a>: r = await tab.find_elements_by_text('needle', tag_hint='a'); assert all(e.tag == 'a' for e in r)  # fails, returns ['p','a'].

### A5.10: find(return_enclosing_element=False) is ignored: the enclosing element is always returned
- where (may drift): zendriver/core/tab.py:Tab.find / Tab.find_element_by_text:795
- finder severity: wrong-result
- claim: `await tab.find('top paragraph', return_enclosing_element=False)` returns the <p> element (node_type 1), not the matched text node. find passes return_enclosing_element to find_element_by_text, but find_element_by_text never uses it: it calls find_elements_by_text(text), which always replaces text-node hits with their parent. The find docstring says this flag selects between the text node and its container.
- finder evidence (unverified): Probe: '[find return_enclosing False] -> <p id="topp">top paragraph</p>  node_type 1 P'. grep shows return_enclosing_element only in signatures and docstrings (tab.py 263/277/291/303/309/780/791), never read in a body.
- finder repro idea: r = await tab.find('top paragraph', return_enclosing_element=False); assert r.node_type == 3 fails because it is 1/P. Probe: scratchpad/detect-A5/probe1.py.

### A6.11: find_element_by_text (and so find()) ignores return_enclosing_element; return_enclosing_element=False still returns the parent element
- where (may drift): zendriver/core/tab.py:Tab.find_element_by_text:780
- finder severity: wrong-result
- claim: Tab.find documents return_enclosing_element=False as the way to get the matched node itself instead of its enclosing element, and it forwards the flag to find_element_by_text. find_element_by_text never reads the parameter, and find_elements_by_text always replaces text nodes with their parent (lines 734-740). So await tab.find('x', return_enclosing_element=False) behaves exactly like True: the flag does nothing, and there is no way to get the matched text node.
- finder evidence (unverified): Code trace: find() calls find_element_by_text(text, best_match, return_enclosing_element) at tab.py:302/308. find_element_by_text (lines 776-814) calls find_elements_by_text(text) and never references return_enclosing_element. find_elements_by_text unconditionally appends `elem.parent or elem` for node_type==3.
- finder repro idea: Page <p>needle</p>: el = await tab.find('needle', return_enclosing_element=False); expected the text node (node_type 3), got <p>. grep shows return_enclosing_element is never used inside find_element_by_text.

### A5.6: select_all/select(include_frames=True) silently return partial results: iframe-document query errors are print()ed and dropped, and the stale retry drops the iframe documents entirely
- where (may drift): zendriver/core/tab.py:Tab.query_selector_all (_include_frames branch):572
- finder severity: wrong-result
- claim: `select_all('div', include_frames=True)` should return div#top (main document) and div#inner (same-origin iframe). Two paths lose the iframe matches. (1) A per-content-document DOM.querySelectorAll that fails (stale id after another getDocument, or the iframe document being swapped) hits `except Exception as e: print(f'Exception in new content doc ids loop {e}')`: the error goes to stdout and those matches are dropped. (2) When the main-document query is stale, the retry calls `self.query_selector_all(selector, doc, ...)` with `_node=doc`, and content_doc_nodes are collected only when `not _node`, so the retry ignores all iframes. In both cases the main-document matches make `items` non-empty, so select_all/select return immediately with an incomplete list and never retry. Running 6 select_all('div', include_frames=True) concurrently gave 6 one-element lists.
- finder evidence (unverified): Probe: 'lens [1, 1, 1, 1, 1, 1]' for the concurrent calls against '[sequential select_all ...] -> [<div id="top">..., <div id="inner">...]'. Stdout showed three 'Exception in new content doc ids loop Could not find node with given id ... DOM.querySelectorAll' lines. The same print also appears on a plain select('#inner', include_frames=True) right after page load.
- finder repro idea: Page with div#top and a same-origin iframe holding div#inner; res = await asyncio.gather(*(tab.select_all('div', include_frames=True) for _ in range(6))); every len(r) is 1, not 2, and 'Exception in new content doc ids loop Could not find node with given id' is printed. Probe: scratchpad/detect-A5/probe4.py.
