### A11.2: verify_cf raises 'Error checking input element' when the solved challenge navigates away, which is the normal Cloudflare success path
- where (may drift): zendriver/core/cloudflare.py:verify_cf.check_input:239
- finder severity: wrong-result
- claim: `await tab.verify_cf()` on a Cloudflare interstitial: the click solves the challenge, and the challenge page reloads or redirects to the real site during the click_delay sleep. The next check_input call runs `await input_el` (Element.update) before it queries for a fresh input. update() calls DOM.resolveNode with the old backendNodeId, and that now fails ('Node with given id does not belong to the document'). The `except Exception` at line 241 turns this into a bare `Exception('Error checking input element: ...')`. So the success branch the code intends ('if the input disappears ... assume it's successfully completed', `not fresh_input`) can never be reached when the input disappears through navigation. The caller gets an exception after a successful solve.
- finder evidence (unverified): Real Chromium probe (scratch cf_probe.py). MODE navigate -> verify_cf raised Exception("Error checking input element: Node with given id does not belong to the document\ncommand:DOM.resolveNode\nparams:{'backendNodeId': BackendNodeId(9)} [code: -32000]."), and the final url was /solved, so the challenge was solved. Control cases: MODE value (the input gets a value) -> returned OK after 1.02s; MODE remove (input.remove() with no navigation) -> returned OK.
- finder repro idea: Serve a page with a closed shadow root whose child div has data-src='https://challenges.cloudflare.com/x', a document-level <input type=hidden name=cf-turnstile-response>, and a click listener on the div that sets location.href='/solved'. Call tab.verify_cf(click_delay=1, timeout=10).

### A11.3: Forwarder leaks tunnels to an authenticated https:// upstream after Chrome closes the connection, because the close is never passed upstream
- where (may drift): zendriver/core/proxy.py:copy_stream / pipe:312
- finder severity: leak
- claim: Call browser.create_context(proxy_server='https://user:pass@proxy:443'), browse, then let Chrome close a tunnelled connection (tab or context closed, idle socket dropped). copy_stream(client->upstream) reads EOF and calls write_eof() only if writer.can_write_eof(). An asyncio SSL transport returns False there, so the upstream proxy is never told and the tunnel stays up. pipe() gathers both directions, so it keeps waiting for upstream->client to reach EOF. Meanwhile the _handle_client task, the half-open client socket, the TLS upstream socket, the upstream proxy's tunnel and the origin connection all stay alive until the remote side times out (minutes for TLS or HTTP/2 origins, since Chromium does not send close_notify). With an http:// or socks5 upstream the FIN is forwarded and everything is torn down at once. Long scraping sessions through https proxies pile up these connections.
- finder evidence (unverified): Scratch proxy_probe.py: 'tls=False: forwarder client tasks still alive 2s after client closed: 0' and 'tls=True: forwarder client tasks still alive 2s after client closed: 1', with the same fake proxy and origin in both runs. The only difference is the TLS upstream.
- finder repro idea: Run a TLS CONNECT proxy (self-signed cert) whose origin closes on EOF. Build ProxyForwarder(UpstreamProxy.from_url('https://u:p@127.0.0.1:port', insecure_ctx)), open a CONNECT tunnel, close the client socket, sleep 2s, then check len(forwarder._client_tasks).

### A11.7: Proxy forwarder drops the client connection without an HTTP error, and logs an unhandled-exception traceback, when encoding or parsing raises something other than ProxyError
- where (may drift): zendriver/core/proxy.py:ProxyForwarder._handle_client:235
- finder severity: cosmetic
- claim: _handle_client turns only ProxyError into an HTTP error response, and silently handles only OSError, IncompleteReadError and LimitOverrunError. With a socks5 upstream, a CONNECT or GET to a host that has a DNS label over 63 characters or an empty label (e.g. 'a..b.com') makes encode_socks5_address raise UnicodeError from host.encode('idna') (line 337). open_tunnel re-raises it unchanged, _handle_client lets it escape, the client gets an empty response instead of the 502 used for every other upstream failure, and asyncio logs 'ERROR asyncio: Unhandled exception in client_connected_cb' with a full traceback. ValueError from urlsplit or url.port on malformed targets (non-CONNECT path, line 263/274) goes the same way.
- finder evidence (unverified): Scratch proxy_probe.py: 'LOG ERROR asyncio: Unhandled exception in client_connected_cb ... UnicodeEncodeError: 'idna' codec can't encode characters in position 0-63: label too long' and 'long-label CONNECT response: b'''. Expected was 'HTTP/1.1 502 Proxy Error'.
- finder repro idea: With a socks5 upstream forwarder, send `CONNECT {'a'*64}.example.com:443 HTTP/1.1\r\n\r\n` and read the response.

### A11.9: open_tunnel reports a timed-out proxy handshake as 'proxy closed the connection' because TimeoutError is an OSError subclass
- where (may drift): zendriver/core/proxy.py:UpstreamProxy.open_tunnel:112
- finder severity: cosmetic
- claim: On Python 3.11+, asyncio.TimeoutError is the builtin TimeoutError, which subclasses OSError. The isinstance(e, (OSError, IncompleteReadError)) check at line 112 therefore matches first, and the `isinstance(e, asyncio.TimeoutError)` branch at line 114 can never run. When an upstream proxy accepts TCP but never answers CONNECT or the SOCKS handshake within TIMEOUT, the warning logged by _handle_client says 'proxy closed the connection: TimeoutError()' instead of 'timed out waiting for the proxy', which misleads anyone debugging a slow proxy. The status (502) is the same.
- finder evidence (unverified): Scratch proxy_probe.py on Python 3.13.16: 'handshake timeout -> 'proxy closed the connection: TimeoutError()''.
- finder repro idea: Set zendriver.core.proxy.TIMEOUT=0.5 and point UpstreamProxy at a server that accepts and never replies. Call open_tunnel('example.com', 443) and print str(ProxyError).
