### A4.5: Browser.get raises TimeoutError for navigations that never commit (204 No Content, downloads), while Tab.get returns normally
- where (may drift): zendriver/core/browser.py:Browser.get (get_handler / wait_for_navigation):422
- finder severity: wrong-result
- claim: `await browser.get('https://host/file.zip')`, where the server answers with Content-Disposition: attachment (or returns 204). Page.navigate completes without committing a new document, so Chrome emits no Target.targetInfoChanged with the new URL. wait_for_navigation never sees the target id, and get() raises TimeoutError after the full timeout (10s by default). Page.navigate itself only replies once the response arrives (measured at 2.01s against a server that waits 2s before answering), so the extra wait adds only this failure mode. Tab.get(url) returns normally in 0.11s for the same URL.
- finder evidence (unverified): Probe scratchpad/detect-A4/get204_probe.py printed: 'get(page): OK in 0.02s', 'get(204): TimeoutError after 3.01s', 'get(download): TimeoutError after 3.01s', 'tab.get(204): OK in 0.11s'. Probe early_probe.py showed that a raw Page.navigate to a server answering after 2s replied after 2.01s, with location already updated.
- finder repro idea: Run a local http.server with /204 (send_response(204)) and /dl (Content-Disposition: attachment). Call `await browser.get(B+'/204', timeout=3)` and `await browser.get(B+'/dl', timeout=3)`, and compare with `await browser.tabs[0].get(B+'/204')`.
