# Group R22 (session-attach-races)

queue: report  |  triage severity: hang  |  triage fix kind: local

## Claim
Session attach/detach ordering: a reply arriving in the same burst as Target.detachedFromTarget is discarded; cancelling the first command during attach leaks a Chrome-side session; a detachedFromTarget processed before _attach_session registers the session is dropped and later sends hang

## Files
zendriver/core/connection.py (_attach_session, _detach_session, _receive_message)

## Triage fix strategy (a hypothesis, not a requirement)
Register the session before/atomically with the attach reply and drain the inbox before dropping it.

## Triage test approach
Fake peer sending reply+detach back-to-back.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### A1.5: A successful session reply that arrives in the same burst as Target.detachedFromTarget is discarded and the caller gets 'target session was detached'
- where (may drift): zendriver/core/connection.py:Connection._detach_session (called from _receive_message):489
- finder severity: wrong-result
- claim: tab.send(cmd) on a flat session where the command makes the target go away (closing a page or popup through its own session, an OOPIF disappearing), or a reply and the detach that are simply buffered together under load. The browser listener routes the reply into session._inbox with put_nowait. It then reads the next buffered frame without yielding, because wait_for awaits the coroutine inline and websockets returns buffered frames immediately. That frame is Target.detachedFromTarget, so _receive_message calls session._detach_session(). That sets self._inbox = None, which drops the queued reply, and fails every pending tx with ProtocolException('target session was detached'). The command succeeded in Chrome, but the caller sees a failure. The comment in Tab.close ('sent through the browser session, since this tab's own session may be detached before chrome responds') works around exactly this for close_target, but every other session command is still exposed. A fix would drain the inbox (or deliver the detach through the inbox) before failing the pending txs.
- finder evidence (unverified): probe_detach_race.py (owner stub plus session Connection, unique session id per attach) printed 'evaluate replied successfully by chrome: 20; caller saw success: 0, saw ProtocolException: 20 / example error: target session was detached'. The control probe_detach_race_delay.py, with a 50ms gap between reply and detach, printed 'caller saw success: 20, saw ProtocolException: 0'. On real Chromium with page.close / target.close via the session, the frames arrived separately in 6 trials, so the bug did not show there.
- finder repro idea: Run a fake peer whose Runtime.evaluate handler sends the reply (with sessionId) and then immediately Target.detachedFromTarget for that session. tab.send(runtime.evaluate('1+1')) then raises ProtocolException. Adding a 50ms gap between the two frames makes it succeed.

### A1.6: Cancelling the first command on a fresh tab during attach leaks a Chrome-side CDP session that is never detached
- where (may drift): zendriver/core/connection.py:Connection._attach_session:467
- finder severity: leak
- claim: tab = await browser.get(url, new_tab=True) (the tab is not attached yet). Then asyncio.wait_for(tab.evaluate('1+1'), small_timeout), or any timeout or cancel that hits the first send. _attach_session has already sent Target.attachToTarget and is awaiting the reply when it is cancelled. Chrome creates the session, but self.session_id is never set and the id is never recorded in browser_connection._sessions. The next send attaches a second session. tab.aclose() and Browser.stop() later detach only the recorded session, so the orphaned DevTools session stays attached in Chrome until the browser websocket closes. Each timed-out first command leaks one.
- finder evidence (unverified): probe_orphan_session.py on real headless Chromium printed 'tab session after timeout: None attached events so far: [SessionID('0784...')]', then 'attached: [0784..., F341...]', 'detached after tab.aclose(): [F341...]', 'orphan sessions (attached, never detached): [SessionID('078467FA91818147B95CF37E0B413ABE')]'.
- finder repro idea: On real Chrome, add handlers for target.AttachedToTarget and DetachedFromTarget on browser.connection. Open a new tab, time out its first evaluate after 2ms, evaluate again, call tab.aclose(), then compare the attached and detached session ids.

### B14.7: _attach_session registers the session only after the attach reply, so a detachedFromTarget in the same batch is dropped and every later send on the tab hangs
- where (may drift): zendriver/core/connection.py:Connection._attach_session:474
- finder severity: hang
- claim: tab.send(...) on a target that is being destroyed: for example an OOPIF from get_frames() whose iframe is removed, or a tab closed concurrently. aopen -> _attach_session awaits browser_connection.send(Target.attachToTarget). Chrome sends the attach reply and then Target.detachedFromTarget for the new session. On Python >= 3.12 the browser listener handles both buffered frames before _attach_session resumes. _receive_message finds no entry in _sessions for that id, so the detach is ignored. Then _attach_session registers browser_connection._sessions[sid] = self and keeps session_id=sid. Every later command on the tab goes out with the dead sessionId. Chrome's reply for an unknown session carries no sessionId (verified against real Chromium: {"id":4,"error":{"code":-32001,"message":"Session with given id not found."}}). The reply is therefore routed to the browser connection, whose mapper does not contain the id, and silently dropped. tab.send has no timeout of its own, so this send and every later send on that tab hang forever.
- finder evidence (unverified): probe_attach_race.py (fake server): delay=0 printed 'HANG - send never completed; session_id=S1 registered=[S1] browser mapper=[] tab mapper=[2]' and 'second send also HANGS'. delay=0.2 printed 'ProtocolException: target session was detached' for both sends. probe_unknown_session.py confirmed that real Chromium answers commands on unknown or detached sessions with no sessionId field. Medium confidence because, against real Chrome, the trigger needs the detach to land in the same read as the attach reply; 15 concurrent close+evaluate attempts on real Chrome did not hit it.
- finder repro idea: A fake CDP server (websockets.serve) replies to Target.attachToTarget with {sessionId:'S1'}, sends detachedFromTarget for S1 immediately, and answers any message with a sessionId by an error without a sessionId, as Chrome does. Use a browser Connection plus a target Connection whose _owner.connection is it, then wait_for(tab.send(runtime.evaluate('1')), 3). It times out. With a 0.2s delay before the detach, it raises 'target session was detached' as it should.
