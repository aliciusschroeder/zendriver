## Lens: reproduce (verdict confirmed, realism high, severity hang)

### Summary
Reproduced every member with my own probes, on real headless Chromium 141 and on a browser-free fake CDP peer. (1) Browser._stop awaits Target.detachFromTarget (inside Connection.aclose, connection.py:517) and Browser.close (browser.py:883), and neither has a timeout. A frozen or unresponsive browser therefore makes stop() hang forever before it reaches terminate/kill. Bounding stop() with wait_for leaves the process alive and the profile on disk, and the atexit hook has already been unregistered, so nothing cleans up later. (2) If Chrome dies just before stop(), Connection.aclose raises ConnectionClosedError, because it only catches ProtocolException. The exception aborts _stop: _process stays set, the process is never reaped and the profile leaks. (3) Two concurrent stop() calls race in the terminate/poll loop and one raises AttributeError 'NoneType' object has no attribute 'poll' at _stop:901. (4) Under asyncio.run, the atexit cleanup always fails at `await asyncio.to_thread(self._process.wait)` (_stop:909) with RuntimeError('Executor shutdown has been called'), so the /tmp/uc_* profile leaks. This happens on Python 3.13 and 3.11, and also on the Ctrl+C path. Tab.close() also hangs well past the 10 s its docstring promises, stuck at Tab.close:1079 -> Connection.send.

### Refinements
- Root cause 1 (hang) has two independent unbounded awaits: the per-target Connection.aclose -> Target.detachFromTarget at connection.py:517, and Browser.close at browser.py:883. Either one alone hangs stop(), as the fake peer shows for each. A fix must bound both, or bound _stop's CDP phase as a whole, and must always fall through to terminate/kill. Tab.close has the same unbounded send at tab.py:1079 (Tab.close).
- Root cause 2: Connection.aclose's session branch catches only ProtocolException. Because the listener fails pending transactions with the ConnectionClosed instance itself (listener_loop, _fail_pending_transactions(e)), ConnectionClosedError escapes. It aborts _stop before Browser.close, proxy-forwarder close, terminate/reap and profile removal. The same exception also breaks the atexit path when Chrome has died (seen in the tabclose run: 'Unhandled exception in asyncio atexit callback ...: no close frame received or sent', leaving a zombie and the profile).
- A3.11: the race needs the two stop() calls to be offset (a stagger above a few ms). Simultaneous gather calls rarely hit it on real Chromium (0 of 8). The surviving call still removes the profile, so the impact is a spurious AttributeError, not a leak.
- A3.1/B16.3: only the profile leaks. The process is terminated and reaped by the poll loop before the to_thread call fails. `async with await zd.start()` does not stop the browser in __aexit__, so the documented examples always rely on this broken atexit path.
- stop() calls asyncio_atexit.unregister before _stop, so any hang or exception in _stop leaves nothing to clean up at exit.

## Lens: refute (verdict confirmed, realism medium, severity hang)

### Summary
I could not refute any member. All of them reproduce on real headless Chromium (Python 3.13.16, websockets 14.1). Q3 is really four separate defects in Browser.stop()/_stop()/_atexit_cleanup, and their realism differs a lot. (1) The atexit leak is deterministic and the most realistic. Under asyncio.run, _stop() reaches `await asyncio.to_thread(self._process.wait)` after Runner.close has already called shutdown_default_executor, gets RuntimeError('Executor shutdown has been called'), and skips _cleanup_temporary_profile. This hits every script that never calls stop(), including Ctrl+C. (2) The stop() hang needs the browser process itself to be wedged. Target.detachFromTarget (sent from Connection.aclose) and Browser.close are sent with no timeout, and both come before the terminate/kill fallback. If the caller bounds stop() with wait_for, Chrome is orphaned and the profile is left, because stop() unregistered the atexit hook first. (3) Connection.aclose catches only ProtocolException. A ConnectionClosedError escapes and aborts _stop when stop() starts before the listener has seen the socket close. (4) Concurrent stop() calls race on self._process and one of them raises AttributeError. The other call still cleans up.

### Refinements
Treat Q3 as four bugs that share one function. (a) Atexit leak: deterministic on Python 3.10+ (Runner.close calls shutdown_default_executor before loop.close) for any browser not stopped explicitly, including after Ctrl+C. Only the temp profile leaks plus the stderr message: Chrome is terminated and reaped. (b) Hang: only when the browser (main) process stops servicing DevTools: SIGSTOP or a frozen container/VM, a hung browser UI/IO thread, or a remote browser behind a silent network partition. A busy or infinite-looping renderer does NOT trigger it (verified). The stderr-pipe deadlock trigger is unlikely with the default flags, since only about 5 KB is written at startup (verified in this container). The keepalive bounds the wait at about 930 s, but stop() then raises ConnectionClosedError from aclose and still never terminates or kills Chrome. Cancelling stop() via wait_for orphans Chrome and the profile, because the atexit hook is already unregistered. (c) ConnectionClosedError escape: only if stop() starts before the listener has handled the socket close, i.e. within about 3-10 ms of browser death or after blocking synchronous work. A second stop() recovers. (d) Concurrent stop(): about 1 in 10 runs, only a spurious AttributeError in one caller, no leak. A fix must keep the healthy-path stop() fast and without kill (existing test asserts under 2 s and no kill).

## Lens: fixsafety (verdict confirmed, realism high, severity hang)

### Summary
I could not disprove any member; I reproduced all four failure modes in Browser._stop on the repo code. (1) An unresponsive browser makes stop() hang forever. The target.aclose() loop (Target.detachFromTarget, Connection.aclose:517) and the Browser.close send (_stop:883) have no timeout and run before terminate/kill. stop() has already unregistered the atexit hook (stop:870), so cancelling it with wait_for leaks the process and the profile. (2) If Chrome dies just before stop(), ConnectionClosedError escapes Connection.aclose (it only catches ProtocolException) and aborts _stop before terminate and profile cleanup. (3) Two stop() calls a little apart crash: one sets self._process=None while the other is in asyncio.sleep(0.25) and then calls self._process.poll() (_stop:901). (4) On the atexit path under asyncio.run, `await asyncio.to_thread(self._process.wait)` (_stop:909) raises RuntimeError('Executor shutdown has been called'), so the temp profile is left behind. A minimal fix in browser.py alone (about 30 lines) fixes all four. All 7 regression tests fail on the repo code and pass on the prototype under Python 3.13 and 3.11. The repo's own tests/core suite passes on the prototype, and mypy shows no new errors.

### Refinements
1) Unresponsive-browser stop() is bounded on the prototype but takes about 23 s (5 s detach + 5 s Browser.close + about 10 s websockets close_timeout on a frozen peer + 3 s terminate wait, then kill). The 10 s close_timeout part is inferred from the 23.2 s total, not measured on its own. It could be cut by skipping Browser.close once the detach step timed out, or by passing a smaller close_timeout to websockets.connect. This is optional. 2) A3.11 never reproduced with zero offset (0 of 9 runs, and the earlier finder saw 2 of 7). It is deterministic once the second stop() starts 50-200 ms later, as with a signal-handler task plus a finally block. Only the late call raises; the profile is still removed by the other call. 3) The B13.5 aside about Tab.close (close_target send outside the 10 s wait_for) is real from reading the code, but it is a separate method; fix it separately if wanted. 4) Pre-existing and unrelated, also on the repo code: a normal stop() leaves the Popen stdin/stdout/stderr pipes unclosed (ResourceWarning under -W default). The atexit path also warns that 'Connection.send_context async generator was scheduled after loop.shutdown_asyncgens()'. 5) Connection.aclose still lets ConnectionClosed escape for other callers such as `async with tab:` (Connection.__aexit__). The _stop fix does not depend on changing that.

- prototype: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/Q3-fixsafety/pkg
- regression test: /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/Q3-fixsafety/tests/test_q3_stop_cleanup.py
- fails on repo: yes; passes on prototype: yes; mypy ok: yes
- diff summary: zendriver/core/browser.py only (full diff in /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/Q3-fixsafety/fix.diff). (a) New module constant STOP_COMMAND_TIMEOUT = 5 (could be private). (b) _stop: replace `for target in self.targets: await target.aclose()` with `await asyncio.wait_for(asyncio.gather(*(t.aclose() for t in self.targets), return_exceptions=True), STOP_COMMAND_TIMEOUT)` inside `except asyncio.TimeoutError: logger.debug(...)`. This gives one budget for all targets, and per-target exceptions such as ConnectionClosedError are swallowed. (c) Wrap the Browser.close send in asyncio.wait_for(..., STOP_COMMAND_TIMEOUT); the existing broad except already covers the timeout. (d) Snapshot `process = self._process` and use the local for terminate/poll/kill, so a concurrent stop() setting self._process=None cannot break this one. (e) Remove `await asyncio.to_thread(self._process.wait)`: the break path is already reaped by poll(), and after kill() it uses `while process.poll() is None: await asyncio.sleep(0.05)`, which needs no default executor. (f) stop(): call `await self._stop()` first, then asyncio_atexit.unregister and registry discard, so a stop() that fails or is cancelled keeps the atexit fallback.
- risks: No locks are added, so there are no re-entrancy, deadlock or lock-ordering concerns. Cancellation still propagates: wait_for/gather re-raise CancelledError. Each aclose calls _detach_session() synchronously before its send, so a timeout leaves local session state consistent, and Connection.aclose() later fails or clears any pending browser-connection transactions. Behaviour changes callers would notice: (1) stop() of a hung browser now returns after about 23 s with a 'Could not send the close command' warning instead of hanging; (2) detaches run concurrently rather than one after another; (3) gather(return_exceptions=True) drops exceptions other than ProtocolException from aclose without logging them (suggest debug-logging the results); (4) after a stop() that fails or is cancelled, the atexit callback and its strong reference to the Browser stay until loop close, where _atexit_cleanup retries. That is intended, but it is new. (5) A slow but healthy Chrome that takes more than 5 s to answer Browser.close now gets terminate() early. On POSIX that is a graceful SIGTERM. On Windows terminate() is TerminateProcess, but it was already called right after the reply, so this is no worse. The post-kill poll loop is unbounded, like the old wait() (only matters for a D-state process). Python 3.10 compatibility: only wait_for, gather and asyncio.TimeoutError are used. I tested 3.13 and 3.11, not 3.10. Healthy-path stop time is unchanged (0.37 s), and the repo's test_browser_stop_exits_gracefully_without_kill still passes.
