# Group Q5 (stderr-pipe)

queue: fix  |  triage severity: hang  |  triage fix kind: local

## Claim
Chrome's stdout/stderr are PIPEs that nothing drains while the browser runs; once ~64 KiB accumulate Chrome blocks and every CDP call (and stop()) hangs. The startup-failure stderr capture also always returns empty while Chrome is alive

## Files
zendriver/core/util.py (_start_process, _read_process_stderr), zendriver/core/browser.py (start failure path)

## Triage fix strategy (a hypothesis, not a requirement)
Do not leave undrained pipes: send stdout to DEVNULL and stderr to a temporary file (or drain it) and read that for the failure message.

## Triage test approach
Real Chromium with --enable-logging=stderr and console spam -> evaluate keeps answering past 64 KiB of stderr; failure path still reports stderr content.

## Members (UNVERIFIED claims from Stage 1 finders or seeded leads; line numbers may be wrong; do not reuse their scripts)

### B13.4: Chrome's stdout/stderr are PIPEs that are never drained: once ~64 KiB of logs pile up, Chrome blocks and every CDP call (and stop()) hangs
- where (may drift): zendriver/core/util.py:_start_process:352
- finder severity: hang
- claim: zd.start() spawns Chrome with stdout=PIPE and stderr=PIPE. Nothing reads them during the session; only _read_process_stderr does, and only after start() fails to connect. Chrome logs ERROR lines to stderr. Default flags in a container already leave about 5 KB at startup (dbus errors), and each navigation that hits a certificate error adds about 370 bytes. When the 64 KiB kernel pipe buffer fills, the Chrome thread that logs blocks in write(2). From then on: (a) default flags: after about 157 bad-certificate navigations, Page.navigate is never answered, so tab.get / tab.send / find etc. hang; (b) with a common debugging flag such as browser_args=['--enable-logging=stderr','--v=1'], the browser process stops answering even Browser.getVersion within a few navigations, and browser.stop() hangs too (see the stop() finding). The user sees a browser that just stops responding, with no error.
- finder evidence (unverified): probe_pipe.py with --enable-logging=stderr --v=1: `pipe size 65536 stderr pending after start 44192` ... `iteration 5: TIMEOUT - stderr pending 64361` / `browser process does NOT answer Browser.getVersion` / `stop failed TimeoutError`. probe_pipe4.py with DEFAULT flags, navigating to a self-signed https://127.0.0.1 server: stderr grew 5073 -> 14145 -> 23073 -> ... -> 62046 bytes, then `iteration 157: navigate TIMEOUT stderr pending 64350 after 473s`. In normal navigation without errors (probe_pipe.py, default flags, 400 pages) stderr stayed at 5019 bytes, so the growth comes from Chrome's ERROR logging.
- finder repro idea: Start with browser_args=['--enable-logging=stderr','--v=1'], loop over tab.get(data-url) with a 10 s wait_for, and observe the TimeoutError after about 5 iterations while FIONREAD on browser._process.stderr reads about 64 KiB. Fix: spawn with stdout/stderr=DEVNULL (or a file / a drained reader task) and keep only a bounded tail for the failure message.

### B13.8: Startup-failure stderr capture always returns empty while Chrome is still running: blocking read(65536) cannot finish within the 0.25 s wait_for
- where (may drift): zendriver/core/util.py:_read_process_stderr:368
- finder severity: wrong-result
- claim: zd.start() cannot connect while Chrome stays alive, e.g. the DevTools port is taken ('Cannot start http server for devtools.') or Chrome needs more than browser_connection_max_tries*browser_connection_timeout (default 2.5 s) to open the port. Browser.start then calls _read_process_stderr, which runs process.stderr.read(65536) in a thread. Assert the logged stderr contains 'Cannot start http server for devtools'. Fix: read non-blocking / read1 / os.read of the bytes available, or drain stderr continuously.

## Lens: reproduce (verdict confirmed, realism high, severity hang)

### Summary
Confirmed on real headless Chromium 141 under Python 3.13.16. util._start_process (util.py ~L348-353) starts Chrome with stdout=PIPE and stderr=PIPE. The only reader of the stderr pipe is util._read_process_stderr, which Browser.start (browser.py ~L588-591) calls only on a failed connect. While the browser runs, nothing drains the pipe. When the 64 KiB pipe fills, the Chrome process that is logging blocks in anon_pipe_write and CDP stops answering. With --enable-logging=stderr this is the browser main process, so Runtime.evaluate, Browser.getVersion and Browser.stop() all hang. With default flags it is the network-service utility process, after about 188 navigations that hit a certificate error; Page.navigate is then never answered while Browser.getVersion still is. Draining the pipe from the test harness unblocks Chrome at once, and a control run that drains continuously never hangs, which proves the pipe is the cause. Separately, on a failed start with Chrome still alive, _read_process_stderr returns '' even though the pipe holds more than 5 KB, including 'Cannot start http server for devtools.'. Browser.start then logs 'Browser stderr: No output from browser'.

### Refinements
1) The hang does not need a full 64 KiB. A Linux pipe has 16 page slots, and small writes merge into a page only when they fit, so lines of about 2 KB fill the pipe at about 37 KB (B16.1 hangs at #15 with 36931 bytes). 2) Which process blocks depends on who logs. With --enable-logging=stderr the browser main process blocks, so every CDP call (including Browser.getVersion) and stop() hang. With default flags and TLS errors the network-service utility process blocks, so Page.navigate and other network work hang while browser-level CDP calls still answer. 3) stdout stayed at 0 bytes in every run; the problem in practice is stderr, though stdout is undrained too. 4) The stop() hang is a consequence and sits in Browser._stop -> target.aclose / Target.detachFromTarget, which has no timeout (overlaps the separate stop() finding). 5) B13.8: read(n) on a BufferedReader blocks until n bytes or EOF, so it returns content only once Chrome has exited. Fix direction, not tested: DEVNULL for stdout, and stderr to a temp file or a drain task that keeps a bounded tail; the failure path then reads that tail.

## Lens: refute (verdict confirmed, realism medium, severity hang)

### Summary
I could not refute this group. Browser.start (browser.py) spawns Chrome through util._start_process (util.py:348-355) with stdout=PIPE and stderr=PIPE. The only reader is util._read_process_stderr, and it runs only on the connect-failure path (browser.py:589). Real headless Chromium 141 writes ERROR lines to that pipe even with zendriver's default flags. Once the pipe's 16 page slots are full, the Chrome thread that logs blocks in write(2) (wchan anon_pipe_write). Draining the pipe immediately un-wedges it, and a control run with a drain thread never hangs. Default flags are enough in a GPU-less environment: about 160 page loads that each create a WebGL context hung tab.get, evaluate and screenshot. With --enable-logging=stderr, about 10 evaluates that do console spam freeze the browser process itself, including Browser.getVersion and browser.stop(). B13.8 also holds: while Chrome is still alive, _read_process_stderr's BufferedReader.read(65536) cannot finish within 0.25 s. It returns '' and zendriver logs 'No output from browser' even though the pipe holds the exact cause. That one only affects a diagnostic message.

### Refinements
- Effective capacity is 16 pipe pages, not 64 KiB of bytes. With small lines Chrome blocks at about 63-64 KB. With lines just over 2 KB it blocks at about 37 KB, because each write takes its own page.
- What hangs depends on which Chrome process logs first once the pipe is full:
  - Browser process (--enable-logging console messages): everything, including Browser.getVersion and stop(). stop() sits on Target.detachFromTarget with no timeout; that belongs to the stop() group.
  - GPU process (WebGL): rendering-dependent tab operations (tab.get, evaluate on that tab, screenshot). Browser.getVersion, new_tab and stop() keep working.
  - Network service (TLS errors): navigation and network only.
  Each process blocks only when it next logs, so the set of stuck operations grows over time.
- Default-flag triggers are per-event ERROR logs, not volume:
  - Each WebGL context in a GPU-less environment (Docker/CI/servers): about 390 B headless, about 136 B headful/Xvfb, so roughly 155 or roughly 440 such page loads.
  - Each failing TLS handshake: about 170 B.
  - console.log, normal pages, 404s, DNS failures and connection refused add nothing.
  - Idle growth is negligible (about 1.8 KB per 10 min).
  On a desktop with a real GPU the WebGL line is probably not emitted (assumed).
- With --enable-logging=stderr (a common debugging flag) the hang comes within seconds.
- stdout received 0 bytes in every run, so only stderr matters in practice. stdin=PIPE is harmless.
- Draining fully recovers Chrome, so a drain or a file is a complete fix.
- Python-version independent (kernel pipe semantics); I only ran 3.13.
- Windows release Chrome does not log to stderr without --enable-logging (assumed), so Linux (and probably macOS) is the main exposure.
- B13.8 applies only when Chrome is still alive at the failure: DevTools port race, or startup slower than about 2.5 s (default 10 x 0.25 s). The canonical root-without-sandbox and crash-at-start failures exit, hit EOF and are reported correctly. Its impact is a missing diagnostic line, which I rate cosmetic; the group's severity stays hang.

## Lens: fixsafety (verdict confirmed, realism high, severity hang)

### Summary
Confirmed on real headless Chromium 141 (Python 3.13). util._start_process (util.py:332-355) starts Chrome with stdout=PIPE and stderr=PIPE, and nothing reads them while Chrome runs. The only reader is _read_process_stderr (util.py:358), and it runs only on the connect-failure path in Browser.start (browser.py:588). Once the stderr pipe is full, Chrome's logging thread blocks in anon_pipe_write and CDP stops answering. This happens with --enable-logging=stderr after about 44 console.log calls, and with DEFAULT flags after about 183 navigations that fail the TLS handshake (about 288 B of ERROR log each). Separately, _read_process_stderr does a blocking read(65536) under wait_for(0.25). For a Chrome that is still alive this always times out, so Browser.start logs 'Browser stderr: No output from browser' even though Chrome wrote 'Cannot start http server for devtools.' to the pipe. A minimal local fix works: stdout=DEVNULL, plus a daemon thread that drains stderr and keeps only the last 64 KiB, which _read_process_stderr then returns. The browser-free regression tests fail on the repo code and pass on the prototype, the repo's real-browser tests pass on the prototype, and mypy reports no new errors.

### Refinements
Exact counts differ from the finders' numbers, but the mechanism is the same. In my runs Chrome blocked with 52-64 KiB pending (partial pages count against the 16-page pipe), not exactly 64 KiB. Default flags add about 288 B per TLS-failure navigation (finder: 370 B). Ordinary navigation and console spam without --enable-logging do not grow stderr. The stop() hang the finders mention after the pipe fills comes from the separate stop() issue: stop() sends Browser.close without a timeout. Fixing Q5 removes this trigger for it but not the underlying issue. B13.8 has a second, minor latent problem: the strict utf-8 decode in _read_process_stderr could raise UnicodeDecodeError on a read cut mid-character. The prototype decodes with errors='replace'.

- diff summary: zendriver/core/util.py only, diff saved at /tmp/claude-0/-home-user-zendriver/b2021b39-94e6-5220-9e66-7f33c0314a80/scratchpad/verify/Q5-fixsafety/fix.diff. (1) _start_process passes stdout=subprocess.DEVNULL instead of PIPE; stdin and stderr stay PIPE. After Popen it registers _stderr_tails[process] = _StderrTail(process.stderr). (2) New class _StderrTail: a daemon thread named 'zendriver-browser-stderr' loops `while chunk := os.read(stream.fileno(), 2**16)`, appends under a threading.Lock and trims with `del self._data[:-size]`, so at most 64 KiB is kept. It closes the stream itself at EOF and catches OSError/ValueError. Its async read(n, timeout) runs `await asyncio.to_thread(self._thread.join, timeout)` (0.25 s, the same budget as before) and returns the last n bytes. (3) Module-level `_stderr_tails: weakref.WeakKeyDictionary[Popen[bytes], _StderrTail]`. (4) _read_process_stderr returns the tail decoded with errors='replace' when the process is tracked. Untracked processes still go through the old read path. browser.py is unchanged.
- risks: Behaviour changes: (a) browser._process.stdout is now None; it was an unread pipe. (b) browser._process.stderr is now consumed by the drain thread, so a user reading it directly would race with the thread. Both attributes are private. (c) The failure log may now contain up to 64 KiB of Chrome noise, such as dbus errors, at INFO level; before, it said 'No output' for a live Chrome. (d) Chrome's stderr is still discarded during the session apart from the tail; forwarding it to logger.debug would be an optional addition.

Concurrency: one threading.Lock, held only for append/trim and the final copy. It is never held across an await, nothing else locks inside it, and no asyncio.Lock is involved, so there is no re-entrancy or lock-ordering hazard.

Cancel path: if Browser.start is cancelled during _read_process_stderr, the executor's join finishes within 0.25 s on its own. This is harmless.

Lifetime: one thread per launched browser, which exits at EOF once Chrome and its crashpad/zygote children exit; I verified this after stop(). An orphaned child that keeps the write end open keeps one daemon thread and one fd alive until it exits. The thread keeps its own reference to the stream and checks fileno() on every iteration, so the fd is not closed by GC and reused under it. Only an external process.stderr.close() racing with an in-flight read has a tiny window. If thread start fails (RuntimeError under resource exhaustion), Popen has already spawned Chrome, which is then orphaned; this edge case could be guarded.

Compatibility: no new mypy errors (332 errors in both the untouched and the prototype trees, all in cdp/; util.py reports 'Success: no issues found'). The code works on Python 3.10+ (walrus; annotation-only generic subscript under `from __future__ import annotations`; tested on 3.11 and 3.13), and os.read on the pipe fd also works on Windows.

Alternatives considered: DEVNULL-only would regress the exited-Chrome diagnostics that work today (test_stderr_of_an_exited_browser_is_read passes on the repo code). A temp file grows without bound under --enable-logging --v=1, and /tmp is often tmpfs.
