# Stage 3 verification of group Q1

Votes: reproduce=confirmed, refute=confirmed, fixsafety=confirmed. Survives: True.

## Lens: reproduce (verdict confirmed, realism high, severity hang)

### Summary
I reproduced all six members on Python 3.13.16 with websockets 14.1, using my own fake CDP peer and also real headless Chromium 141. Three things go wrong. (1) When Transaction.__call__ fails to parse a reply, the exception escapes Listener.listener_loop at the `tx(**message)` call, which has no try around it. The listener dies, and the Transaction it already popped from mapper is never resolved: send() hangs forever, and neither later sends nor aclose() release it. (2) An async handler whose arity is wrong raises TypeError synchronously in the callback dispatch. The code logs it and then re-raises on purpose, which kills the listener. (3) Any exception from _receive_message other than TimeoutError, CancelledError or ConnectionClosed (JSONDecodeError, KeyError, ConcurrencyError) also kills the listener without logging anything. In cases (2) and (3) the tx stays in mapper, so an in-flight send hangs until some later send() starts a new Listener. Once the browser connection's listener is dead, every send from a flat-session tab hangs: Tab.aopen/_attach_session returns early and never revives the parent's listener, so nobody reads the shared websocket.

### Refinements
Failure modes split by duration. Parse failures in Transaction.__call__ (A1.1/A2.3/B15.1) lose the tx permanently: it was popped from mapper, and neither later sends nor aclose() resolve it; only cancelling the caller ends it. Handler-raise (B15.4) and _receive_message exceptions (SEED-L1) leave the tx in mapper, so the in-flight send recovers at the next send() on that same connection (or fails at aclose). For a flat-session tab whose parent browser listener died (A2.4), tab sends do not help: only a browser-level send revives it. B15.4 applies only to coroutine-function handlers and is logged as a warning. SEED-L1 is silent, but I found no natural trigger for the ConcurrencyError or a non-JSON frame. Its realistic value is defensive, so its realism is lower than the parse-failure path, which has a historical Chrome-skew precedent (#245). Connection.wait() without t also hangs forever if the listener dies while idle is clear. Not tested: _inbox growth while a tab listener is dead.

## Lens: refute (verdict confirmed, realism medium, severity hang)

### Summary
I could not refute this group. Every member's mechanism reproduces on Python 3.13 and websockets 14.1, using a fake CDP peer, real headless Chromium 141, or both.

(1) Transaction.__call__ lets any non-StopIteration exception from the generated parser or a custom generator escape. The Listener.listener_loop call `tx(**message)` has no try around it, so the listener task dies. The Transaction was already popped from mapper, so its future is never resolved, and aclose()/_fail_pending_transactions cannot release it. The send() hangs permanently.

(2) In the listener_loop callback dispatch, the `raise` after logger.warning, plus the outer `except Exception: raise`, kill the listener when an async handler with the wrong arity is called.

(3) A flat-session Tab's aopen/_attach_session returns early once session_id is set. Its send() restarts only the tab's own inbox Listener. When browser.connection.listener is dead, nothing reads the shared websocket, and every tab command hangs until something sends on the browser connection.

(4) Any other exception from _receive_message (for example a JSONDecodeError) also kills the listener. I found no way for real Chrome to trigger this in the current code.

### Refinements
- Parse-failure hangs (A1.1/A2.3/B15.1) are permanent for the affected send: the tx was popped from mapper, so aclose() cannot fail it, and only the caller's own timeout ends the wait. Other in-flight commands are stuck only until the next send() on the same connection.
- With matched versions (Chromium 141 and the bundled cdp), common generated commands do not hit this (verified). It takes protocol skew, which has happened before (Chrome 146 sameParty), or a custom generator.
- ProtocolException('could not parse ...') is reachable only from custom generators that yield twice.
- B15.4 applies only to async callables (including partials of them) whose call raises synchronously. A hang needs a command whose reply is queued behind the triggering event. Tab.get is bounded at 10s.
- A2.4 is an amplifier: any death of the browser listener, from a handler, a skewed browser-level reply, or an unexpected receive exception, starves all tabs until a browser-level send.
- SEED-L1 has no real-Chrome trigger in the current code: the ConcurrencyError route was fixed by 31c92f1, nesting is capped by Chrome, and surrogates are escaped. The tx stays in mapper, so aclose() and later sends recover it unless the lost frame was the reply itself.
- The behaviour is not Python-version dependent; the RecursionError path is the only one that would be, and Chrome cannot reach it.

## Lens: fixsafety (verdict confirmed, realism high, severity hang)

### Summary
Confirmed: all four listener-robustness defects are real, and each needs its own fix. (1) Transaction.__call__ (connection.py ~L112-130) catches only StopIteration. A KeyError or ValueError from a generated from_json, an exception from a custom generator, or its own explicit `raise ProtocolException('could not parse...')` escapes through `tx(**message)` in Listener.listener_loop (~L973), which is outside every try. The listener dies, and the tx was already popped from mapper, so send() hangs forever and aclose() cannot release it. (2) Callback dispatch in listener_loop (~L1000-1011) logs a handler that raises when called (e.g. wrong arity) and then re-raises, which kills the listener. (3) The receive try in listener_loop catches only TimeoutError, CancelledError and ConnectionClosed. Any other exception from _receive_message (e.g. JSONDecodeError, RuntimeError/ConcurrencyError) ends the task silently and in-flight sends hang. (4) For a flat-session tab, Connection.aopen only calls _attach_session, which returns early once session_id is set. Nothing restarts the browser connection's listener, so every tab command hangs after that listener stops. The minimal local fix has 4 hunks and passes: 9 regression tests fail (hang) on the repo and pass on the prototype, on both Python 3.13 and 3.11. 68 of the repo's own tests also pass against the prototype with real headless Chromium, and mypy shows no new errors.

### Refinements
(a) The finder's real-Chrome repro for A2.4 (Runtime.evaluate custom cmd on browser.connection) does not hang, because Chrome answers with an error since the browser target has no Runtime domain. Use a browser-domain method (Target.getTargets) instead. (b) Severity is per path. For parse failures the tx is popped and lost, so the hang is permanent and aclose cannot release it. For the bad-handler and receive-error paths the tx stays in mapper, so a later send() (which restarts the listener) or aclose() releases it. For tabs it is permanent unless something sends on browser.connection. (c) The receive-error fix must break, not continue: a continue-based handler freezes the whole event loop on py>=3.12 when the error is persistent and synchronous (shown with ConcurrencyError). (d) Optional, not in the prototype: set self.idle on listener exit, so a wait() already blocked on the dead listener's idle event returns. This is pre-existing for ConnectionClosed too. Once hunk 1 is in, parse failures no longer kill the listener, which covers A2.3's tab.wait() side claim for that path. (e) The outer `except Exception: raise` in dispatch becomes dead code and can be dropped in the real PR.

Behaviour changes callers would notice: (a) a parse failure now surfaces as ProtocolException (cause chained), not a hang. Callers that already catch ProtocolException (get_frames, _search_frames, describe_node loops, element resolve, _send_oneshot in _prepare_headless) now degrade gracefully.
